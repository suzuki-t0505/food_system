# 要求内容: CSV 一括取込・一括再引当・一括梱包完了(F-S5・F-S8)

- Issue: [#16](https://github.com/suzuki-t0505/food_system/issues/16)(段階 5 の 1 番目)
- 根拠: [product-requirements.md F-S5・F-S8](../../docs/product-requirements.md)、[functional-design.md §6.1・§6.2・§6.4](../../docs/functional-design.md)
- 対象アプリ: `food_ship` のみ(在庫側の API・画面は変更しない)
- 注: Issue 記載の引き継ぎ資料 `.steering/20261108-stage5-remaining/handoff.md` はリポジトリに存在しないため、上記の永続ドキュメントと既存実装から要求を起こした。

## 背景

発送側は伝票を 1 件ずつ手入力で登録し、再引当・梱包完了も 1 件ずつ行う。1 日 300〜1,000 件の伝票を扱うため、CSV での一括登録と、再引当・梱包完了の一括実行が必要。既存の `FoodShip.ShippingSlips`(確保 → 在庫 API → 結果の反映)を 1 伝票ずつ再利用し、在庫 API の呼び出しをトランザクションに入れない原則は変えない。

## 要求(スコープ)

### 1. CSV 一括取込(F-S5)

- `staff` 以上が、作業画面から CSV をアップロードして取り込める
- 形式: 1 行 = 1 伝票。列は `client_code, client_slip_no, scheduled_ship_date, item_code, order_count`。`client_slip_no` は必須(空欄は検証エラー)
- 文字コードは **UTF-8**(BOM 付きも可)。先頭行は列名の見出し行とする(未決事項 #2。決めた内容は `product-requirements.md` に記録する)
- **検証**(1 行でもエラーがあればファイル全体を取り込まず、行番号つきのエラー一覧を表示する。DB には何も保存しない):
  - 列数・見出しの不一致、必須項目の空欄
  - 未登録・アーカイブ済みの `client_code` / `item_code`
  - `scheduled_ship_date` の形式不正(`YYYY-MM-DD`)、`order_count` が 1 以上の整数でない
  - 出荷期限ルールが無い発注元 × 商品の組み合わせは、手入力と同じ扱い(最低許容期限日は制限なし)
  - ファイル内で `client_slip_no` が重複(同じ発注元 × 商品)、すでに登録済みの有効な伝票と重複
- 検証を通ったら、全行を `input_source = csv` の `pending` で保存してから(保存は `Task` の前に完了)、**出荷予定日の早い順 → ファイル順**に 1 件ずつ引当する
- 在庫不足は検証エラーではなく `shortage` で保存する。取込結果に、行ごと(行番号・伝票番号・発注元・商品・件数)の引当の成否を一覧表示する
- 引当は `Task` で処理し、`handle_info` で進捗(処理済み件数／全件)を更新する
- デフォルト倉庫が未設定のときは、取り込みを拒否して警告を出す(手入力と同じ)

### 2. 一括再引当(F-S5)

- `staff` 以上が、作業画面から実行できる
- `pending` / `shortage` の伝票を、**出荷予定日の昇順 → `slip_no` の昇順**で 1 件ずつ再引当する(`allocate_shipping_slip/2` を再利用)
- **恒久エラー**(`unauthorized` / `not_found` / `validation_failed` など、再試行で直らないもの)の `pending` 行は対象外。一時エラー(`connection`)と、`shortage`、エラーなしの `pending` は対象
- 進捗(処理済み件数／全件)と、伝票ごとの成否(`allocated` / `shortage` / `pending` / 突合 / エラー)を一覧表示する
- アプリが途中で停止しても、残りは `pending` のまま残るので、一括再引当で復旧できる(進捗を持つテーブルは作らない)

### 3. 一括梱包完了(F-S8)

- `staff` 以上が、作業画面で `allocated` の伝票を選択して実行できる(行のチェックボックス＋「選択した伝票を梱包完了にする」。確認ダイアログあり)
- 選択した伝票を **1 件ずつ順に**梱包完了にする(`pack_shipping_slip/2` を再利用)。進捗(完了件数／全件)と伝票ごとの成否を表示する。失敗した伝票は `allocated` のまま残る
- 実行中は一括完了ボタンと対象行(チェックボックス・個別の操作ボタン)を無効化し、二重実行できない

### 共通

- 実行中の画面は `busy` と同じ作り(`Task` ＋ `handle_info`)で、進捗を更新する。画面を開き直しても DB の状態から再表示できる(進捗は画面の状態だけに持つ)
- 操作ログ(`OperationLog`)を、取込・一括再引当・一括梱包完了の単位と、伝票ごとの更新で記録する
- 在庫 API 以外の新しい外部連携は追加しない

## スコープ外

- トータルピック・PDF 帳票(F-S6)、出庫取消(F-S7)
- 取込結果の CSV ダウンロード、エラー行だけの再取込、取込履歴の保存(取込結果は画面表示のみ)
- 発注元ごとに異なる CSV 形式・Shift_JIS の対応(未決事項 #2 は UTF-8 固定で進める)
- 引当処理の並列化(1 件ずつ順に処理する)
- 一括取消、複数日をまたぐ一括梱包の自動選択
- 在庫側(food_vault)の変更

## 受け入れ条件

- 正しい CSV を取り込むと、全行が `csv` / `pending` で保存され、出荷予定日の早い順 → ファイル順に引当されて、行ごとの成否が一覧表示される。在庫不足の行は `shortage` で保存される
- 検証エラーが 1 行でもあるとき、行番号つきのエラー一覧が表示され、伝票は 1 件も保存されない(`client_slip_no` の空欄・ファイル内重複・既存との重複・未登録コード・日付と数値の不正を含む)
- 引当の途中で処理が止まっても、残りが `pending` で残り、一括再引当で出荷予定日昇順 → `slip_no` 昇順に引当される。恒久エラーの `pending` は対象外
- 一括再引当は伝票ごとの成否を一覧表示する
- 一括梱包完了は、選択した `allocated` の伝票を 1 件ずつ処理し、進捗と伝票ごとの成否を表示する。失敗した伝票は `allocated` のまま残る
- 実行中は一括完了ボタンと対象行が無効化され、二重実行できない(取込・一括再引当も同様に二重起動できない)
- `viewer` には取込・一括再引当・一括梱包完了の操作が表示されず、イベントを直接送っても拒否される
- 性能: CSV 1,000 行の検証・保存が 30 秒以内、続く全行の引当完了が 15 分以内(在庫 API 側の応答時間を除く、発送側の処理のオーバーヘッドで確認)
- `mix format --check-formatted`・`mix compile --warnings-as-errors`・`mix test` が通る

## 確認したい点(承認時にご指示ください)

1. CSV に見出し行を必須とする(1 行目を列名として検証する)案でよいか
2. 1 回の取込の上限行数(案: 2,000 行 / ファイル 1 MB。性能目標の 1,000 行の倍)を設けてよいか
3. 一括再引当の対象は、表示中の出荷予定日ではなく**全日付の** `pending` / `shortage` でよいか(案: 全日付)
