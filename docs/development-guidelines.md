# 開発ガイドライン (Development Guidelines)

- 対象: 食品在庫管理システム（`food_vault`）と発送システム（`food_ship`）の開発に関わる全員（AI エージェントを含む）
- 位置づけ: 「どう進めるか」を定める。何を作るかは [product-requirements.md](product-requirements.md)・[functional-design.md](functional-design.md)、技術は [architecture.md](architecture.md)、置き場所は [repository-structure.md](repository-structure.md)、コード規約は [coding-rules.md](coding-rules.md)（`[必須]` / `[推奨]` 付き）、用語は [glossary.md](glossary.md) に従う
- 本書の「規則」は新規に定めたものを含む。変更は承認を得て本書を更新する

---

## 1. 開発プロセス（スペック駆動開発）

### 1.1 基本フロー

1. **ドキュメント作成**: 永続ドキュメント（`docs/`）で「何を作るか」を定義する
2. **作業計画**: `.steering/{YYYYMMDD}-{タスク名}/` で「今回何をするか」を計画する
3. **実装**: `tasklist.md` に従って実装し、進捗を随時更新する
4. **検証**: テストと動作確認
5. **更新**: 必要に応じて永続ドキュメントを更新する

`docs/ideas/` のドラフトから直接実装に進まない。

### 1.2 実装前の確認（必須）

新しい実装を始める前に、必ず次を行う。

1. [CLAUDE.md](../CLAUDE.md) を読む
2. 関連する永続ドキュメント（`docs/`）を読む（機能は functional-design、用語は glossary、技術は architecture）
3. Grep で既存の類似実装を探す（coding-rules §1.3）
4. 既存パターンを理解してから実装を開始する

### 1.3 作業ごとのステアリングファイル

作業ごとに `.steering/{YYYYMMDD}-{タスク名}/` を作成する（例：`20261201-add-inventory-receipt`）。

| ファイル | 内容 |
| :-- | :-- |
| `requirements.md` | 今回の作業の要求内容（対応する要件 ID：F-V2 など、受け入れ条件） |
| `design.md` | 実装アプローチ（既存コードを調査したうえでの設計、変更するファイル、DB 変更、影響範囲） |
| `tasklist.md` | チェックボックス形式の具体的なタスク。実装の進捗に合わせて随時更新する |

- 作業の粒度は、1 つの機能要件（例：F-V2 入荷登録と在庫一覧）、またはそれを分割した 1 つのまとまり。
- 作業が終わっても削除せず、履歴として保持する。
- ドキュメント（`requirements.md` など）は 1 ファイルずつ作成し、承認を得てから次に進む（CLAUDE.md）。

### 1.4 推奨する実装順序

[リリース計画](product-requirements.md#機能要件)（P0 → P1 → P2）に沿って、依存関係の順に進める。

| 段階 | 内容 | 要件 ID |
| :-- | :-- | :-- |
| 0 | **基盤整備**: ULID 依存の検証、`{App}.Schema`、Logger・OperationLog・Permission の雛形、`check` ターゲット・`credo`・CI | architecture §4・§14 |
| 1 | **認証・ユーザー管理**（両アプリ。`phx.gen.auth` を削減して ULID 化、`current_scope`、認可 3 層） | F-A1, F-A2 |
| 2 | **在庫側の核**: マスタ → 入荷・在庫一覧・受払履歴 → 引当・確定・解除（ロック、荷崩し、冪等）→ 棚卸調整 | F-V1, V2, V3, V5, V6 |
| 3 | **在庫 API**（サービストークン、共通エラー形式、冪等性、①〜③⑤⑥⑦） | F-V4 |
| 4 | **発送側（P0）**: マスタ → `Inventory.Client` → 伝票登録・再引当 → 作業画面・数量変更・取消 → 梱包完了 | F-S1〜S4 |
| 5 | **P1**: 出庫取消（在庫 ④ と発送）、緊急操作、倉庫間移動、CSV 取込・一括再引当、トータルピック・PDF 帳票（環境構築は別セッション）、一括梱包完了 | F-V7〜V9, F-S5〜S8 |

在庫側の API（段階 3）を先に仕上げてから発送側（段階 4）に進む。発送側の結合テストは、在庫側の API 仕様（functional-design §7）に対するスタブで進められる。

## 2. 環境構築と日常コマンド

### 2.1 初回セットアップ

```bash
make setup    # 両アプリの npm i と mix setup（ecto.create / migrate / seeds / assets）
docker compose up -d
```

| サービス | URL / ポート | 備考 |
| :-- | :-- | :-- |
| 在庫管理システム | http://localhost:4000 | `food_vault_web` |
| 発送システム | http://localhost:4001 | `food_ship_web`（コンテナ内は 4000） |
| PostgreSQL | localhost:5432 | `food_vault_dev` / `food_ship_dev` |
| pgAdmin | http://localhost:7777 | 開発用 |

### 2.2 コマンド（コンテナ経由）

**ホストで直接 `mix` を叩かない**。次のコマンドは `Makefile` に集約されている（両アプリに対して実行する）。

| コマンド | 内容 |
| :-- | :-- |
| `make mix_compile` | `mix compile --warnings-as-errors --force` |
| `make mix_format` | `mix format` |
| `make mix_credo` | `mix credo --all`（`credo` 導入後） |
| `make mix_test` / `make mix_test_cover` | テスト／カバレッジ |
| `make mix_clean` | `mix clean` |
| `make check`（整備予定） | 上の compile → format → credo → test をまとめて実行 |

1 つのアプリだけを対象にする場合は `docker compose run --rm food_vault_web mix ...` / `food_ship_web` を直接使う。

### 2.3 品質ゲート（プッシュ前に必ず通す）

1. コンパイル警告ゼロ（`--warnings-as-errors`）
2. `mix format` で差分が出ない
3. `mix credo --all` が通る
4. `mix test` が通る

CI でも同じ `check` を回す（整備予定、[architecture §14](architecture.md#14-開発環境品質ゲートci)）。失敗したままプッシュしない。

## 3. Git の運用

### 3.1 ブランチ

- `main` は常にデプロイ可能（テストが通る）状態に保ち、直接コミットしない。
- 作業ブランチは用途別の接頭辞を付ける: `feature/{要件ID}-{内容}`（例：`feature/f-v2-inventory-receipt`）、`fix/{内容}`、`docs/{内容}`。自動化ツールが指定するブランチ名（例：`claude/...`）がある場合はそれに従う。
- 1 つのブランチに複数の無関係な変更を混ぜない。

### 3.2 コミット

| 規則 | 内容 |
| :-- | :-- |
| メッセージ | 1 行目に「接頭辞: 要約」（日本語）。必要なら空行のあと本文に「何を・なぜ」を箇条書き |
| 接頭辞 | `feat`（機能）／`fix`（不具合）／`docs`（ドキュメント）／`refactor`／`test`／`chore`（設定・依存・ビルド） |
| 粒度 | 1 コミット = 1 つの意味のある変更。テストと実装は同じコミット（または連続）に含める |
| 含めないもの | 秘密情報、生成物（`deps/`・`_build/`・`priv/static/`）、個人の環境設定（`.env` など）・実行時のロックファイル（[repository-structure §6.2](repository-structure.md#62-ルートの-gitignore-の方針)） |
| 履歴 | 他人のブランチの履歴を書き換えない。push 済みのコミットを `amend` しない |

### 3.3 プルリクエスト

- 概要に「何を・なぜ」「対応する要件 ID／`.steering/` のパス」「検証内容（テスト結果・動作確認）」「影響範囲（DB 変更・API 変更）」を書く。
- 次を満たしてから出す: 品質ゲート通過、tasklist の更新、必要なドキュメント更新（§8）。
- **DB スキーマ・API・権限の変更を含む PR は、両アプリへの影響（連携 API の契約）をレビュー観点に含める**（§7）。

## 4. コーディングの運用

コード規約の本体は [coding-rules.md](coding-rules.md)。ここでは運用上の要点と、本プロジェクト固有の取り決めだけを示す。

### 4.1 規約の優先順位

1. `[必須]` は例外なく守る。`[推奨]` は理由があれば外れてよい（PR で説明する）
2. 規約とコードが食い違ったら、コードを正とするか規約を更新する（どちらかに寄せ、放置しない）
3. 規約に書かれていない判断は、既存の類似実装に合わせる（§1.2）

### 4.2 本プロジェクトで特に守ること

| 領域 | 規則 |
| :-- | :-- |
| スキーマ | `use Ecto.Schema` を直書きしない。`use {App}.Schema`（ULID）を使う。列挙は `Ecto.Enum`。`@spec` / `@type` は書かない |
| Context | Context ＋ スキーマの 2 層だけ。子エンティティ専用の Context を作らない。書き込み関数は操作者を第 1 引数に取る（画面は `user`、在庫 API は `{:api, operator}`） |
| Web 層 | Context の公開 API だけを呼ぶ。`Repo` やスキーマのクエリを直接書かない。`core_components.ex` は改変しない。表示用の計算（総バラ数など）はテンプレートに書かず `Utils.Calc` に置く |
| トランザクション | 複数テーブルの更新は `Ecto.Multi` ＋ `Repo.transact/1`。`cast_assoc` / `put_assoc` は使わない。Multi のステップ名は文字列 |
| **在庫のロック** | ロットは **ロックキー `(warehouse_id, item_id, expiration_date, received_date, id)` の昇順で、1 クエリでまとめて `FOR UPDATE`**。先に `items` を `FOR SHARE`。操作の途中で追加のロットをロックしない |
| **DB 制約** | 不変条件は changeset と CHECK 制約の両方。一意制約は `unique_constraint` と `unsafe_validate_unique` を対で書き、対応する `unique_index` を必ず作る |
| **外部 I/O（発送）** | 在庫 API はローカル DB のトランザクションの外で呼ぶ。先に `pending` で保存 → API → 結果で更新。リトライは `retry: :transient`。画面からの呼び出しは `Task` ＋ `handle_info` |
| **冪等性** | 状態を変える API は冪等にする。再送は内容一致のときだけ既存を返す。冪等応答では履歴を追加しない |
| 認証・認可 | 認可は HTTP plug・`on_mount`・イベント単位の 3 層。判定は `Permission.can?/2` に一本化。`:if` だけで隠さない。`current_user` は `current_scope.user` と読み替える |
| 秘密情報・設定 | `runtime.exs` に集約し、必須値は未設定なら起動時に落とす。`System.get_env` をアプリコードから直接呼ばない。モジュール属性で設定を読まない |
| ログ | カテゴリ付き Logger ラッパー経由。成功した書き込みだけ操作ログに出し、`Task` の中では出さない。機微データは出力側で自動マスク（呼び出し側で `Map.drop` しない） |
| 日時 | UTC で保存し、表示直前にだけ JST に変換する。`date` 型の業務日付は変換しない |
| 文言 | 日本語を直書き（gettext を使わない）。成功・失敗メッセージは「ます形＋句点」、バリデーションは「〜してください」。リソース名は [glossary.md](glossary.md) に揃える。同じ意味の文言を揺らさない |
| 在庫システムと発送システム | **一方のコードを他方から参照しない**。連携は HTTP API のみ。同形のモジュールは両方に置く（コピーを許容し、変更は両方に反映） |

### 4.3 用語の使い分け

画面・帳票・コードの用語は用語集に統一する。特に、「出庫」は在庫側の用語（発送側の画面では使わない）、「引当解除」「取消」「出庫取消」は別の操作、「荷崩し」と「荷まとめ」は逆方向、最低許容期限日は両システムとも `min_expiration_date`（[glossary §8](glossary.md#8-用語の使い分け揺れを防ぐ)）。

## 5. テストの指針

[architecture §13](architecture.md#13-テスト戦略)の必須の観点に従う。運用上の要点は次のとおり。

| 項目 | 規則 |
| :-- | :-- |
| いつ書くか | 機能・修正と同じ PR に含める。**受け入れ条件**（functional/requirements の各チェック項目）を、テストでも確認できる形にする |
| 構成 | `test/` は `lib/` をミラー。Context テストの `describe` は「関数名/アリティ」、LiveView は画面名。`test` は日本語の説明 |
| フィクスチャ | Context の公開 API 経由で作る。`Repo.insert` で直接作らない。FK はデフォルトに入れない |
| 成功系と失敗系 | 対で書き、**失敗時のロールバックまで検証する** |
| 並行性 | 引当・移動・マスタ変更の競合は、複数プロセスで同時に走らせて検証する（二重引当、デッドロックなし） |
| mock | 外部 I/O 境界だけ（`FoodShip.Inventory.Client` の HTTP は `Req.Test` のスタブ、`Utils.Pdf`）。自作のモジュールを mock しない |
| LiveView | 画面の表示と DB の書き込みの両方を検証する |
| 実行 | `async` は既定 false（DB を共有する）。DB に触らない純関数だけ `async: true`。`mix test` は毎回 DB を再作成 |
| 生成されたままのテスト | 手を入れていないテストは `@describetag :skip` で凍結し、コメントアウトで残さない |
| 動作確認 | 画面を変更した場合は、実際にアプリを起動して画面で確認する（ブラウザの確認ができない場合は、その旨を PR に書く） |

## 6. セキュリティの指針

- **認証情報**: パスワードは bcrypt、最小 12 文字。平文をログ・画面に出さない（`redact: true`）。ログイン失敗のメッセージは 1 種類。
- **認可**: ロールごとの権限を、plug・`on_mount`・イベントの 3 層で検査する。`viewer` に書き込み系のイベントを許さない。管理者操作（出庫取消・棚卸調整・ユーザー管理・マスタ編集）は `admin` のみ。
- **在庫 API**: サービストークンは定数時間で比較し、値をログに出さない。複数トークンでローテーションする。本番は TLS ＋ `/api` の送信元制限。
- **入力**: 数量は整数、負数は拒否（changeset ＋ CHECK 制約）。ID の形式不正は 404／422 にし、500 にしない。CSV は全行を検証してから保存する。
- **帳票**: テンプレートに外部リソースを書かない。差し込む値は HEEx でエスケープする。本番は `no_sandbox` を使わない。
- **秘密情報**: コンパイル時 config に置かない（`runtime.exs` のみ）。リポジトリに秘密情報の値をコミットしない。
- **依存**: 追加する依存は、保守状況・対応バージョン（Elixir 1.20 / Ecto 3.13）を確認する。未使用の依存は `mix deps.unlock --unused` で整理する。
- 必要に応じて、`security-review`（保留中の変更の確認）や `security-audit` スキルを使う。

## 7. レビュー観点（チェックリスト）

PR を出す側・レビューする側が共通で使う。

**設計・仕様**
- [ ] 対応する要件 ID と受け入れ条件を満たしているか。範囲外の変更が混ざっていないか
- [ ] 用語・ステータス・API の項目名が [glossary.md](glossary.md)・[functional-design.md](functional-design.md) と一致しているか

**データ・並行制御**
- [ ] 不変条件を changeset と CHECK 制約の両方で守っているか。一意制約は 2 つセット＋ `unique_index` があるか
- [ ] FK に索引があるか。`create index` は `create table` の外か。NOT NULL 追加に `default:` があるか
- [ ] 在庫の更新が単一トランザクションで、ロック順序（ロックキー・1 クエリ）に従っているか
- [ ] 状態を変える処理が冪等か、履歴（受払履歴・オーダー履歴・実行者）を残しているか

**認証・認可・セキュリティ**
- [ ] 認可が 3 層（plug・`on_mount`・イベント）で揃っているか。ボタンを隠すだけにしていないか
- [ ] 秘密情報・機微データがコード・ログに出ていないか

**連携（2 アプリ）**
- [ ] API の契約（リクエスト・レスポンス・エラー形式）を変えたら、両アプリと functional-design §7 を更新したか
- [ ] 在庫 API の呼び出しがローカル DB のトランザクションの外か。失敗時に `pending` で復旧できるか

**コード品質**
- [ ] コンパイル警告・format・credo・テストがすべて通るか。失敗系とロールバックのテストがあるか
- [ ] Web 層から `Repo` を呼んでいないか。計算式をテンプレートに書いていないか。`core_components.ex` を改変していないか
- [ ] 文言が「ます形＋句点」などの規則に合っているか

## 8. ドキュメントの更新ルール

変更の種類に応じて、永続ドキュメントを同じ PR（または直後）で更新する。更新が不要な理由があれば PR に書く。

| 変更 | 更新するドキュメント |
| :-- | :-- |
| 要件の追加・変更・優先度の変更 | product-requirements.md |
| 機能・画面・データ・API・権限・ステータスの変更 | functional-design.md（API の契約は両アプリで整合） |
| 技術選定・実装方針・設定項目・環境変数・テスト方針の変更 | architecture.md |
| ファイル・ディレクトリの追加・命名規則の変更 | repository-structure.md |
| 開発の進め方・規約の運用の変更 | development-guidelines.md |
| 新しい用語・ステータス・名称の変更 | glossary.md |
| コード規約の追加・修正 | coding-rules.md |
| 実装方針の議論・技術調査・設計のたたき台 | docs/ideas/ |

- **永続ドキュメントの更新は承認を得て行う**（頻繁に変えない。「北極星」を保つ）。
- 実装中に設計の誤りや不足に気づいたら、コードだけで解決せず、該当ドキュメントを先に（または同時に）直す。
- 実装した作業は `.steering/` に残し、`tasklist.md` を完了状態にする。

## 9. 完了の定義（Definition of Done）

次を満たしたとき、作業が完了したとする。

- [ ] 対応する要件の受け入れ条件をすべて満たしている（テストまたは動作確認で確認した）
- [ ] 品質ゲート（compile 警告ゼロ・format・credo・test）が通っている
- [ ] 失敗系とロールバックのテストがある。並行性・冪等性が要件にある機能は、それを確認するテストがある
- [ ] 認可（ロール別の許可・拒否）のテストがある
- [ ] 必要な永続ドキュメントを更新した（§8）
- [ ] `.steering/` の tasklist を更新した
- [ ] レビュー（§7）を通った

## 10. コミュニケーションの規則

- 対話・ドキュメント・コミットメッセージは **日本語**で行う。
- 質問への回答は、指定がなければ短い文章で、**結論から簡潔に**述べる。感想や相槌は省く。
- 長いエラーは全文を出さず、重要な部分だけを示し、原因と対処法を簡潔に伝える。
- ドキュメントの作成が終わったら、「[ドキュメント名]の作成が完了しました。内容を確認してください。承認いただけたら次のドキュメントに進みます。」と明確に伝え、承認を待つ。
