# **発送システム 基本設計書**

## **1\. システム概要と基本方針**

発注元（EC・百貨店など）から順不同で届く出荷伝票（紙・FAX・PDF・CSV）を一元管理し、出荷予定日順の作業指示・梱包管理を行うとともに、既存の「食品在庫管理システム」とAPI連携して厳密な期限管理（FEFO）および在庫減算を自動化するシステムです。

### **📌 コア要件・決定仕様まとめ**

| 項目 | 決定仕様 | 備考 |
| :---- | :---- | :---- |
| システム構成 | 発送システム専用のDBを構築し、在庫管理システムとは **API連携** で疎結合にする | 在庫側の複雑な自動荷崩し・受払履歴ロジックの二重実装を防ぐため |
| 対象倉庫 | 特定の1倉庫に固定（warehouse\_id を環境変数・設定値として保持） | 画面上での倉庫選択は省略し、入力負荷を軽減 |
| 伝票入力方法 | 画面からの手入力（紙・FAX・PDF閲覧）および **CSV**一括取込 に対応 | 1回の伝票入力・取込単位ごとに在庫引当を行う |
| 順不同伝票の管理 | 「受付日」ではなく **「出荷予定日」** を軸に自動ソート・グルーピング表示 | 梱包完了後に追加の翌日出荷分が届いた場合も、未梱包分のみを識別可能にする |
| **数量・**箱数の換算 | 商品ごとに「1件あたりの標準箱数・商品数量（バラ数）」をマスタ化 | 基本は 1件 \= 1箱 \= 1個、一部 1件 \= 3箱 \= 3個 等に対応（手修正も可） |
| 在庫要求単位 | 在庫管理システムへはすべて **「バラ数（req\_pieces）」** として要求（req\_cases \= 0） | バラ不足時のケース開封は在庫管理システム側の「自動荷崩し機能（AUTO\_BREAK）」に一任 |
| 出荷期限ルール | 「発注元 × 商品（メーカー含む）」ごとに 出荷予定日からの最低残日数 を定義 | 算出した最低許容期限日（min\_expiration\_date）を在庫引当APIへ渡し、先出し（FEFO）引当 |
| 在庫減算のタイミング | ① 伝票登録時：在庫引当APIで仮押さえ（ALLOCATED）＆在庫不足チェック② 梱包完了時：出庫確定APIで実在庫を減算（SHIPPED） | 2段階連携により、入力時点での欠品検知と梱包完了時の確実な実在庫減算を両立 |

## **2\. データベース設計（発送システム専用DB）**

全5テーブル（マスタ3、トランザクション2）で構成します。

### **① 発注元マスタ (clients)**

得意先（EC、百貨店など）を管理します。

| カラム名 (論理名) | カラム名 (物理名) | 型 | 制約 / 説明 |
| :---- | :---- | :---- | :---- |
| 発注元ID | client\_id | BIGINT | PK (主キー) |
| 発注元コード | client\_code | VARCHAR | UNIQUE (CSV取込時の識別コード等) |
| 発注元名 | client\_name | VARCHAR | NOT NULL (例：ECサイト、百貨店A) |
| 有効フラグ | is\_active | BOOLEAN | DEFAULT TRUE |

### **② 発送商品・梱包換算マスタ (shipping\_items)**

在庫管理システムの商品マスタ（items）と紐付けつつ、発送システム独自の「件数 ➔ 箱数・商品数量」の換算ルールを保持します。

| カラム名 (論理名) | カラム名 (物理名) | 型 | 制約 / 説明 |
| :---- | :---- | :---- | :---- |
| 発送商品ID | shipping\_item\_id | BIGINT | PK |
| 在庫システム商品ID | inventory\_item\_id | BIGINT | NOT NULL / 在庫システム items.item\_id（API連携キー） |
| 商品コード | item\_code | VARCHAR | UNIQUE (JANコードや自社品番・CSV取込用) |
| メーカー名 | maker\_name | VARCHAR | 画面表示・検索用（在庫システムと同期またはマスタ保持） |
| 商品名 | item\_name | VARCHAR | NOT NULL / 画面表示用 |
| 1件あたり標準箱数 | boxes\_per\_order | INT | NOT NULL (DEFAULT 1\) ※3箱になる商品は 3 |
| 1件あたり商品数量 | pieces\_per\_order | INT | NOT NULL (DEFAULT 1\) ※在庫を減らす基準値（バラ数） |
| 有効フラグ | is\_active | BOOLEAN | DEFAULT TRUE |

### **③ 出荷期限ルールマスタ (expiration\_rules)**

「発注元 × 商品（メーカー含む）」ごとの出荷可能期限ルールを管理します。

| カラム名 (論理名) | カラム名 (物理名) | 型 | 制約 / 説明 |
| :---- | :---- | :---- | :---- |
| ルールID | rule\_id | BIGINT | PK |
| 発注元ID | client\_id | BIGINT | FK (clients.client\_id) |
| 発送商品ID | shipping\_item\_id | BIGINT | FK (shipping\_items.shipping\_item\_id) |
| 最低残日数 | min\_remaining\_days | INT | NOT NULL (出荷予定日から何日以上の期限が必要か。例：30) |

* 💡 複合ユニーク制約：UNIQUE (client\_id, shipping\_item\_id)  
* 💡 最低許容期限日の計算式：$最低許容期限日=出荷予定日+min\backslash \_remaining\backslash \_days$

### **④ 出荷伝票テーブル (shipping\_slips)**

順不同で届く伝票を管理し、入力単位ごとに在庫管理システムの「出庫オーダーID（order\_id）」と紐付けます。

| カラム名 (論理名) | カラム名 (物理名) | 型 | 制約 / 説明 |
| :---- | :---- | :---- | :---- |
| 伝票ID | slip\_id | BIGINT | PK |
| 発注元ID | client\_id | BIGINT | FK (clients.client\_id) |
| 発送商品ID | shipping\_item\_id | BIGINT | FK (shipping\_items.shipping\_item\_id) |
| 出荷予定日 | scheduled\_ship\_date | DATE | NOT NULL (**ソート・**集計の基準軸) |
| 件数 | order\_count | INT | NOT NULL (伝票に記載された件数) |
| 箱数 | box\_count | INT | NOT NULL (初期値：$件数\times 標準箱数$ ※画面で手修正可) |
| 出庫総数量（バラ） | total\_piece\_qty | INT | NOT NULL (初期値：$件数\times 商品数量$ ※在庫要求バラ数) |
| 算出最低期限日 | required\_exp\_date | DATE | NOT NULL (引当時に適用した最低許容期限日) |
| 在庫出庫オーダーID | inventory\_order\_id | BIGINT | NULL可 (在庫システム側の shipment\_orders.order\_id) |
| ステータス | status | ENUM | ALLOCATED(引当済・未梱包) / SHORTAGE(在庫不足エラー) / PACKED(梱包完了・在庫減算済) / CANCELLED(取消) |
| 登録経路 | input\_source | ENUM | MANUAL(手入力) / CSV(CSV取込) |
| 登録日時 | created\_at | TIMESTAMP | NOT NULL |
| 梱包完了日時 | packed\_at | TIMESTAMP | NULL可 |

### **⑤ 引当ロット明細控え (slip\_allocated\_lots)**

在庫管理システムから返却された「どの期限日のロットが何個引き当てられたか」を保持し、現場のピッキング画面に表示します。

| カラム名 (論理名) | カラム名 (物理名) | 型 | 制約 / 説明 |
| :---- | :---- | :---- | :---- |
| 明細ID | id | BIGINT | PK |
| 伝票ID | slip\_id | BIGINT | FK (shipping\_slips.slip\_id) |
| 在庫ロットID | inventory\_lot\_id | BIGINT | 在庫システム側の inventory\_lots.lot\_id |
| 期限日 | expiration\_date | DATE | ピッキング時に目視確認する賞味・消費期限日 |
| 引当バラ数 | allocated\_pieces | INT | 該当ロットからピッキングすべき個数 |

## **3\. 在庫管理システムとのAPI連携・改修仕様**

### **🔧 在庫管理システム側の拡張ポイント（1箇所のみ）**

在庫管理システムの「ロジック①：出庫時の自動引当 ＆ 自動荷崩し」における対象ロット抽出条件を以下のように拡張します。

* 改修前：WHERE warehouse\_id \= :warehouse\_id AND item\_id \= :item\_id AND expiration\_date \>= :shipment\_date  
* 改修後：WHERE warehouse\_id \= :warehouse\_id AND item\_id \= :item\_id AND expiration\_date \>= COALESCE(:min\_expiration\_date, :shipment\_date)  
* **ソート順（変更なし）**：ORDER BY expiration\_date ASC, received\_date ASC, lot\_id ASC（条件を満たすロットの中で最も古いものから先出し）

### **🔄 APIインターフェース定義（3本）**

#### ***① 出庫引当API（伝票登録・CSV取込時）***

* エンドポイント例：POST /api/v1/inventory/orders/allocate  
* 処理内容：指定された最低許容期限日以降のロットからバラ数を引き当て（不足時は自動荷崩し AUTO\_BREAK を実行）、ステータスを ALLOCATED として在庫をロックする。  
* **リクエストJSON**：

{  
  "warehouse\_id": 1,  
  "shipment\_date": "2026-11-15",  
  "external\_slip\_id": 1001,  
  "items": \[  
    {  
      "item\_id": 105,  
      "req\_cases": 0,  
      "req\_pieces": 3,  
      "min\_expiration\_date": "2026-12-15"  
    }  
  \]  
}

* **レスポンスJSON（成功時）**：

{  
  "status": "ALLOCATED",  
  "inventory\_order\_id": 9876,  
  "allocated\_lots": \[  
    {  
      "lot\_id": 55,  
      "expiration\_date": "2026-12-20",  
      "allocated\_pieces": 3  
    }  
  \]  
}

#### ***② 出庫確定API（梱包完了ボタン押下時）***

* エンドポイント例：POST /api/v1/inventory/orders/{order\_id}/ship  
* 処理内容：対象オーダーのステータスを SHIPPED に更新し、inventory\_lots の現在バラ数（piece\_qty）および引当済バラ数（allocated\_piece\_qty）を減算。受払履歴（inventory\_transactions）に SHIP を記録する。

#### ***③ 引当解除（キャンセル）API（伝票修正・取消時）***

* エンドポイント例：POST /api/v1/inventory/orders/{order\_id}/cancel  
* 処理内容：梱包前（ALLOCATED 状態）の伝票がキャンセルまたは数量変更された際、allocated\_piece\_qty のロックを解除し、ステータスを CANCELLED に更新する。

## **4\. 業務フローと例外処理設計**

### **📋 基本業務フロー**

1. **伝票の入力・CSV**取込

* オペレーターが「発注元」「出荷予定日」「商品」「件数」を入力（またはCSV取込）。  
* システムがマスタを参照し、「箱数」「出庫総数量（バラ）」「最低許容期限日」を自動算出。  
* 同時に **「① 出庫引当API」** を呼び出し、在庫の有効性チェックと仮押さえを実行。

2. **出荷日別のピッキング・**梱包作業

* 作業画面は **「出荷予定日」ごと** にタブ分け・ソートされて表示。  
* 各伝票行には、引き当てられたロットの **「期限日（例：2026-12-20）× 個数」** が明記されており、現場担当者はその期限の商品を目視確認してピッキング・梱包を行う。  
* 梱包時に実際の箱数が変わった場合は、画面上で箱数を修正可能。

3. 梱包完了と実在庫の減算

* 梱包が終わった伝票の「梱包完了」ボタンを押下（複数行の一括完了も可）。  
* **「② 出庫確定API」** が呼ばれ、在庫管理システムの実在庫が減算される。画面上のステータスは PACKED（梱包完了） となりグレーアウトする。

4. **追加伝票への対応（順不同・当日追加）**

* 翌日出荷分を梱包完了したあとに追加の翌日出荷伝票が届いた場合も、入力すると同じ出荷予定日タブ内に **「未梱包（ALLOCATED）」**としてハイライト表示 される。  
* すでに梱包済みの在庫は減算（またはロック）されているため、残りの有効在庫から安全に先出し引当が行われる。

### **🛡️ 例外ケースへの対策仕様**

| 例外シナリオ | システムの挙動・対策仕様 |
| :---- | :---- |
| **① 伝票入力時に在庫不足（期限条件を満たす在庫が足りない）** | 入力内容が消えないよう、発送システム側にはステータス **SHORTAGE（在庫不足）** として伝票を保存し、画面にアラートを表示する。在庫システム側で入荷処理が行われた後、画面の「再引当ボタン」を押すことで引当APIを再実行できる仕組みとする。 |
| **② 梱包前の「件数変更」または「伝票キャンセル」** | 数量を変更する場合は、システム裏側で自動的に **「旧オーダーの引当解除API ➔ 新数量での出庫引当API」** を連続実行し、在庫ロック数のズレを防止する。 |
| **③ 梱包完了（PACKED）後の取り消し（誤操作など）** | 誤操作防止のため、梱包完了ボタン押下時に確認ダイアログを表示する。万が一 SHIPPED 後に取り消す場合は、在庫の証跡（inventory\_transactions）を守るため、管理者権限でのみ「取消調整（返品入庫相当の加算処理）」を行える仕様とする。 |

## **5\. 画面構成案（主要3画面）**

5. **伝票登録・CSV**取込画面

* 手入力フォーム（発注元・出荷予定日・商品・件数を入れると、箱数・バラ数・要求期限日をリアルタイム自動計算）  
* CSVドラッグ＆ドロップ取込エリア（取込結果と引当成否の一覧プレビュー）

6. **出荷日別 作業・梱包消込画面（メイン画面）**

* 出荷予定日別のサマリータブ（例：11/14 (残0件)、11/15 (残3件)）  
* 状態フィルタ（未梱包のみ表示 / 在庫不足エラーのみ表示 / すべて表示）  
* 伝票一覧リスト（ピッキング対象の期限日表示、箱数のインライン編集、個別・一括の「梱包完了」ボタン）

7. マスタ管理画面

* 発注元マスタ、発送商品・梱包換算マスタ（1件あたりの箱数・バラ数設定）、出荷期限ルールマスタ（発注元×商品の残日数設定）のCRUD画面
