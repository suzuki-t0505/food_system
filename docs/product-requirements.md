# プロダクト要求定義書 (Product Requirements Document)

- 対象: 食品在庫管理システム（`food_vault`）と発送システム（`food_ship`）の 2 アプリ
- 出典: [食品在庫管理システム設計.md](ideas/食品在庫管理システム設計.md)（v2.2）、[発送システム 基本設計書.md](ideas/発送システム%20基本設計書.md)（v2.2）。用語は [glossary.md](glossary.md) に従う
- 本書は「何を作るか」を定義する。「どう作るか」は `functional-design.md`・`architecture.md` で定義する
- 確認済みの前提（ユーザー回答）: ピーク時の出荷伝票は **300〜1,000 件/日**、主な利用者は **出荷事務担当者**、**KPI は本書では定義しない**、リリースは **最小構成から段階的**

## プロダクト概要

### 名称

**食品在庫管理システム＋発送システム（food_vault / food_ship）** - 期限（FEFO）と荷姿（ケース・バラ）に対応した在庫管理と、順不同の出荷伝票を出荷予定日順に捌く発送管理

### プロダクトコンセプト

- **期限と荷姿を前提にした在庫管理**: 在庫を「倉庫 × 商品 × 期限日 × 入荷日」のロットで持ち、ケースとバラを分けて管理する。引当は期限の近いロットから自動で行い、バラ不足時は自動で荷崩しする
- **出荷予定日を軸にした発送管理**: 紙・FAX・PDF・CSV で順不同に届く伝票を、受付順ではなく出荷予定日で並べ、梱包済みか未梱包かを一目で分かるようにする
- **疎結合な 2 システム構成**: 発送は専用 DB を持ち、在庫は API（一方向 HTTP）でのみ連携する。引当・荷崩し・受払履歴などの在庫ロジックは在庫側に 1 か所だけ持つ

### プロダクトビジョン

食品の出荷現場で、「期限の短い在庫を先に出す」「欠品を入力した時点で知る」「現場に迷わず作業指示を渡す」を、人の記憶と手作業に頼らず実現する。発送担当者は伝票を入力（または CSV で取込）するだけで、期限ルールを満たす在庫の引当と欠品の検知が自動で行われ、トータルピック表と作業指示書を印刷して現場に渡せる。在庫は常にロット単位で期限付きに把握でき、誰がいつ何を変えたかが履歴として残る。

### 目的

- 発注元ごとの出荷期限ルール（出荷予定日から N 日以上の残り期限）を、引当時に自動で守る
- 伝票入力の時点で在庫不足を検知し、梱包完了の時点で在庫を確実に減算する（二重引当・二重減算を起こさない）
- 出荷予定日ごとの作業（ピッキング・梱包）を、複数伝票をまとめたトータルピックと PDF 帳票で効率化する
- 在庫の変動と出庫の状態遷移を、操作者付きの履歴として追跡できるようにする

## ターゲットユーザー

### プライマリーペルソナ: 出荷事務担当者（`staff` ロール）

> 本書のペルソナは設計書から導出したものであり、実際の現場ヒアリングで検証する（未決事項 #1）。

- 発注元（EC・百貨店など）から、紙・FAX・PDF・CSV の形で、出荷予定日がバラバラの伝票を受け取って処理する
- 1 日 300〜1,000 件のピーク時でも、同じ「発注元 × 商品 × 出荷予定日」の伝票が追加で届き、梱包完了後にも追加が入る
- 発注元ごとに「期限が N 日以上残っている商品しか出荷できない」ルールがあり、人手では在庫の期限を見て判断している（現在の課題: 期限判定の手間・見落とし、欠品に気づくのが梱包時になること）
- 期待する解決策: 入力した時点で引当と欠品の検知が済み、現場に渡す作業指示書が自動で出る
- 典型的な 1 日の流れ（設計書から導出）:
  1. 朝: 当日・翌日以降の伝票を手入力または CSV で取り込む。引当結果（`allocated` / `shortage`）を確認する
  2. 欠品（`shortage`）は、入荷後の再引当や数量変更で解消する。遠い日付の伝票に在庫を取られている場合は手動で調整する
  3. 出荷予定日タブで「トータルピック作成」を行い、トータルピック表と作業指示書を PDF で印刷して現場に渡す
  4. 日中: 追加伝票を登録し、追加ピックを作成する。梱包が終わった伝票を「梱包完了」で消し込む（一括も可）
  5. 梱包後に誤りが見つかった場合は管理者に出庫取消を依頼する

### 利用者ロール

ペルソナは出荷事務担当者だが、システムは次の 3 ロールで権限を分ける（在庫・発送で共通、ユーザーは別管理）。

| ロール | 主な担当 | できること |
| :-- | :-- | :-- |
| `admin`（管理者） | 責任者・在庫管理者 | すべて。ユーザー管理、マスタ編集、棚卸調整・入荷訂正、出庫取消、緊急操作 |
| `staff`（担当者） | 出荷事務担当者・倉庫担当者 | 業務操作（入荷、出庫オーダー、移動、伝票登録、梱包完了、トータルピック、帳票出力） |
| `viewer`（閲覧） | 参照のみの関係者 | すべての参照 |

## 成功指標(KPI)

**本書では KPI を定義しない。** 次の方針とする。

- 数値目標は、現場ヒアリングと運用開始後の実測（伝票数、欠品の件数と検知タイミング、入力〜帳票出力までの所要時間など）をもとに、**リリース後に別途定義**する
- そのため、リリース後に計測できるよう、次のデータをシステムが保持する（要件として [非機能要件](#非機能要件)・機能要件に含める）:
  - 伝票の登録・引当・梱包完了・取消・出庫取消の日時と実行者（発送側 `shipping_slips`、在庫側 `shipment_order_events`）
  - 在庫の増減の履歴（受払履歴）
  - 引当失敗の理由と回数（`allocation_error`）

## 機能要件

優先度は「最小構成から段階的に」リリースする方針に基づく。**P0 ＝ 第 1 リリース（MVP）**、P1 ＝ 第 2 リリース以降の早い段階、P2 ＝ 将来検討。

### リリース計画の概要

| 区分 | 範囲 |
| :-- | :-- |
| **P0（MVP）** | 認証・ユーザー管理、マスタ、入荷・在庫一覧・受払履歴、出庫引当（自動引当・荷崩し）・出庫確定・引当解除、在庫 API（①〜⑦）、棚卸調整（入荷訂正を含む）、発送の伝票手入力登録・引当・再引当・数量変更・取消・梱包完了、出荷日別の作業画面 |
| **P1** | CSV 一括取込と一括再引当、トータルピックと PDF 帳票、一括梱包完了、倉庫間移動、出庫取消、緊急操作 |
| **P2** | 期限アラート通知、ピッキング実績の消し込み、引当の自動振り替え、在庫側との定期突合、移動対象ロットの自動選択、ログイン試行制限・メール再設定 |

> P0 に棚卸調整を含めるのは、入荷の誤入力の訂正手段が棚卸調整（`admin`）に集約されている（在庫側 §4.7）ため。出庫取消を P1 とするため、P0 の期間に梱包完了を誤った場合は、在庫側の棚卸調整と発送側の運用（紙での記録）で対応する（未決事項 #3）。

### 共通: 認証・ユーザー管理（在庫・発送それぞれに実装）

#### F-A1 ログインとロール（P0）

**ユーザーストーリー**:
業務担当者として、自分の権限に応じた操作だけを安全に行うために、メールとパスワードでログインし、ロールで操作を制限してほしい。

**受け入れ条件**:
- [ ] メール＋パスワードでログインできる。自己登録・マジックリンク・メール確認は無い
- [ ] ログイン失敗時のエラーは「メールアドレスまたはパスワードが正しくありません。」の 1 種類のみで、メールの存在有無が分からない
- [ ] パスワードは 12 文字以上。ハッシュ化して保存し、平文をログや画面に出さない
- [ ] 未ログインの画面アクセスはログイン画面へ遷移し、ログイン後は元のページへ戻る
- [ ] `viewer` は参照のみ、`staff` は業務操作、`admin` は全操作が可能（権限表と 1 対 1 に実装）。ボタンの非表示だけでなく、サーバー側のイベント処理でも検査する
- [ ] パスワード変更・ロール変更・アーカイブをしたユーザーの全セッションが即時に失効する

#### F-A2 ユーザー管理（P0）

**ユーザーストーリー**:
管理者として、担当者のアカウントを管理するために、ユーザーの登録・ロール変更・パスワード再設定・無効化をしたい。

**受け入れ条件**:
- [ ] `admin` のみが作成・ロール変更・パスワード再設定・アーカイブを実行できる
- [ ] 管理者が設定した初期（再設定）パスワードでのログイン直後は、パスワード変更画面へ強制遷移する
- [ ] 有効な `admin` が常に 1 人以上残る（最後の `admin` と自分自身のロール変更・アーカイブは拒否される）
- [ ] アーカイブ済みユーザーはログインできない

### 在庫管理システム（`food_vault`）

#### F-V1 マスタ管理（P0）

**ユーザーストーリー**:
管理者として、在庫の前提となる情報を整えるために、メーカー・倉庫・商品を登録・編集・アーカイブしたい。

**受け入れ条件**:
- [ ] メーカー・倉庫・商品を作成・編集できる（商品はケース入数と期限区分 `consumption` / `best_before` / `none` を持つ）。編集は `admin` のみ、参照は全ロール
- [ ] ロット（在庫 0 を含む）がある商品は、ケース入数と期限区分を変更できない。入荷と同時にマスタ更新が走っても、この規則が破られない
- [ ] アーカイブは、在庫 0・引当なしの商品／倉庫、有効な商品を持たないメーカーに限り可能。アーカイブ済みは入荷・引当・移動の対象にできない
- [ ] 商品コード・メーカーコード・倉庫コードは一意

**優先度**: P0(必須)

#### F-V2 入荷登録と在庫一覧（P0）

**ユーザーストーリー**:
倉庫担当者として、期限付きの在庫を正確に持つために、入荷を登録し、現在の在庫をロット単位で確認したい。

**受け入れ条件**:
- [ ] 倉庫・商品・期限日・入荷日・ケース数・バラ数を入力して入荷登録できる（`staff` 以上）。入力と同時に総バラ数が表示される
- [ ] 期限区分が `none` 以外の商品は期限日が必須。`none` は期限日を `9999-12-31` で保存し、画面では「期限なし」と表示する
- [ ] 同じ「倉庫 × 商品 × 期限日 × 入荷日」のロットがあれば加算、なければ新規作成される（同時入荷でも加算が失われない）
- [ ] 在庫一覧で、倉庫・商品・期限で絞り込み、ロット別・商品別に「ケース数｜バラ数｜総バラ数」「引当済」「有効在庫」を期限の近い順に表示できる。在庫 0 のロットは既定で非表示
- [ ] 入荷は受払履歴（`receive`）に操作者付きで記録される

**優先度**: P0(必須)

#### F-V3 出庫引当・出庫確定・引当解除（P0）

**ユーザーストーリー**:
出荷事務担当者（発送システム）として、期限の近いロットから漏れなく・二重に引き当てずに出庫するために、自動引当と、確定・解除を在庫システムに任せたい。

**受け入れ条件**:
- [ ] 引当は、期限日昇順 → 入荷日昇順 → ロット ID 昇順で行い、期限切れ・最低許容期限日未満のロットは引き当てない
- [ ] バラが足りないとき、同一ロット内のケースを自動で荷崩しして引き当てる。荷崩しは受払履歴（`auto_break`）に 1 ロット 1 行で記録され、引当解除・出庫取消でも元に戻らない
- [ ] 在庫不足の場合、全体がロールバックされオーダーは作られず、不足した全明細分の不足数が返る
- [ ] 同じ商品に対する同時の引当が重なっても、引当済み数が現在庫を超えない（DB の CHECK 制約でも担保）。複数明細・倉庫間移動が同時に走ってもデッドロックしない
- [ ] 出庫確定で現在庫と引当済数を減算し、受払履歴（`ship`）とオーダー履歴（`shipped`）を残す。引当解除でロックだけを外し、引当明細は残す
- [ ] 画面登録のオーダーは `staff` 以上が確定・解除できる。発送システム起源のオーダーの画面での確定・解除は P1 の緊急操作（F-V8）に限る

**優先度**: P0(必須)

#### F-V4 在庫 API（発送システム向け）（P0）

**ユーザーストーリー**:
発送システムとして、在庫ロジックを二重実装せずに引当・確定・解除・照会を行うために、安全で冪等な API を使いたい。

**受け入れ条件**:
- [ ] ①引当 ②出庫確定 ③引当解除 ④出庫取消 ⑤照会（`:id` と `?external_slip_id=`）⑥倉庫一覧 ⑦商品検索を `/api/v1` で提供する
- [ ] サービストークン（Bearer。複数登録可）で認証し、不正なトークンは 401。比較は定数時間で行う
- [ ] 状態を変える API は `operator` を必須とし、受払履歴・オーダー履歴に残す
- [ ] 同じ `external_slip_id` の再送は、内容が一致すれば既存オーダーを 200 で返し、内容が違えば 409 `idempotency_conflict`。確定・解除・出庫取消は現状態なら 200
- [ ] 全エラーが共通形式 `{ "error", "message", ... }` で返り、不正な ID は 404／422 になる（500 にならない）
- [ ] 通信断で引当応答を受け取れなくても、`external_slip_id` の照会で復旧できる

**優先度**: P0(必須)（④出庫取消の API は F-V7 と同時に P1）

#### F-V5 棚卸調整・入荷訂正・荷まとめ（P0）

**ユーザーストーリー**:
在庫管理者として、実在庫とシステム在庫のずれや入力ミスを直すために、ロットを指定して数量を調整したい。

**受け入れ条件**:
- [ ] `admin` のみが、ロット指定でケース数・バラ数を増減できる。理由は必須で、受払履歴（`adjust`）に記録される
- [ ] 有効在庫（現在庫 − 引当済）を下回る減算はできない
- [ ] 入荷の訂正（数量の誤り、期限日・入荷日の誤り）と、荷まとめ（バラ → ケース）を、1 回の調整として登録できる
- [ ] ロット詳細に、そのロットを引き当てているオーダーが表示される

**優先度**: P0(必須)

#### F-V6 受払履歴（P0）

**ユーザーストーリー**:
在庫管理者として、在庫の増減の経緯を追跡するために、受払履歴をロット・商品・期間・処理区分・操作者で検索したい。

**受け入れ条件**:
- [ ] 現在庫が変わる全操作（入荷・出庫確定・出庫取消・荷崩し・移動・調整）が追記専用で記録され、更新・削除できない
- [ ] 操作者（画面ユーザー、または API の `operator`）が必ず残る
- [ ] 移動のペア（`transfer_id`）と出庫オーダーへのリンクがある

**優先度**: P0(必須)

#### F-V7 出庫取消（P1）

**ユーザーストーリー**:
管理者として、誤って出庫確定した伝票を戻すために、出庫取消をしたい。

**受け入れ条件**:
- [ ] `admin` のみ実行できる。理由が必須で、API 経由では `operator` と `reason` も必須
- [ ] 引当分の在庫が元のロットに戻り（引当ロックは戻らない）、受払履歴（`ship_reverse`）とオーダー履歴（`reversed`）が残る
- [ ] 対象の商品・倉庫がアーカイブ済みの場合は 409 になる

**優先度**: P1(重要)

#### F-V8 緊急操作（発送システム起源オーダーの画面操作）（P1）

**ユーザーストーリー**:
管理者として、紛失・破損で在庫を調整する必要があるときのために、発送システム起源のオーダーを在庫側画面から確定・解除したい。

**受け入れ条件**:
- [ ] 発送システム起源（`external_slip_id` あり）のオーダーの確定・引当解除は `admin` のみ。理由が必須で、「発送システムと状態がずれます」の警告が表示される
- [ ] 実行者・理由がオーダー履歴に残る

**優先度**: P1(重要)

#### F-V9 倉庫間移動（P1）

**ユーザーストーリー**:
倉庫担当者として、倉庫間の在庫を動かすために、ロットを指定して別倉庫へ即時に移動したい。

**受け入れ条件**:
- [ ] 移動元ロットを指定し、移動先倉庫・ケース数・バラ数を入力して移動できる（`staff` 以上）。移動元と移動先が同じ倉庫は拒否される
- [ ] 期限日・入荷日を引き継いで移動先ロットに加算される。バラ不足時は同一ロット内で自動荷崩しされる
- [ ] 移動出庫と移動入庫が同じ `transfer_id` で必ず対になって記録される。有効在庫を超える移動はできない

**優先度**: P1(重要)

### 発送システム（`food_ship`）

#### F-S1 マスタ管理（P0）

**ユーザーストーリー**:
管理者として、伝票の自動計算の元になる情報を整えるために、発注元・発送商品（梱包換算）・出荷期限ルールを管理したい。

**受け入れ条件**:
- [ ] 発注元を登録・編集・アーカイブできる（アーカイブ済みは新規伝票の選択肢に出ない）
- [ ] 発送商品は、商品コードを入力すると在庫側 API から商品 ID・商品名・メーカー ID・メーカー名を取得して初期入力される。1 件あたり標準箱数・商品数量（バラ数）を持つ。在庫側の商品と 1 対 1
- [ ] マスタ画面から在庫側の値を再取得できる（自動同期はしない）
- [ ] 出荷期限ルール（発注元 × 商品、最低残日数）を CRUD できる。未登録は期限制限なし。編集は `admin` のみ

**優先度**: P0(必須)

#### F-S2 伝票登録・引当・再引当（P0）

**ユーザーストーリー**:
出荷事務担当者として、入力した時点で在庫の引当と欠品の検知を済ませるために、伝票を登録して自動引当したい。

**受け入れ条件**:
- [ ] 発注元・出荷予定日・商品・件数（任意で発注元伝票番号）を入力すると、箱数・出庫総数量（バラ）・最低許容期限日が自動計算され、リアルタイムで画面に表示される。箱数は手修正でき、バラ数は手修正できない
- [ ] 伝票は先に `pending` で保存（コミット）してから在庫側の引当 API を呼び、結果で `allocated` / `shortage` に更新される。通信失敗でも入力内容が消えない
- [ ] 在庫側の応答の引当合計が `total_piece_qty` と一致しなければ `allocated` にならない
- [ ] `pending` の行に、引当エラーの種別（一時／恒久）と最終試行日時が表示される
- [ ] `shortage` / `pending` の伝票は「再引当」で復旧できる。再引当は、既存の在庫側オーダーを照会・解除してから引当し、最低許容期限日を現在のルールで再計算する
- [ ] 同じ発注元伝票番号の同じ商品の二重登録は、取消・出庫取消済みを除いて拒否される

**優先度**: P0(必須)

#### F-S3 出荷日別の作業画面・数量変更・取消（P0）

**ユーザーストーリー**:
出荷事務担当者として、順不同の伝票を出荷予定日で捌くために、日付タブごとに伝票を確認し、変更・取消をしたい。

**受け入れ条件**:
- [ ] 出荷予定日ごとにタブ分けして表示し、タブに残件数（`pending` / `allocated` / `shortage` の合計）を表示する。状態でフィルタできる（未梱包のみ／在庫不足のみ／すべて）
- [ ] 各伝票に、引当ロットの「期限日 × 個数」が表示される
- [ ] `allocated` / `shortage` / `pending` の伝票の件数・出荷予定日を変更できる（旧引当の解除 → 再引当）。在庫不足で旧引当が解除されたままになる旨を確認ダイアログに表示する
- [ ] 梱包前の伝票を取消できる。取消の実行者・日時が記録される
- [ ] `viewer` は参照のみ

**優先度**: P0(必須)

#### F-S4 梱包完了（P0）

**ユーザーストーリー**:
出荷事務担当者として、実際の梱包と在庫を一致させるために、梱包完了を消し込んで在庫を減算したい。

**受け入れ条件**:
- [ ] 梱包完了で在庫側の出庫確定 API を呼び、成功したら `packed`・梱包完了者・日時を保存する。分割梱包は扱わない
- [ ] 梱包時に実際の箱数が変わった場合、箱数を修正できる（在庫数には影響しない）
- [ ] 在庫側が停止している間は梱包完了は失敗して `allocated` のまま残り、復旧後にやり直すと整合する
- [ ] 409 が返った場合は在庫側へ照会し、在庫側が `shipped` なら発送側も `packed` に更新する

**優先度**: P0(必須)（一括梱包完了は F-S8、P1）

#### F-S5 CSV 一括取込と一括再引当（P1）

**ユーザーストーリー**:
出荷事務担当者として、大量の伝票を短時間で登録するために、CSV を取り込み、まとめて引き当て・再引当したい。

**受け入れ条件**:
- [ ] CSV（1 行 = 1 伝票。列は `client_code, client_slip_no, scheduled_ship_date, item_code, order_count`）を取り込める。`client_slip_no` は必須
- [ ] 検証エラーが 1 行でもあれば、ファイル全体を取り込まず、行番号つきのエラー一覧を表示する。在庫不足は検証エラーではなく `shortage` で保存し、取込結果に引当の成否を一覧表示する
- [ ] 全行を `pending` で保存してから、出荷予定日の早い順 → ファイル順に引当する
- [ ] アプリが途中で停止しても、`pending` の行が一括再引当（出荷予定日昇順 → 伝票番号昇順）で復旧できる。一括再引当は伝票ごとの成否を一覧表示する

**優先度**: P1(重要)

#### F-S6 トータルピックと PDF 帳票（P1）

**ユーザーストーリー**:
出荷事務担当者として、現場がまとめてピッキングできるように、トータルピック表と作業指示書を PDF で出力したい。

**受け入れ条件**:
- [ ] 「出荷予定日 × 発注元 × メーカー」ごとに、未ピックの `allocated` 伝票を束ねてトータルピックを作成できる。同時に作成しても、同じ伝票が二重にピックされない
- [ ] トータルピック表（商品 × 期限日の合算と仕分け表）と、伝票ごとの作業指示書を、1 つの PDF（ピック表 → 作業指示書の順）または個別にダウンロードできる。日本語が正しく表示され、A4 縦に収まる
- [ ] 追加伝票は追加ピックとして作成され、既存のピックは変わらない
- [ ] 紐づく伝票を数量変更・出荷予定日変更・取消・出庫取消すると、その伝票はピックから外れ、ピックは「要再発行」になる。要再発行のピックは、再発行（版の加算）するまで PDF を出力できない
- [ ] 帳票は都度生成し、保存しない。日時は JST で表示する
- [ ] 操作は `staff` 以上

**優先度**: P1(重要)

#### F-S7 梱包完了後の取消（出庫取消）（P1）

**ユーザーストーリー**:
管理者として、誤って梱包完了にした伝票を戻すために、理由を付けて出庫取消したい。

**受け入れ条件**:
- [ ] `admin` のみ実行できる。理由が必須で、在庫側の出庫取消 API に `operator` と `reason` を渡す
- [ ] 成功したら `reversed` になり、実行者・日時・理由が伝票に残る。在庫は元のロットに戻り、引当ロックは再設定されない
- [ ] 「複製して再登録」で、同じ発注元伝票番号の新しい伝票を作れる

**優先度**: P1(重要)

#### F-S8 一括梱包完了（P1）

**ユーザーストーリー**:
出荷事務担当者として、多数の伝票を一度に消し込むために、梱包完了を一括で実行したい。

**受け入れ条件**:
- [ ] 選択した伝票を 1 件ずつ順に処理し、進捗（完了件数／全件）と伝票ごとの成否を表示する。失敗した伝票は `allocated` のまま残る
- [ ] 実行中は一括完了ボタンと対象行が無効化され、二重実行できない

**優先度**: P1(重要)

### 将来的な機能(Post-MVP)

#### 期限アラート通知

商品ごとのアラート日数に基づき、期限が近いロットを通知する。機能の設計時に必要なカラムを追加する。

**優先度**: P2(できれば)

#### ピッキング実績の消し込み

引当明細にピッキング済みを記録する、または画面で「ピック完了」「検品スキャン」を登録する。

**優先度**: P2(できれば)

#### 引当の自動振り替え

出荷予定日が近い伝票が `shortage` のとき、遠い日付の伝票の引当を自動で振り替える。

**優先度**: P2(できれば)

#### 在庫側との定期突合

発送側 `allocated` と在庫側オーダーの状態の不一致を定期的に検出する（照会 API は用意済み）。

**優先度**: P2(できれば)

#### その他

移動対象ロットの自動選択、ログイン試行制限・アカウントロック、メールによるパスワード再設定、ユーザーの共通化（シングルサインオン）。

**優先度**: P2(できれば)

## 非機能要件

> 数値は **設計目標（案）**。ピーク時 1,000 件/日の規模をもとにしており、実装後に実測して見直す（未決事項 #4）。

### パフォーマンス

- 在庫側の引当 API（1 伝票 = 1 明細）の応答時間: 通常時 95 パーセンタイルで 1 秒以内
- 画面登録 1 件の「保存 → 引当結果表示」: 3 秒以内（通信リトライを除く）
- 出荷日別の作業画面: 1 日分 1,000 伝票の一覧表示を 2 秒以内
- CSV 1,000 行の取込（検証・保存）: 30 秒以内。続く全行の引当完了: 15 分以内
- トータルピック PDF（50 伝票を束ねた場合）: 30 秒以内に生成

### ユーザビリティ

- 出荷事務担当者が、マニュアル無しで、手入力の伝票登録から梱包完了までを 1 日の運用で習得できる（受け入れ試験で、初見の担当者が手順書なしで 1 伝票を登録〜梱包完了できること）
- 入力画面は、ケース数・バラ数・箱数・最低許容期限日などの自動計算結果をリアルタイムで表示する
- エラー表示は、一時エラー（再試行で直る）と恒久エラー（設定・マスタの修正が必要）を区別し、次に取る操作を示す
- 帳票・画面の用語は [glossary.md](glossary.md) に統一する

### 信頼性

- 在庫の更新（引当・荷崩し・確定・解除・出庫取消・移動・調整）は単一トランザクションで行い、途中で失敗したら全体がロールバックされる
- データ不整合の防止: ロットの数量・引当済数は DB の CHECK 制約（0 以上、引当済 ≤ 現在庫）で常に守られる。二重引当・二重確定は発生しない
- 在庫側 API の一時的な失敗（接続エラー・5xx）は、最大 3 回の自動リトライ（待機 1・2・4 秒）で吸収し、それでも失敗した伝票は入力内容を失わず `pending` で残る
- すべての在庫側 API 呼び出しは冪等であり、再送しても二重処理にならない
- 受払履歴・オーダー履歴は追記のみで、更新・削除できない

### セキュリティ

- 認証: メール＋パスワード（12 文字以上）。ユーザーは管理者のみが作成し、ログイン失敗時のメッセージは存在有無を漏らさない
- 認可: HTTP plug・LiveView `on_mount`・イベント単位の 3 層で、ロールごとの権限を検査する（画面の非表示だけに頼らない）
- 在庫 API: 複数登録可能なサービストークン（Bearer）で認証し、定数時間で比較する。トークンの値はログに出さず、無停止でローテーションできる。本番は TLS を終端し、`/api` を発送システムの送信元に限定する
- 監査: 在庫の増減と出庫オーダーの状態遷移の「誰が・いつ・なぜ」を DB に残す（API 操作は `operator` を必須とする）
- 秘密情報（トークン・DB パスワード・初期管理者パスワード）はコンパイル時 config に置かず `runtime.exs`（環境変数）から読み、未設定なら起動時に落とす
- PDF 帳票: テンプレートに外部リソースを読み込まず、差し込む値は HEEx でエスケープする。本番ではサンドボックスを無効化しない

### スケーラビリティ

- 1 日 300〜1,000 件の出荷伝票、同時に操作する担当者は数名程度を想定する（人数はヒアリングで確認、未決事項 #4）
- 対象倉庫は発送システムでは 1 倉庫に固定。在庫システムは複数倉庫に対応する
- 在庫 0 のロットは削除しないため、長期運用での肥大化対策（アーカイブなど）を運用開始後に検討する
- 同時引当は、全操作共通のロック順序（倉庫・商品・期限日・入荷日・ID の昇順）によりデッドロックを避ける

## スコープ外

明示的にスコープ外とする項目:

- 分割梱包・部分出荷（1 伝票は全数まとめて梱包完了する）
- 帳票へのバーコード／QR の印字（`slip_no` / `pick_no` の数字表示のみ）
- 画面でのピッキング完了登録・検品スキャン（帳票の手書き記入欄のみ。将来機能として P2 に記載）
- 発送システムでの倉庫選択（特定の 1 倉庫に固定し、倉庫 ID は設定値）
- 在庫側 API の定期突合の自動実行（照会 API は用意するが、突合バッチは P2）
- 発注元・商品・メーカーの在庫側マスタとの自動同期（登録時のコピーと手動再取得のみ）
- バラの自動まとめ（荷まとめは棚卸調整による手動運用）
- 倉庫間移動での「移動中」状態、および移動対象ロットの自動選択
- 在庫システムと発送システムのユーザー共通化（別管理）
- メール送信基盤（パスワード再設定は管理者が行う）
- 既存の帳票テンプレートの再現（既存テンプレートは無く、新規にレイアウトを設計する）

## 前提と制約

- 技術スタック: Elixir 1.20.5 / Erlang 29 / Phoenix 1.8.16 / LiveView / Tailwind CSS / PostgreSQL 15 / Docker Compose。コーディング規約は [coding-rules.md](coding-rules.md)
- 2 アプリは別プロジェクト・別 DB・別コンテナ。連携は、発送 → 在庫の一方向 HTTP（JSON API）のみ。DB 共有・Erlang クラスタは使わない
- PDF 帳票の実行環境（Chromium・日本語フォント・ライブラリ）は別セッションで構築する。設計上の前提（外部リソース禁止、サンドボックス、負荷上限、表示確認）は発送側設計書 §8.2 に定めた
- ULID 依存は `ecto_ulid_next` を採用した（[architecture.md §4](architecture.md#4-ulid-基盤)）
