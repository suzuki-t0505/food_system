# ユビキタス言語定義（用語集）

食品在庫管理システム（`food_vault`）と発送システム（`food_ship`）で使う用語を定義する。**画面の日本語・帳票・コードの識別子を、この表で 1 対 1 に対応させる**（coding-rules §16.4）。同じ意味の語を揺らさない。

- 出典: [食品在庫管理システム設計.md](ideas/食品在庫管理システム設計.md)（v2.2）、[発送システム 基本設計書.md](ideas/発送システム%20基本設計書.md)（v2.2）。定義が食い違ったときは、**在庫に関する語は在庫側設計書、伝票・梱包・ピックに関する語は発送側設計書**を正とし、本書を更新する。
- 表記: 「コード」列は `snake_case` の識別子（テーブル名・カラム名・Enum 値）。「所属」は `在庫`（food_vault）／`発送`（food_ship）／`共通`。

---

## 1. システムと基本概念

| 用語 | コード | 所属 | 定義 |
| :-- | :-- | :-- | :-- |
| 在庫管理システム | `food_vault` | 共通 | 在庫・入荷・出庫・移動・棚卸を管理するアプリ。API の提供側。開発時ポート 4000、DB `food_vault_dev` |
| 発送システム | `food_ship` | 共通 | 出荷伝票・梱包・トータルピック・作業指示書を管理するアプリ。在庫管理システムの API の呼び出し側。開発時ポート 4001、DB `food_ship_dev` |
| 発注元 | `client` / `clients` | 発送 | 出荷伝票を送ってくる EC・百貨店など。`client_code`（CSV 取込時の識別コード）で特定する |
| メーカー | `maker` / `makers` | 在庫 | 商品の製造元。発送側にはマスタを持たず、在庫側の `makers.id` を `inventory_maker_id` として保持する |
| 倉庫 | `warehouse` / `warehouses` | 在庫 | 在庫を保管する拠点。発送システムは特定の 1 倉庫に固定し、倉庫 ID を設定値（`runtime.exs`）で持つ |
| 商品 | `item` / `items` | 在庫 | 在庫管理の対象。`item_code`（JAN コードや自社品番）で一意 |
| 発送商品 | `shipping_item` / `shipping_items` | 発送 | 在庫側の商品と **1 対 1** で紐づく、発送独自の「件数 → 箱数・バラ数」換算のマスタ（`inventory_item_id` で紐づけ） |
| アーカイブ | `archived_at` | 共通 | マスタ・ユーザーの論理削除。`archived_at` が NULL なら有効。物理削除はしない。アーカイブ済みは入荷・引当などの対象にできない |
| ユーザー | `user` / `users` | 共通 | 画面にログインする担当者。管理者が登録する（自己登録なし）。在庫と発送で別管理 |
| ロール | `role` | 共通 | `admin`（管理者）・`staff`（担当者）・`viewer`（閲覧者）。上位は下位の操作を含む。判定は `Permission.can?/2` に一本化 |
| 初期（再設定）パスワード | `must_change_password` | 共通 | 管理者が設定したパスワード。このパスワードでのログイン直後は、パスワード変更画面へ強制遷移する |
| 現在のスコープ | `current_scope` | 共通 | ログイン中のユーザーを持つ構造体（`current_scope.user`）。plug と `on_mount` の 2 箇所でのみ assign する |

## 2. 荷姿・数量

| 用語 | コード | 所属 | 定義 |
| :-- | :-- | :-- | :-- |
| ケース | `case` / `*_cases` / `*_case_qty` | 在庫 | 箱単位の荷姿。在庫はケース数とバラ数を **分けて独立に** 管理する |
| バラ | `piece` / `*_pieces` / `*_piece_qty` | 在庫 | 1 個単位の荷姿 |
| ケース入数 | `units_per_case` | 在庫 | 1 ケースに入るバラ数。商品マスタの固定値。ロット（在庫 0 を含む）が存在したら変更できない |
| 総バラ数 | — | 在庫 | ケース数 × 入数 ＋ バラ数。画面・帳票では常にケース数・バラ数と併記する。計算は `FoodVault.Utils.Calc` に集約する |
| 件数 | `order_count` | 発送 | 伝票に記載された注文の数 |
| 標準箱数（1 件あたり） | `boxes_per_order` | 発送 | 1 件が何箱になるか（基本 1、商品により 3 など） |
| 商品数量（1 件あたり） | `pieces_per_order` | 発送 | 1 件が何バラか。**在庫を減らす基準値** |
| 箱数 | `box_count` | 発送 | 伝票の梱包箱数。初期値は件数 × 標準箱数。画面で手修正できる（在庫数には影響しない） |
| 出庫総数量（バラ） | `total_piece_qty` | 発送 | 件数 × 商品数量。在庫側へ要求するバラ数（`req_pieces`）。手修正不可 |

## 3. 在庫・ロット・期限

| 用語 | コード | 所属 | 定義 |
| :-- | :-- | :-- | :-- |
| ロット | `inventory_lot` / `inventory_lots` | 在庫 | 在庫の管理単位。**倉庫 × 商品 × 期限日 × 入荷日** で一意。在庫 0 になっても行は削除しない |
| 期限日 | `expiration_date` | 在庫 | 消費期限または賞味期限の日付（業務日付。タイムゾーン変換しない） |
| 期限区分 | `expiration_type` | 在庫 | `consumption`（消費期限）／`best_before`（賞味期限）／`none`（管理なし）。ロットが存在したら変更できない |
| 期限なし | — | 在庫 | 期限区分 `none` のロットの期限日。`9999-12-31` で保存し、画面では「期限なし」と表示する |
| 入荷日 | `received_date` | 在庫 | ロットを入荷した日。倉庫間移動でも元の入荷日を引き継ぐ |
| 現在庫 | `case_qty` / `piece_qty` | 在庫 | ロットの現在の数量（引当済みを含む） |
| 引当済 | `allocated_case_qty` / `allocated_piece_qty` | 在庫 | 出庫待ちとしてロックされている数量。現在庫以下 |
| 有効在庫 | — | 在庫 | 引当可能な数量。現在庫 − 引当済。有効ケース数・有効バラ数・有効総バラ数がある |
| 先出し | — | 在庫 | 期限日昇順 → 入荷日昇順 → ロット ID 昇順で引き当てる基準（FEFO ＋ FIFO のハイブリッド）。ロット ID は順序を一意にするタイブレークで、作成順の意味は持たない |
| 最低許容期限日 | `min_expiration_date` | 共通 | この日以降が期限のロットだけを引当対象にする下限。在庫側は引当リクエストの項目、発送側は伝票のカラムで、**同名** |
| 出荷期限ルール | `expiration_rule` / `min_remaining_days` | 発送 | 「発注元 × 商品」ごとの最低残日数。**最低許容期限日 ＝ 出荷予定日 ＋ 最低残日数**。未登録は制限なし |
| 出庫可能期限 | — | 在庫 | 出庫引当の対象となる期限日の下限。`GREATEST(出庫予定日, 最低許容期限日)`。期限切れ在庫は引き当てない |

## 4. 在庫の操作

| 用語 | コード | 所属 | 定義 |
| :-- | :-- | :-- | :-- |
| 入荷 | `receive` | 在庫 | ロットの数量を加算する。同じロットがあれば加算、なければ新規作成。`staff` 以上 |
| 出庫 | — | 在庫 | 倉庫から在庫を出す操作全般（引当 → 確定）。**在庫側の用語**。発送側の「出荷」「梱包」と区別する（§8） |
| 引当 | `allocate` | 在庫 | 出庫に先立ち、先出し順にロットの数量をロックすること。在庫は減らない。「仮押さえ」と同義だが、**文言は「引当」に統一** |
| 引当解除 | `cancel` | 在庫 | `allocated` のオーダーのロックを外して `cancelled` にする。現在庫は変わらない |
| 出庫確定 | `ship` | 在庫 | 引当分を現在庫から減算して `shipped` にする。発送側の「梱包完了」で呼ばれる |
| 出庫取消 | `reverse` / `ship_reverse` | 在庫 | `shipped` のオーダーを `reversed` にして在庫を元のロットに戻す。**管理者のみ・理由必須**。引当ロックは戻さない |
| 荷崩し（自動荷崩し） | `auto_break` | 在庫 | バラ不足時に、同一ロットのケースを開封してバラにする自動処理。1 ロット・1 オーダー（または 1 移動）につき履歴 1 行。**引当解除・出庫取消でも元に戻さない** |
| 荷まとめ | `adjust` | 在庫 | 累積したバラをケースに戻す運用。自動では行わず、棚卸調整（`admin`）で 1 回の増減として登録する |
| 倉庫間移動 | `transfer_out` / `transfer_in` | 在庫 | ロット ID を指定して別倉庫へ即時移動する（「移動中」状態なし）。期限日・入荷日を引き継ぐ。出庫と入庫を `transfer_id` で対にする |
| 棚卸調整 | `adjust` | 在庫 | ロット指定の増減登録。廃棄・入荷の訂正・荷まとめもこれで行う。`admin` のみ・理由必須 |
| 受払履歴 | `inventory_transaction` / `inventory_transactions` | 在庫 | **現在庫が変動する操作**の追記専用ログ。処理区分は `receive` / `ship` / `ship_reverse` / `auto_break` / `transfer_out` / `transfer_in` / `adjust`。引当・引当解除は記録しない |
| 移動 ID | `transfer_id` | 在庫 | 移動出庫と移動入庫を結ぶ ULID。参照先テーブルは持たない |

## 5. 出庫オーダー（在庫側）

| 用語 | コード | 所属 | 定義 |
| :-- | :-- | :-- | :-- |
| 出庫オーダー | `shipment_order` / `shipment_orders` | 在庫 | 出庫指示のヘッダ。1 オーダー ＝ 1 倉庫・1 出庫予定日 |
| 出庫オーダー明細 | `shipment_order_line` | 在庫 | 「何を何個要求したか」。要求ケース数 `req_cases`・要求バラ数 `req_pieces` |
| 引当明細 | `shipment_allocation` | 在庫 | 自動引当の結果（どのロットから何個）。取消後も削除しない |
| オーダー履歴 | `shipment_order_event` / `shipment_order_events` | 在庫 | オーダーの状態遷移（`created` / `shipped` / `cancelled` / `reversed`）の追記専用ログ。誰が・いつ・なぜを残す |
| 連携元伝票 ID | `external_slip_id` | 在庫 | 発送システムの伝票 ID。冪等キー。これを持つオーダーが「**発送システム起源**」で、画面での確定・引当解除は `admin` の緊急操作のみ |
| 緊急操作 | — | 在庫 | 発送システム起源のオーダーを在庫側の画面で確定・引当解除する操作。`admin` のみ・理由必須・警告表示 |
| 操作者 | `operator` | 在庫 | API 操作で発送側が渡す、操作したユーザーの識別子（メール）。受払履歴・オーダー履歴に残る |
| 冪等性 | — | 共通 | 同じ要求を再送しても二重処理にならない性質。引当は `external_slip_id` ＋内容一致のときだけ既存を返し、内容が違えば 409 `idempotency_conflict`。確定・解除・出庫取消は現状態なら 200 |
| サービストークン | `INVENTORY_API_TOKENS` | 共通 | 発送システムが在庫 API を呼ぶ Bearer トークン。画面ログインとは別系統。複数登録でローテーションする |

## 6. 伝票・梱包・トータルピック（発送側）

| 用語 | コード | 所属 | 定義 |
| :-- | :-- | :-- | :-- |
| 出荷伝票（伝票） | `shipping_slip` / `shipping_slips` | 発送 | 発注元から届く出荷依頼。**1 伝票 ＝ 1 発注元 × 1 商品 × 1 出荷予定日 ＝ 在庫側 1 出庫オーダー**。`id` を `external_slip_id` として渡す |
| 伝票番号 | `slip_no` | 発送 | 現場用の通し番号（DB シーケンス採番）。`S-000123` 形式で表示 |
| 発注元伝票番号 | `client_slip_no` | 発送 | 発注元の伝票・注文番号。二重登録防止に使う。手入力は任意、CSV は必須 |
| 出荷予定日 | `scheduled_ship_date` | 発送 | 出荷する予定の日（業務日付）。ソート・集計・タブ分けの基準軸。在庫側の `shipment_date` に対応 |
| 追加伝票 | — | 発送 | 梱包完了後や出荷予定日の途中で届く追加の伝票。同じ日のタブに「未梱包」としてハイライトする |
| 引当ロット明細控え | `slip_allocated_lots` | 発送 | 在庫側が返した「期限日 × 個数」の表示用キャッシュ。在庫の正は在庫側 |
| 在庫出庫オーダー ID | `inventory_order_id` | 発送 | 伝票に対応する在庫側 `shipment_orders.id` |
| 梱包 / 梱包完了 | `packed` / `packed_at` | 発送 | 全数をまとめて梱包し終えること（分割梱包は扱わない）。梱包完了で在庫側の **出庫確定** を呼ぶ |
| 再引当 | — | 発送 | `pending` / `shortage` の伝票に対し、既存オーダーの照会・解除 → 引当 → 引当合計の検証を行う手順。個別と一括がある |
| 一括再引当 | — | 発送 | `pending` / `shortage` の伝票を、全日付にわたり出荷予定日昇順 → `slip_no` 昇順で順に再引当する。再試行で直らない恒久エラー（`unauthorized`・`not_found`・`validation_failed`）の `pending` は対象外。CSV 取込の中断からの復旧にも使う |
| 引当エラー | `allocation_error` | 発送 | 直近の在庫側 API 失敗の理由。`connection` は **一時エラー**（再試行で直る）、`unauthorized` / `not_found` / `validation_failed` / `idempotency_conflict` は **恒久エラー**（設定・マスタ・内容の修正が必要） |
| 不足バラ数 | `shortage_pieces` | 発送 | `shortage` のとき在庫側が返した不足数 |
| 対象倉庫 / デフォルト倉庫 | `is_default`（在庫の `warehouses`） | 在庫・発送 | 発送システムが引当を要求する倉庫。在庫の倉庫画面で `admin` が設定する（0 件または 1 件。手動設定のみ）。発送は引当のたびに API ⑥ の `is_default` で取得する。未設定の間は伝票登録・再引当・数量変更を受け付けない。アーカイブ済みの倉庫は設定不可、デフォルト倉庫はアーカイブ不可 |
| 登録経路 | `input_source` | 発送 | `manual`（手入力）／`csv`（CSV 取込） |
| 複製して再登録 | — | 発送 | 出庫取消した伝票の内容をもとに新しい伝票を作る操作。引当ロックは戻らないため、出荷し直すにはこれを使う |
| トータルピック | `total_pick` / `total_picks` | 発送 | **同じ「出荷予定日 × 発注元 × メーカー」の引当済み伝票を、商品 × 期限日ごとに合算してまとめてピッキングし、伝票ごとに仕分ける作業単位** |
| ピック番号 | `pick_no` | 発送 | トータルピックの通し番号。`TP-000045` 形式で表示 |
| 追加ピック | — | 発送 | ピック作成後に届いた伝票を、同じグループの別のトータルピックとして作成したもの。既存のピックは変更しない |
| 要再発行 | `outdated` | 発送 | 紐づく伝票が外れて内容が変わったピックの状態。**再発行するまで PDF を出力できない** |
| 再発行 | — | 発送 | 要再発行のピックの `revision` を加算して発行し直す操作 |
| 版 | `revision` | 発送 | ピックの再発行回数に応じた番号。帳票に「第 N 版」と表示 |
| トータルピック表 | — | 発送 | ピック 1 件につき 1 通の帳票（PDF）。商品 × 期限日の合算明細と、後半の仕分け表を含む |
| 仕分け表 | — | 発送 | トータルピック表の後半。明細行ごとの「伝票番号 × 数量」の内訳 |
| 作業指示書 | — | 発送 | 伝票 1 件につき 1 枚の帳票（PDF）。引当ロットの期限日 × 個数、実績記入欄を含む |
| 帳票 | — | 発送 | トータルピック表と作業指示書。**都度生成して保存しない**。日時は JST |

## 7. ステータス

### 7.1 出庫オーダー（在庫側 `shipment_orders.status`）

| 値 | 表示 | 意味 |
| :-- | :-- | :-- |
| `allocated` | 引当済 | 引当済み・出庫待ち |
| `shipped` | 出庫完了 | 出庫確定済み。現在庫を減算済み |
| `cancelled` | 取消 | 引当解除済み。引当明細は残る |
| `reversed` | 出庫取消済 | 出庫確定を巻き戻した（管理者操作）。終端 |

### 7.2 出荷伝票（発送側 `shipping_slips.status`）

| 値 | 表示 | 意味 |
| :-- | :-- | :-- |
| `pending` | 引当待ち | 保存済みだが在庫側の引当が未完了（通信失敗・恒久エラー・数量変更の途中など）。理由は引当エラーで区別 |
| `allocated` | 引当済・未梱包 | 在庫側で引当済み |
| `shortage` | 在庫不足 | 期限条件を満たす在庫が足りない |
| `packed` | 梱包完了 | 梱包済み・在庫減算済み（在庫側の `shipped` に対応） |
| `cancelled` | 取消 | 梱包前に取り消した |
| `reversed` | 出庫取消済 | 梱包完了後に取り消した（管理者操作）。終端 |

### 7.3 トータルピック（発送側 `total_picks.status`）

| 値 | 表示 | 意味 |
| :-- | :-- | :-- |
| `issued` | 発行済 | PDF を出力できる |
| `outdated` | 要再発行 | 紐づく伝票が外れた。再発行（版の加算）するまで PDF 出力不可 |
| `cancelled` | 取消 | 取消済み（紐づく伝票が 0 件になった自動取消を含む）。終端 |

### 7.4 在庫側と発送側の対応

| 発送側 伝票 | 在庫側 オーダー |
| :-- | :-- |
| `pending` / `shortage` | （オーダーなし。通信失敗などで未解除のオーダーが残っている場合がある） |
| `allocated` | `allocated` |
| `packed` | `shipped` |
| `cancelled` | `cancelled` |
| `reversed` | `reversed` |

## 8. 用語の使い分け（揺れを防ぐ）

| 区別 | ルール |
| :-- | :-- |
| 出庫 と 出荷・発送・梱包 | **出庫**は在庫側の用語（倉庫から在庫を出す操作）。**出荷**は発注元向けの業務（出荷予定日・出荷伝票）、**梱包**は現場作業、**発送システム**はアプリ名。発送側の画面では「出庫」を使わない（在庫側の API・オーダーを指すときのみ「在庫側の出庫確定」と書く） |
| 取消・解除・出庫取消 | **引当解除**＝在庫側でロックを外す（`cancel`）。**取消**＝伝票・オーダー・ピックを `cancelled` にする。**出庫取消**＝確定済みを巻き戻す（`reverse`、管理者のみ）。この 3 つを入れ替えない |
| 引当 と 仮押さえ・ロック | 画面・文言は「引当」。「ロック」は DB ロック（`FOR UPDATE`）と引当済数の説明にだけ使う |
| 荷崩し と 荷まとめ | **荷崩し**＝ケース → バラ（自動）。**荷まとめ**＝バラ → ケース（手動・棚卸調整）。逆方向を同じ語で呼ばない |
| 最低許容期限日 | 発送・在庫とも `min_expiration_date`。略称（`required_exp_date` / `exp_date`）は使わない |
| 操作者の ID | 画面ユーザーは `user_id` 系（`created_by_user_id` など役割付き）、API は `operator`。役割の無い汎用の `user_id` を伝票・ピックに作らない（受払履歴・オーダー履歴は画面操作の `user_id` ＋ API の `operator`） |

## 9. 認証・権限

| 用語 | コード | 所属 | 定義 |
| :-- | :-- | :-- | :-- |
| 管理者 | `admin` | 共通 | すべての操作が可能。ユーザー管理・マスタ編集・棚卸調整・出庫取消・緊急操作。**有効な `admin` を常に 1 人以上残す**（自分自身のロール変更・アーカイブも不可） |
| 担当者 | `staff` | 共通 | 業務操作（入荷・出庫オーダー・移動、伝票・梱包・ピック・帳票）が可能。管理操作は不可 |
| 閲覧 | `viewer` | 共通 | 参照のみ。ロールの既定値（最小権限） |
| 権限判定 | `Permission.can?/2` | 共通 | `FoodVault.Utils.Permission` / `FoodShip.Utils.Permission`。権限表と 1 対 1 で、ボタン表示とイベント処理の両方で呼ぶ |
| 現在のスコープ | `current_scope` | 共通 | Phoenix 1.8 の認証の assign（`current_scope.user`）。coding-rules の `current_user` はこれと読み替える |
| 要パスワード変更 | `must_change_password` | 共通 | 管理者が初期設定・再設定したパスワードでログインした直後に、変更画面へ強制遷移させるフラグ |

## 10. 技術用語（実装）

| 用語 | 定義 |
| :-- | :-- |
| ULID | 全テーブルの主キー（`id`）と外部キー。Ecto 型 `Ecto.ULID`、DB 列は `binary_id`（`uuid` 型）。同一ミリ秒内の生成順は保証しない |
| Context | ドメイン層の公開 API（`FoodVault.Inventories` など）。Context + スキーマの 2 層で、子エンティティ専用の Context は作らない |
| `Ecto.Multi` / `Repo.transact/1` | 複数テーブルの更新に使う（coding-rules §7）。在庫側の引当・確定・取消は単一トランザクション |
| ロックキー | 在庫のデッドロック防止のため、ロットを `(warehouse_id, item_id, expiration_date, received_date, id)` 昇順で 1 クエリでロックする規則 |
| 引当計画 | `FoodVault.ShipmentOrders.AllocationPlan.plan_line/4` が、ロックしたロットと要求数量から、どのロットから何ケース・何バラ引き当て、何ケース荷崩しするかを DB に触れずに計算した結果。計画を作ってから Multi で適用する |
| 操作者（actor） | 在庫側の書き込み関数の第 1 引数。画面のユーザー（`%User{}`）か、在庫 API の `{:api, operator}`。受払履歴・オーダー履歴の `user_id` / `operator` に残る |
| 追記専用 | `inventory_transactions` と `shipment_order_events` は INSERT のみ。更新・削除の関数を作らず、DB のトリガー（`forbid_update_delete()`）でも拒否する |
| 引当合計の検証 | 発送側が、在庫側の応答の引当バラ数の合計が `total_piece_qty` と一致することを確認する処理。不一致は `allocated` にしない |
