# 批判的分析レポート: `発送システム 基本設計書.md` の全否定

作成日: 2026-11-03
対象文書: `docs/ideas/発送システム 基本設計書.md`（ドラフト v2.1）

> 調査範囲の注記: 在庫側レビュー（`食品在庫管理システム設計-critical-review.md`）と同様、`food_ship/` は `mix phx.new` 直後の雛形で、スキーマ・Context・マイグレーションは存在しない。`docs/` には `coding-rules.md` しか無く、`glossary.md` / `functional-design.md` も無い。根拠は、設計書内部の矛盾、`coding-rules.md`、`docker-compose.yml` / `Dockerfile.dev` / `mix.exs` などの実ファイル、および在庫側設計書との契約の整合に置く。在庫側レビューと共通の指摘（ULID 基盤の未整備、用語集不在、`current_user` と `current_scope` の乖離）は重複を避け、参照のみとする。

---

## 総評

発送フロー（`pending` を先に保存してから在庫側 API を呼ぶ方式、トータルピックの「要再発行」ルール）は筋が良い。ただし **再引当時に古い在庫側オーダーを掴んでしまう手順の穴**、**トータルピックの仕様の内部矛盾**、**梱包後取消・取消の実行者が記録されない点**、**CSV 取込の途中失敗への復旧手段の不足**があり、このままでは実装に進めない。これらは在庫側設計書の修正（冪等性・照会 API・出庫取消の `operator`）と同時に決める必要がある。

---

## 1. 再引当・数量変更の手順が、在庫側の冪等仕様と組み合わさると古いオーダーを掴む

**問題:** 発送側は `external_slip_id = shipping_slips.id` を冪等キーにし（§4.1）、在庫側は「同じ `external_slip_id`（`cancelled` 以外）の再引当は既存オーダーを返す（200）」とする（在庫側設計書 L324）。しかし「再引当」ボタン（`pending` / `shortage` の行、§5.8-①②）と数量変更（§5.5）は、**既存の `inventory_order_id` が残っているときの手順を定義していない**。

**証拠（具体的な流れ）:**
1. 数量変更（§5.5）: 新しい `total_piece_qty` で `pending` に更新 → 引当解除 API を呼ぶ。この呼び出しが通信断・タイムアウトで失敗する。
2. 伝票は `pending` のまま、`inventory_order_id` は旧オーダーの ID を保持（§3.4 L122 は `allocated` / `packed` / `reversed` で必須としているだけで、`pending` 時の値を規定していない）。
3. 利用者が「再引当」を押す。引当 API は `external_slip_id` が同じで、旧オーダーが `allocated` のままなので、**旧数量のオーダーを 200 で返す**。
4. 発送側 §4.2 は 200 / 201 を成功として `allocated` にし、`slip_allocated_lots` を保存する。**伝票の `total_piece_qty` と引当数量が食い違ったまま `allocated`** になる。

発送側には、応答の引当合計が `total_piece_qty` と一致するかを検証する記述も無い。

**批判:** 「再引当」の定義を次の順に固定する。(1) `inventory_order_id` があれば先に在庫側の現状を照会（GET）し、`allocated` なら引当解除 → (2) 引当 API → (3) 応答の引当合計バラ数 = `total_piece_qty` を検証し、不一致は `allocated` にせずエラーにする。在庫側の「内容不一致なら 409」（在庫側レビュー #4）の対応とセットで決める。`status` と `inventory_order_id` の関係は DB の CHECK 制約（例：`allocated`/`packed`/`reversed` なら NOT NULL）にも落とす。

## 2. トータルピックの仕様が内部で矛盾・曖昧

**問題 A: 紐づく伝票の範囲が矛盾している。**
- §3.4 L115: 「`allocated` の伝票だけが紐づく」。
- §5.2: 「梱包完了（`packed`）はピックの状態に影響しない」「ピック表の集計対象は、紐づく伝票すべて（梱包済みを含む）」「ピックの取消は、紐づく伝票がすべて未梱包（`allocated`）のときだけ可能」。

梱包完了後も `total_pick_id` は残る設計であり、§3.4 の記述は誤り。`packed` に変わっても外さないのか、DB 制約・クエリ条件（二重ピック防止の `total_pick_id IS NULL`）がどちらを前提にするかが決まらない。

**問題 B: 「要再発行」のピックを再ダウンロードしたときの版数・内容が不定。**
§5.2 は「要再発行のピックは PDF を再出力して差し替える（版 `revision` が加算される）」と書く一方、「帳票は都度生成し、要再発行のピックは出力時に最新化される」とも書く。画面の操作は「PDF ダウンロード」と「再発行」が別ボタン（§6）。`outdated` のまま「PDF ダウンロード」を押すと、**版数は旧のまま、中身だけ最新**の帳票が出る。現場では紙の「第N版」で最新かを判断するため、旧版と同じ番号で内容が違う紙が混在する。

**問題 C: トータルピックの状態遷移が定義されていない。**
伝票は §3.7 に遷移図があるが、`total_picks`（`issued` / `outdated` / `cancelled`）には無い。「`outdated` からの取消可否」「全伝票が外れて自動 `cancelled` になった後の扱い」「`outdated` を再発行できる条件（紐づく伝票が 1 件以上）」が散文に分散している。

**批判:** (A) `total_pick_id` は伝票の状態にかかわらず、取消・数量変更・出庫取消でのみ外す、と §3.4 を直す。(B) `outdated` のときは PDF ダウンロードを禁止して再発行に誘導するか、ダウンロード時に必ず再発行（`revision` 加算）扱いとする。(C) `total_picks` の遷移図と、操作ごとの可否表を §3.7 に追加する。

## 3. 梱包後取消・取消の「誰が・いつ・なぜ」が発送側に残らない

**問題:** `shipping_slips` には `user_id`（登録者）・`packed_by_user_id`・`packed_at` があるが、**取消（`cancelled`）・出庫取消（`reversed`）の実行者・日時・理由を持つカラムが無い**。

**証拠:**
- §3.4 L110-128 のカラム一覧に、`cancelled_at` / `reversed_at` / `reversed_by_user_id` / `reverse_reason` に相当するものが無い。
- §5.7 は「理由の入力を必須とし、在庫側の出庫取消 API を呼ぶ」「在庫側の受払履歴に `ship_reverse` と理由が残る」と書くが、在庫側の `user_id` は API 操作で NULL（在庫側設計書 L180）。§7 は「誰が操作したかは `shipping_slips.user_id` / `packed_by_user_id` で追跡する」とするが、この 2 カラムは登録者と梱包者であり、**取消・出庫取消の実行者とは一致しない**。

**批判:** どちらのシステムにも出庫取消の実行者が残らない状態になる（在庫側レビュー #3 と同一の穴）。発送側に `cancelled_at` / `cancelled_by_user_id`、`reversed_at` / `reversed_by_user_id` / `reverse_reason` を追加し、出庫取消 API に操作者を渡す。

## 4. `pending` が複数の異なる状況を兼ねており、失敗理由が保存されない

**問題:** `pending` は「保存直後で未引当」「通信失敗」「数量変更の途中」に加えて、§4.2 により **404 `not_found`・422 `validation_failed`・401 `unauthorized` のときも「`pending` のまま」** になる。

**証拠:** §4.2 の表は、エラー内容を「画面に表示」とだけ書く。`shipping_slips` には失敗理由や最終試行日時のカラム（§3.4）が無く、画面を再読込すると原因が消える。設定エラー（401）やマスタ不整合（404 / 422）は何度「再引当」しても直らないが、利用者からは通信失敗と区別できない。

**批判:** `allocation_error`（短い列挙値または文字列）と `last_allocation_attempted_at` を追加し、作業画面の行に表示する。恒久エラー（401 / 404 / 422）は再試行しても直らないことが分かる表示にする。`pending` を細分化（例：`allocation_failed`）するかは、遷移図（§3.7）への影響を含めて決める。

## 5. CSV 取込を `Task` で処理する際、途中停止からの復旧手段が無い

**問題:** §5.1 は、行数が多い場合は `Task` で処理し `handle_info` で進捗を更新する（coding-rules §9.9）とする。しかし (1) アプリの再起動・デプロイ・`Task` の異常終了で取込が途中で止まると、残りの行は `pending` のまま残り、(2) 復旧する「再引当」ボタンは行単位（§5.8-①）で、**一括再引当が無い**。

**証拠:** coding-rules §9.9（`docs/coding-rules.md:1094`）の例は `Task.start`（監視なし）で、プロセス終了時の再開機構を持たない。CSV の引当順序「出荷予定日の早い順 → ファイル順」（§5.1）は取込時のみの仕様で、`pending` / `shortage` の再引当順序（先着か出荷日順か）は未定義。`oban` 等のジョブ基盤は `food_ship/mix.exs` の依存に無い。

**批判:** (1) 一括再引当（対象: `pending` / `shortage`、出荷予定日昇順 → 登録順）を画面とバッチ処理の仕様に追加する。(2) 取込の進捗・中断を DB に残す（取込バッチ ID・件数・未処理件数）か、中断しても `pending` 行から一括再引当で復旧できることを明記する。(3) 在庫逼迫時に出荷日が近い伝票が `shortage` になり、遠い日付の伝票が引当を握ったままになる場合の運用（遠い方を解除して再引当するなど）を §5.8 に追記する。

## 6. 在庫側 API 呼び出しの実装方針に不明確・誤解を招く点

**問題:**
1. §4.2 は「自動リトライ（最大3回、`Req` の retry）」とするが、Req の既定のリトライ（`:safe_transient`）は GET / HEAD 以外のリクエストを再試行しない。**引当・確定・取消は POST なので、`retry: :transient` を明示しないと設計どおりに動かない**。
2. 接続・受信タイムアウトの数値が未決（設定値に含めるとしか書かれていない）。単発の伝票登録（LiveView の `handle_event`）が在庫側 API をブロッキングで呼ぶと、画面が固まる（coding-rules §9.9 は外部 API 呼び出しを `Task` で非同期にすることを求めている）。
3. 一括梱包完了（§5.4-3）は 1 伝票ずつ順に呼ぶため、数十件で数十秒かかる。進捗表示・二重実行防止（ボタン無効化）の仕様が無い。
4. 在庫側が停止中だと梱包完了が一切できない。紙で出荷だけ先に進めた場合の後追い登録（オフライン時の手順）が無い。

**批判:** リトライ方針（対象メソッド・回数・待機）と各タイムアウトを数値で決める。単発操作の API 呼び出しも `Task` + `handle_info`（または専用プロセス）で行う方針を明記する。在庫側ダウン時の梱包運用（一括確定のやり直し手順）を §5.8 に追記する。

---

## 7. 出荷期限ルールの変更が「再引当」に反映されるかが未定義

**問題:** §3.3 L104 は「伝票は引当時点の最低許容期限日を保持するため、ルールを後から変更・削除しても登録済み伝票には影響しない」とする。しかし、`shortage` の伝票を「再引当」するとき、保持している `required_exp_date` を使うのか、最新のルールで再計算するのかが書かれていない。数量・出荷予定日変更（§5.5）は「再計算」と明記されている。

**批判:** `shortage` の再引当は、運用上「在庫が入荷したので再度試す」場合だけでなく「期限ルールを緩めたので再度試す」場合にも使う。再計算するのか、固定のままにするのかを決め（再計算するなら、ルール削除で NULL に戻る場合を含む）、§5.8-① に明記する。あわせて `shortage` 解消時の `shortage_pieces` のクリア（NULL 化）も書く。

---

## 8. CSV 取込の識別キー（`client_slip_no`）が任意のため、重複防止が効かない

**問題:** §3.4 L116 の `client_slip_no` は NULL 可で、CSV の列にも含まれる（§5.1）が、必須かどうかが定義されていない。部分ユニーク制約は `client_slip_no IS NOT NULL` の行にしか効かない（L141）。CSV で空欄の行があると、**同じファイルを二度取り込んでも重複登録・二重引当**になる。

**批判:** CSV では `client_slip_no` を必須にするか、必須でない場合の重複防止策（取込ファイルのハッシュ・取込バッチ単位の再取込防止）を定める。また出庫取消（`reversed`）後の「複製して再登録」で同じ `client_slip_no` を使うと、部分ユニーク（`status <> 'cancelled'`）に引っかかる（未決 #6 で「引き継がない」としているが、`reversed` を部分ユニークの除外対象に含めるかも併せて決める）。

---

## 9. PDF 生成の実行環境が既存の Docker 設定と整合しておらず、セキュリティ前提も無い

**問題:** §8.2 は `ChromicPDF`（ヘッドレス Chromium）を推奨し、環境構築は別セッション（§9 #9）とする。しかし現状の構成だけでも次の不整合・未検討がある。

**証拠:**
- `Dockerfile.dev` の `apt-get install` に Chromium・`fonts-noto-cjk` が無い。
- `docker-compose.yml` は両サービスとも `target: build_as_root`。root で Chromium を起動する場合は `--no-sandbox` が必要になり、ChromicPDF の `no_sandbox: true` が前提になる。サンドボックスを無効化した Chromium に、在庫側 API 由来の文字列（商品名・メーカー名）や CSV 由来の文字列（発注元名）を含む HTML を描画させることになる。
- 本番用の `Dockerfile` / リリース手順は現状リポジトリに無く、本番環境での Chromium の入れ方・メモリ・同時実行数（ChromicPDF のプール数）が決まらない。数十伝票を束ねる PDF（§5.2）は、描画のたびに重い処理になる。

**批判:** 環境構築を別セッションに切り出す場合でも、(1) HTML テンプレートに差し込む値は HEEx のエスケープに限定し、外部リソース（画像・フォント・スクリプト）を一切読み込まない、(2) `no_sandbox` の可否と、root で動かさない本番構成、(3) 同時生成数の上限とタイムアウト、を設計書の前提として書く。`Utils.Pdf` のモックはテストのみで、実際の日本語表示・改ページの確認手順（現場確認の前に最低限必要）も未決事項に追加する。

## 10. DB 設計: 制約・索引・命名の漏れ

**問題:**
1. `shipping_slips` の索引は `(scheduled_ship_date, status)` と `(total_pick_id)` のみ。coding-rules §14.4（`docs/coding-rules.md:1667-1690`）は FK ごとの `create index` を定型とするが、`client_id`、`shipping_item_id`、`user_id`、`packed_by_user_id`、`slip_allocated_lots(shipping_slip_id)`、`expiration_rules(shipping_item_id)`、`total_picks(client_id)`、`users_tokens(user_id)` の扱いが書かれていない。`inventory_order_id` による照会（突合）の索引も無い。
2. `status` と他カラムの整合を守る CHECK 制約が無い（例：`packed` なら `packed_at` / `packed_by_user_id` が NOT NULL、`shortage` 以外では `shortage_pieces` が NULL、`allocated`/`packed`/`reversed` なら `inventory_order_id` が NOT NULL）。
3. `total_picks.status` の部分ユニーク・二重ピック防止は「`FOR UPDATE` で対象伝票をロック」（§8.1）としているが、複数ユーザーが同じグループを同時に作成した場合の期待動作（後続は「対象なし」で失敗）が書かれていない。
4. 命名: 同じ `user_id` が `shipping_slips`（登録者）と `total_picks`（発行者）で意味が違い、`packed_by_user_id` とは命名規則が揃っていない。`required_exp_date` は在庫側の `min_expiration_date` / `expiration_date` と略語の流儀が違う（§4.1 に対応表はあるが、正式名は用語集で 1 つに決めるべき）。

**批判:** 索引一覧と CHECK 制約の一覧を §3 に追記する。`user_id` は `created_by_user_id` / `issued_by_user_id` のように役割が分かる名前にそろえる。

## 11. 在庫側設計書の修正に依存する前提が、発送側設計書に明記されていない

**問題:** 発送側は「在庫側の API 仕様を正とし、本書では重複して定義しない」（§4）として在庫側にのみ依存を委ねているが、本レビューで見つかった次の項目は **両設計書を同時に直さないと成立しない**。

| 発送側の記述 | 必要な在庫側の仕様（現状は未定義） |
| :-- | :-- |
| §5.4-4 / §9 #2 の「照会して突合」 | ⑤ 照会 API の応答項目、`external_slip_id` による照会 |
| §5.5 / §5.8 の再引当（#1） | 内容不一致の再送を 409 で返す冪等性 |
| §5.7 の出庫取消 | 操作者（`operator`）を受け取り保存する仕様 |
| §3.2 の `inventory_maker_id` | ⑦ 応答の `maker_id`（在庫側 v2.1 で追記済み。応答例 L340 は `maker_id` を含む） |
| §4.2 の 404 / 422 の扱い | アーカイブ済み商品・倉庫を指定したときの応答コード |

**批判:** 発送側設計書の §4 に「在庫側設計書の改訂事項（依存）」の節を設け、上記を一覧化する。どちらかだけ先に実装に入ると、通信断のテスト（§8.2 で必須）が書けない。

## 12. 用語集・命名・永続ドキュメントとの整合（在庫側と共通）

`docs/glossary.md` が存在せず、coding-rules §16.4（用語集に揃えることが `[必須]`）を満たせない。「トータルピック」「仕分け」「梱包」「引当」「追加ピック」「要再発行」などは発送固有の語で、帳票（現場で使う紙）にも出るため、画面・帳票・コードの用語を 1 対 1 に固定する。永続ドキュメント化（`docs/product-requirements.md` 等）と `.steering/` 作成、`implement-idea` の入力形式（`*-final.md`）の扱いは在庫側レビュー #12 と同じ。

## まとめ：実装着手の前提条件

| # | 必要作業 |
|---|--------|
| 1 | 「再引当」の手順を固定（既存オーダー照会 → 解除 → 引当 → 引当合計の検証）。`status` と `inventory_order_id` の関係を CHECK 制約にも落とす |
| 2 | トータルピック: §3.4 の「`allocated` だけが紐づく」を修正。`outdated` 時の PDF ダウンロードと版数の扱いを決め、`total_picks` の遷移図と操作可否表を追加 |
| 3 | `shipping_slips` に取消・出庫取消の実行者・日時・理由を追加し、在庫側の `operator` 受け渡しと対にする |
