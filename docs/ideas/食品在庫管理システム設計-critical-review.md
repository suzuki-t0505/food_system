# 批判的分析レポート: `食品在庫管理システム設計.md` の全否定

作成日: 2026-11-03
対象文書: `docs/ideas/食品在庫管理システム設計.md`（ドラフト v2.1）

> 調査範囲の注記: `food_vault/` は `mix phx.new` 直後の雛形で、スキーマ・マイグレーション・Context は 1 つも無い（`priv/repo/migrations/` は空、`lib/food_vault/` は `application.ex` / `mailer.ex` / `repo.ex` のみ）。`docs/` には `coding-rules.md` しか無く、`glossary.md` / `functional-design.md` は存在しない。このため「既存実装との矛盾」ではなく、**設計書が前提としている基盤の欠落**、**coding-rules.md との整合**、**発送システム設計書（`docs/ideas/発送システム 基本設計書.md`）との契約の穴**を根拠にしている。`deps/` が未取得のため `phx.gen.auth` の生成物は未確認。

---

## 総評

業務ロジック（FEFO 引当・自動荷崩し・CHECK 制約・ロック・冪等性）は v2 でよく練られており、骨格は実装に進める水準。ただし **API 契約の未定義部分（②〜⑤の仕様、冪等性の厳密さ、reverse の権限境界）**と**デッドロック防止のロック順序の定義漏れ**は、発送システム側の実装と食い違ったまま作り込むと手戻りが大きい。実装着手前に下記の前提条件（末尾の表）を設計書へ反映すること。

## 1. ULID 前提の基盤が未整備で、`config.exs` の記述とも食い違っている

**問題:** §2 は「`config/config.exs`（`generators: [... binary_id: true]`）に合わせている」と書くが、`binary_id: true` が生成するのは **UUID**（`:binary_id`）の主キーであり ULID ではない。ULID を使うための依存パッケージ名・バージョン・Elixir 1.20 / Ecto 3.13 との互換性も未確認のまま。

**証拠:**
- `food_vault/config/config.exs:11-12`: `generators: [timestamp_type: :utc_datetime, binary_id: true]`
- `food_vault/mix.exs` の `deps`、および `mix.lock` に `ulid` を含む依存は 0 件。設計書 §7.2 も「`mix.exs` は現状未追加」とだけ書き、パッケージを指定していない。
- `lib/food_vault/schema.ex`（coding-rules §5.1 の `{App}.Schema` マクロ）は存在しない。
- `food_vault/mix.exs:8` は `elixir: "~> 1.20"`、`Dockerfile.dev:1` は `1.20.5-otp-29`。一方 `CLAUDE.md` の技術スタックは「Elixir 1.18.2 / Erlang 27」。

**批判:** ULID は全テーブルの主キー・外部キー・API の ID 形式・先出しの第3ソートキー（§1.1）に波及する根幹の決定だが、実装可否の裏付けが無い。`phx.gen.auth` の生成物は `binary_id`（UUID）前提で出るため、`users` / `users_tokens` を ULID に載せ替える手順も必要。採用ライブラリ（保守状況・Ecto 3.13 対応）を先に確定し、`FoodVault.Schema` と `config.exs` の `generators` の扱い（`binary_id: true` を残すか）を設計書に明記すること。`CLAUDE.md` のバージョン記述も実態に合わせて更新する。

## 2. API ②〜⑤ の仕様が未定義で、発送側が依存している応答項目が決まっていない

**問題:** §5 でリクエスト／レスポンスが定義されているのは ① 出庫引当だけ。②出庫確定・③引当解除・④出庫取消・⑤照会の応答ボディ、④の `reason` 以外の項目、エラー時の形式（特に ④ の権限エラー）が無い。さらに ⑤ は `:id` 指定のみで、`external_slip_id` による照会も一覧もできない。

**証拠:**
- 設計書 §5 L326-334 の表は用途と成功ステータスのみ。レスポンス例は ① だけ（L363-383）。
- 発送側 §5.4-4 は「409 のとき在庫側へ照会し、在庫側がすでに `shipped` なら発送側も `packed` に更新」と、**応答に `status` が含まれること**を前提にしている。
- 発送側 §9 未決 #2 は「`allocated` と在庫側オーダー状態の不一致を検出する定期チェック」を挙げているが、在庫側に一覧・検索 API が無く実現できない。
- 発送側 §4.2 は、引当 API のレスポンスを受け取れなかった（通信断）場合を再 POST の冪等性だけで復旧する設計で、`order_id` を知らない状態から現状を引く手段が無い。
- `food_vault/lib/food_vault_web/controllers/error_json.ex:12,19` は既定で `%{errors: %{detail: ...}}` を返す。設計書の `{ "error": "...", "shortages": [...] }`（L388）とは形式が違い、`FallbackController` 等で統一する方針が書かれていない。

**批判:** 2 つのアプリを別チームが並行実装しても噛み合うよう、②〜⑤ の応答（最低限 `order_id` / `status` / `shipped_at` / 引当明細）を ① と同じ粒度で定義する。⑤ には `GET /shipment_orders?external_slip_id=` を足す（突合と通信断復旧の両方に必要）。JSON エラー形式は全エンドポイント共通にし、不正な ULID 文字列（長さ不正など）が 500 にならず 404/422 になることも明記する。

## 3. 出庫取消（④）の権限を呼び出し側に丸投げしており、実行者も追跡できない

**問題:** 出庫取消は `admin` 限定の操作（§4.5・権限表 L469）だが、API 経由では「管理者判定は呼び出し側で行う」（L291）とされ、在庫側はサービストークンだけで通す。受払履歴の `user_id` も NULL になり、**誰が取り消したかが在庫側に残らない**。

**証拠:**
- 設計書 §4.5 L291、§3.8 L180（`NULL＝API操作`）、§5 L322。
- 発送側 §7 は「誰が操作したかは `shipping_slips.user_id` / `packed_by_user_id` で追跡する」とするが、出庫取消（`reversed`）の実行者を保存するカラムは発送側 §3 にも見当たらない（伝票側の確認は発送設計書レビューで行う）。

**批判:** 共有シークレットが漏れると、在庫を巻き戻す最強権限の操作を誰でも実行でき、痕跡も残らない。④ には `operator`（発送側ユーザーの ID／メール）を必須で受け取り、`inventory_transactions.note` もしくは専用カラムに保存する。あわせて Bearer トークンの比較に `Plug.Crypto.secure_compare/2` を使うこと、API が UI と同一 Endpoint・同一ポート（`runtime.exs:23-24` の `PORT`）で公開されることを踏まえ、ネットワーク制限（Compose 内部のみ公開する等）と本番での TLS 前提を実装方針に書く。トークンのローテーション手順も未定義。

## 4. 冪等性が「内容の違う再送」を黙って成功にしてしまう

**問題:** 「同じ `external_slip_id`（`cancelled` 以外）での再引当は、再処理せず既存オーダーを返す（200）」（L324）。リクエスト内容（倉庫・出庫予定日・数量・最低許容期限）が既存オーダーと**異なっていても**、古い内容のオーダーが 200 で返る。

**証拠:** 発送側 §5.5 の数量変更は「① ローカルを `pending` に更新 → ② 引当解除 API → ③ 新内容で引当 API」。② が通信失敗・タイムアウトで未確定のまま ③ に進む（または利用者が「再引当」を押す）と、在庫側には旧数量の `allocated` オーダーが残っており、③ は **旧数量のオーダーを 200 で返す**。発送側 §4.2 は 201/200 をどちらも成功として `allocated` にするため、**数量が食い違った状態が正常として保存される**。

加えて、同一 `external_slip_id` の同時 POST は部分ユニーク（L132）で一方が制約違反になるが、設計書にはその際に既存オーダーを返す（500 にしない）処理が書かれていない。

**批判:** 冪等再送では「既存オーダーの内容が要求と一致するか」を検証し、不一致は 409（例：`idempotency_conflict`）で返す。ユニーク制約違反は rescue して既存オーダーを再取得し、同様に内容を検証する。coding-rules §5.7 の `unique_constraint` / `unsafe_validate_unique` の対（部分ユニークの `name:` 指定、`unsafe_validate_unique` の `query:` による `status <> 'cancelled'` 条件）の書き方もここで決めておく。

## 5. ロック順序の定義が不十分で、デッドロックを防げない

**問題:** §4.0 は「複数ロットをロックするときは常に `(expiration_date, received_date, id)` の昇順」とするが、この並びは **`warehouse_id` / `item_id` を含まない**。さらに、明細（lines）をどの順で処理するかが定義されていない。

**証拠（具体例）:**
- 複数明細の引当（API は複数明細対応、§8 #8）: オーダー X が [商品A, 商品B]、オーダー Y が [商品B, 商品A] の順で明細を受け取ると、X は A のロット→B のロット、Y は B のロット→A のロットの順にロックし、相互待ちになる。ロット間の期限順はあっても、**商品をまたぐ順序は不定**。
- 出庫確定・引当解除・出庫取消（§4.3-4.5）も「引当明細のロットを先出し順にロック」と書くだけで、明細をまたぐ順序は同じ穴。
- 倉庫間移動（§4.6）は移動元ロット→移動先ロット（`ON CONFLICT DO UPDATE`）の順で更新する。同じ商品・期限・入荷日で A→B 倉庫と B→A 倉庫の移動が同時に走ると、互いのロットを待つ。

**批判:** 全操作共通のロックキーを `(warehouse_id, item_id, expiration_date, received_date, id)` として明文化し、(1) 引当は明細を `item_id` 昇順に並べ替えてから処理、(2) 確定・取消・出庫取消は対象ロットを 1 クエリで `ORDER BY` + `FOR UPDATE` して一括ロック、(3) 移動は移動先ロットを先に（存在しなければ作成してから）同じキー順で一括ロック、とする。

## 6. マスタ変更・アーカイブ時のルールが欠けている

**問題:** 次の取り扱いが未定義。
1. **入数変更禁止の実装方法と競合**: 「ロットが1件でも存在する商品は入数の変更を禁止」（L19）。入荷と同時に入数変更が走ると、チェックを通過した直後に入荷される競合（TOCTOU）が起こり得る。
2. **期限区分（`expiration_type`）の変更**: 入数と違い変更ガードが無い。`none` で作ったロットは `9999-12-31` で保存される（L49）ため、後から `best_before` に変えると**期限が 9999 年の「賞味期限品」ロット**が残る。逆も同様。
3. **アーカイブ済みのメーカー・倉庫・商品**: 入荷・出庫引当・移動での扱い（拒否するのか、既存在庫は引き当てられるのか）が無い。⑦ は「有効な商品」だけを返す（L334）が、① が無効商品の `item_id` を受けたときの応答（404 か 422 か）は未定義。有効商品を持つメーカーのアーカイブ可否も無い。
4. 倉庫の `archived_at` 後に在庫が残っている場合の扱い。

**批判:** 入数・期限区分は「ロット（0 数量のものを含む）が 1 件でもあれば変更不可」とし、入荷・引当側は `items` 行を `FOR SHARE`、マスタ更新側は `FOR UPDATE` で読んで競合を排除する。アーカイブ可否（在庫 > 0 の倉庫・商品、有効商品を持つメーカーは不可など）と、API・画面ごとの拒否時の応答を一覧表にする。

## 7. 発送起源のオーダーを在庫側の画面から操作できてしまう

**問題:** 画面側の権限表では `staff` が出庫オーダーの登録・出庫確定・引当解除を実行できる（L413, L466）。`external_slip_id` を持つ（＝発送システム起源の）オーダーを在庫側の画面で確定・解除すると、**発送側の伝票状態と静かに食い違う**。

**証拠:** 発送側 §5.4-4 は「409 `invalid_state` のとき、在庫側がすでに `shipped` なら発送側も `packed` に更新」とだけ書き、在庫側が `cancelled` になっていた場合は「最新状態を表示してエラー」で終わる（自動復旧しない）。発送側 §9 #2 の定期突合も未決のまま。

**批判:** `external_slip_id` が付いたオーダーは、画面からは参照のみ（または `admin` の緊急操作のみ・理由必須・発送側へ通知）にする、と決める。画面での手動出庫オーダーは `external_slip_id = NULL` のものに限定する。突合の仕組み（§2 の `external_slip_id` 照会）とセットで設計する。

## 8. 状態遷移の「誰が・いつ・なぜ」が DB に残らない

**問題:** §3.8 L192 は「引当・引当解除は受払履歴に記録しない。記録は `shipment_allocations` と `shipment_orders.status` が担う」とするが、`status` は上書きされるだけで、**取消した日時・実行者・理由**を残すカラムが `shipment_orders` に無い。`shipped_at` しか無く、出庫取消の理由はロット単位の `inventory_transactions.note` に複製されるのみ。オーダーの作成者・確定者も記録されない。

**証拠:** `shipment_orders` の定義（§3.5）は `warehouse_id` / `shipment_date` / `status` / `external_slip_id` / `shipped_at` のみ。§7.3 L487 は「書き込み操作は操作ログに操作ユーザーを含める（coding-rules §12。未導入のため併せて実装する）」とするが、Logger 出力であり、ログのローテーション後は追えない。

**批判:** 食品の出庫は事故対応（リコール・誤出荷調査）で履歴が問われる。最低限 `created_by_user_id` / `shipped_by_user_id` / `cancelled_at` / `reversed_at` / `reverse_reason` 等をオーダーに持たせる（API 経由は #3 の `operator` を保存）か、状態遷移履歴用のテーブルを定義する。

## 9. 運用上のリカバリ手段が薄い

**問題:**
- **入荷の誤入力**: 訂正・取消の機能が無く、`admin` 限定の棚卸調整（§4.7）が唯一の手段。`staff` が入荷した誤りは `admin` に依頼するしかない。意図した運用か明記されていない。
- **実在庫が引当済数を下回る場合**（紛失・破損）: 棚卸調整は「有効在庫を下回る減算は不可」（L309）のため、該当ロットがすべて引当済だと調整できない。先にオーダーを解除する必要があるが、それは #7 の発送側との不整合を生む。
- **荷崩しの不可逆性**（§4.2 L270）と荷まとめなし（§3.4 L121）: 数量変更のたびに「解除 → 再引当」が走る運用（発送 §5.5）で、開封済みのバラが累積する。ケース単位の出庫（`req_cases > 0`）が将来できなくなる懸念への対策（定期的な荷まとめ調整など）が無い。

**批判:** 入荷訂正の権限（`staff` で可とするか）、棚卸時の「引当済 > 実在庫」の処理手順、バラ累積時の運用（棚卸調整でケースへ戻す手順）を §4.7 に追記する。

## 10. DB 設計: インデックス未定義と、未使用の先行カラム

**問題:** 設計書は一意制約のみ定義し、通常のインデックスを一切定義していない。coding-rules §14.4 は FK ごとの `create index` を定型としている（`docs/coding-rules.md:1667-1690`）。また、未使用のカラム `shipment_allocations.is_picked`（L162「将来の消し込み用」）・`items.alert_days_before`（L93）を先行で持つ。

**証拠:** 検索・結合が想定される列: `inventory_transactions(lot_id)` / `(shipment_order_id)` / `(transfer_id)` / `(inserted_at)`（受払履歴の期間・移動ペア検索、§6 L416）、`shipment_allocations(lot_id)`（ロット別の引当参照）、`shipment_order_lines(item_id)`、`shipment_orders(warehouse_id, shipment_date)` / `(status)`（一覧）、`users_tokens(user_id)`（全セッション削除、§3.11 L232）。`inventory_lots` の複合ユニーク `(warehouse_id, item_id, expiration_date, received_date)` は引当クエリの並びと一致しており、これは良い。

**批判:** 上記を設計書にインデックス一覧として追記する。`transfer_id` は参照先テーブルの無い裸の ULID なので、`inventory_transactions` 内での整合（`transfer_out` と `transfer_in` が必ず対になること）をアプリ層・テストで担保する旨も書く。`is_picked` / `alert_days_before` は、使う機能が決まるまでマイグレーションに入れない方針に倒すか、先行用意する理由を明記する（`archived_at` の方針とは別に、未使用カラムは `NOT NULL`・デフォルトの設計判断を後回しにすることになる）。

## 11. 荷崩しの実装粒度（履歴の行数・ループ）が曖昧

**問題:** §4.2 は「1ケースずつ開封」を繰り返し、受払履歴に `auto_break` を記録とするが、**1ケースごとに1行か、ロット単位に合算して1行か**が不明。1ケースずつ UPDATE する実装では、大量バラ要求（例：数千個）でクエリ数が線形に増える。

**批判:** 必要ケース数 `k = ceil(不足バラ数 / units_per_case)`（ただし有効ケース数が上限）を算術で求め、ロットごとに 1 回の UPDATE と 1 行の履歴（`case_diff = -k`, `piece_diff = +k × units_per_case`）にまとめる、と書き換える。結果は 1 ケースずつ処理した場合と同じになることを §4.2 に明記する。

## 12. 用語集・永続ドキュメント・開発プロセスとの整合

**問題:** coding-rules §16.4 は「リソース名は `docs/glossary.md` のユビキタス言語に揃える `[必須]`」とするが、`docs/glossary.md` は存在しない。ロット・引当・有効在庫・荷崩し・荷まとめ・出庫確定・出庫取消・トータルピックなどの語が未定義のまま。CLAUDE.md の基本フロー（`docs/` の永続ドキュメント → `.steering/` → 実装）に従うと、次工程は永続ドキュメント化であり、`ideas/` から直接実装には進めない。また `implement-idea` スキルは `docs/ideas/*-final.md` のみを対象とするため、この 2 文書（`-final.md` ではない）は現状そのままでは同スキルの入力にならない。

**命名の食い違い（発送側との対応）:** 同一概念が `min_expiration_date`（在庫側）／`required_exp_date`（発送側）、`req_pieces`／`total_piece_qty`、`shipment_orders`（在庫・出庫）／`shipping_slips`（発送・伝票）と別名になっている。発送側 §4.1 に対応表はあるが、用語集で正式名を 1 つ決める。

**coding-rules との乖離:** coding-rules §11.3 は `current_user` 前提、`food_vault/AGENTS.md:12-14` は Phoenix 1.8 の `current_scope` を前提にしている。設計書 §7.3・§8 #9 は「読み替える」で済ませているが、`[必須]` ルールとの矛盾のまま実装に入ると、レビューのたびに揺れる。規約側を先に更新する。
