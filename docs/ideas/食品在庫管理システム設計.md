- 対象アプリ: `food_vault`（Phoenix / LiveView、開発時ポート 4000、DB `food_vault_dev`）
- 連携先: 発送システム `food_ship`（別アプリ・別DB）。連携は HTTP の JSON API のみ（[§5](#5-外部api仕様発送システム向け)）
- 関連文書: [発送システム 基本設計書.md](発送システム%20基本設計書.md)、[coding-rules.md](../coding-rules.md)

## 1. システム概要と基本方針

食品特有の「消費期限・賞味期限管理」および「荷姿（ケース・バラ）管理」に対応した、複数倉庫向けの在庫管理システム。

### 1.1 コア要件

| 項目 | 決定仕様 | 備考 |
| :-- | :-- | :-- |
| 在庫管理単位 | **ケース数** と **バラ数** を分けて独立管理 | 画面・帳票では「総バラ数」も併記する（[§4.8](#48-画面入出力における総バラ数の表示仕様)） |
| ケース入数 | 商品マスタに **固定値** として保持 | 総バラ数 ＝ ケース数 × 入数 ＋ バラ数。**ロットが1件でも存在する商品は入数の変更を禁止**する |
| 先出し基準 | **第1優先：期限日（昇順）→ 第2優先：入荷日（昇順）→ 第3優先：ロットID（昇順）** | FEFO ＋ FIFO のハイブリッド。第3優先で順序を一意にする |
| 期限管理区分 | 商品マスタで「消費期限」「賞味期限」「管理なし」を区分 | 期限アラート通知は将来拡張。カラムのみ先行用意 |
| 出庫引当方式 | **自動引当（荷姿厳守＋期限順）** | 将来「自動引当＋ピッキング実績消し込み」へ拡張できる構造（引当と実績のロット逆転は起こらない前提） |
| 荷崩し | **完全自動** | バラ不足時、システムが古いロットのケースを1ケースずつ開封して引き当てる（[§4.2](#42-出庫時の自動引当と自動荷崩し)） |
| 最低許容期限 | 出庫引当の入力として **任意の `min_expiration_date`** を受け付ける | 発送システムの「出荷期限ルール」を実現する。**新規開発のため「改修」ではなく最初から仕様に含める** |
| 複数倉庫 | 出庫時は **オーダー時点で倉庫を指定** | 倉庫間移動は「移動中」状態を持たず **即時反映**。期限日・入荷日はそのまま継承 |

### 1.2 技術基盤

| 項目 | 内容 |
| :-- | :-- |
| スタック | Elixir / Phoenix 1.8 / LiveView / Ecto / PostgreSQL 15 / Tailwind CSS（Docker Compose で起動） |
| アプリ構成 | `food_vault`（本システム）と `food_ship`（発送）は **別プロジェクト・別DB・別コンテナ** |
| アプリ間通信 | `food_ship` → `food_vault` の一方向 HTTP（`Req` 使用）。Erlang クラスタ・DB共有はしない |
| コーディング規約 | [coding-rules.md](../coding-rules.md) に従う（Context + スキーマの2層、Multi による更新など） |

## 2. 共通規約

テーブル定義すべてに適用する。`coding-rules.md` および `config/config.exs`（`generators: [timestamp_type: :utc_datetime, binary_id: true]`）に合わせている。

| 項目 | 規約 |
| :-- | :-- |
| 主キー | 全テーブル **カラム名 `id`**、型は **ULID**（Ecto 型 `Ecto.ULID`、DB 列は `binary_id`）。`{App}.Schema` マクロ経由で定義する（coding-rules §5.1）。外部キーは `{参照先単数形}_id` |
| 列挙型 | DB の ENUM 型は使わず **`Ecto.Enum`（DB列は string）**。値は **小文字 snake_case の atom**（例 `:best_before`）。API の JSON では同じ文字列を使う |
| 日時 | `utc_datetime` で UTC 保存し、表示直前にだけ JST へ変換（coding-rules §16.1）。タイムスタンプは `timestamps(type: :utc_datetime)`。**`date` 型（期限日・入荷日・出庫予定日）は業務日付としてそのまま扱い、タイムゾーン変換しない** |
| 有効/無効 | `is_active` は使わず **`archived_at`（utc_datetime、NULL=有効）** による論理削除。FK は `on_delete: :nothing`（物理削除しない） |
| 期限なし | 期限区分 `none` の商品は `expiration_date = 9999-12-31` で保存する（NULL だとユニーク制約が効かないため）。`min_expiration_date` 付きの引当でも自然に対象になる |
| 数量 | `*_qty` / `*_cases` / `*_pieces` はすべて整数。DB に **CHECK 制約**で 0 以上などの不変条件を持たせる |

## 3. データベース設計

全 **8 テーブル**（マスタ 3、在庫 1、出庫 3、履歴 1）で構成する。

| 区分 | テーブル |
| :-- | :-- |
| マスタ | `makers` / `warehouses` / `items` |
| 在庫 | `inventory_lots` |
| 出庫 | `shipment_orders` / `shipment_order_lines` / `shipment_allocations` |
| 履歴 | `inventory_transactions` |

以降の表では、全テーブル共通の `id`（ULID, PK）と `inserted_at` / `updated_at`（`inventory_transactions` は `inserted_at` のみ）を省略する。

### 3.1 メーカーマスタ (`makers`)

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| メーカーコード | `maker_code` | string | NOT NULL, UNIQUE（社内管理コード等） |
| メーカー名 | `maker_name` | string | NOT NULL |
| アーカイブ日時 | `archived_at` | utc_datetime | NULL可（NULL=有効） |

### 3.2 倉庫マスタ (`warehouses`)

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 倉庫コード | `warehouse_code` | string | NOT NULL, UNIQUE |
| 倉庫名 | `warehouse_name` | string | NOT NULL |
| アーカイブ日時 | `archived_at` | utc_datetime | NULL可（NULL=有効） |

### 3.3 商品マスタ (`items`)

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| メーカーID | `maker_id` | ULID | NOT NULL, FK (`makers.id`) |
| 商品コード | `item_code` | string | NOT NULL, UNIQUE（JANコードや自社品番） |
| 商品名 | `item_name` | string | NOT NULL |
| ケース入数 | `units_per_case` | integer | NOT NULL, CHECK (`>= 1`)。ロット存在後は変更不可 |
| 期限区分 | `expiration_type` | Ecto.Enum | NOT NULL。`consumption`(消費期限) / `best_before`(賞味期限) / `none`(管理なし) |
| アラート日数 | `alert_days_before` | integer | NULL可, CHECK (`>= 0`)。将来の期限アラート用。`none` の商品では使わない |
| アーカイブ日時 | `archived_at` | utc_datetime | NULL可（NULL=有効） |

### 3.4 在庫ロット (`inventory_lots`)　★システムの心臓部

「倉庫 × 商品 × 期限日 × 入荷日」の粒度で現在庫と引当済数を保持する。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 倉庫ID | `warehouse_id` | ULID | NOT NULL, FK (`warehouses.id`) |
| 商品ID | `item_id` | ULID | NOT NULL, FK (`items.id`) |
| 期限日 | `expiration_date` | date | NOT NULL。消費/賞味期限。管理なしは `9999-12-31` |
| 入荷日 | `received_date` | date | NOT NULL。倉庫間移動時も元の入荷日を維持 |
| 現在ケース数 | `case_qty` | integer | NOT NULL, DEFAULT 0 |
| 現在バラ数 | `piece_qty` | integer | NOT NULL, DEFAULT 0 |
| 引当済ケース数 | `allocated_case_qty` | integer | NOT NULL, DEFAULT 0（出庫待ちロック分） |
| 引当済バラ数 | `allocated_piece_qty` | integer | NOT NULL, DEFAULT 0（出庫待ちロック分） |

- **複合ユニーク**: `UNIQUE (warehouse_id, item_id, expiration_date, received_date)`
- **CHECK 制約**（不変条件）:
  - `case_qty >= 0` かつ `piece_qty >= 0`
  - `0 <= allocated_case_qty <= case_qty`
  - `0 <= allocated_piece_qty <= piece_qty`
- 有効在庫（引当可能数）の計算式:
  - 有効ケース数 = `case_qty - allocated_case_qty`
  - 有効バラ数 = `piece_qty - allocated_piece_qty`
  - 有効総バラ数 = 有効ケース数 × `units_per_case` ＋ 有効バラ数
- **在庫が 0 になったロットも行は削除しない**（受払履歴・引当明細が FK で参照するため）。一覧画面では既定で 0 ロットを非表示にする。
- **バラの自動まとめ（荷まとめ）は行わない**。`piece_qty` が入数以上になっても自動でケースへ換算しない（入荷時の入力値どおり保持）。

### 3.5 出庫オーダー (`shipment_orders`)

出庫指示のヘッダ。1オーダー＝1倉庫・1出庫予定日。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 出庫元倉庫ID | `warehouse_id` | ULID | NOT NULL, FK (`warehouses.id`)。オーダー時点で指定 |
| 出庫予定日 | `shipment_date` | date | NOT NULL |
| ステータス | `status` | Ecto.Enum | NOT NULL, DEFAULT `allocated`。`allocated`(引当済) / `shipped`(出庫完了) / `cancelled`(取消) / `reversed`(出庫取消済)。遷移は [§3.9](#39-ステータス遷移) |
| 連携元伝票ID | `external_slip_id` | string | NULL可。発送システムの伝票ID（冪等性キー）。**部分ユニーク**: `UNIQUE (external_slip_id) WHERE external_slip_id IS NOT NULL AND status <> 'cancelled'` |
| 出庫確定日時 | `shipped_at` | utc_datetime | NULL可 |

> 部分ユニークにするのは、数量変更時に「取消 → 同じ伝票IDで再引当」を許すため。

### 3.6 出庫オーダー明細 (`shipment_order_lines`)

オーダーが「何を何個要求したか」の記録。取消・再引当・不足判定の根拠になる。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 出庫オーダーID | `shipment_order_id` | ULID | NOT NULL, FK (`shipment_orders.id`) |
| 商品ID | `item_id` | ULID | NOT NULL, FK (`items.id`) |
| 要求ケース数 | `req_cases` | integer | NOT NULL, DEFAULT 0 |
| 要求バラ数 | `req_pieces` | integer | NOT NULL, DEFAULT 0 |
| 最低許容期限日 | `min_expiration_date` | date | NULL可。指定時はこの日以降が期限のロットだけ引当対象 |

- `UNIQUE (shipment_order_id, item_id)`（同一オーダーに同じ商品の明細を重複させない）
- CHECK: `req_cases >= 0`, `req_pieces >= 0`, `req_cases + req_pieces > 0`

### 3.7 出庫引当明細 (`shipment_allocations`)

自動引当の結果（どのロットから何個出すか）。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 出庫オーダー明細ID | `shipment_order_line_id` | ULID | NOT NULL, FK (`shipment_order_lines.id`) |
| 対象ロットID | `lot_id` | ULID | NOT NULL, FK (`inventory_lots.id`) |
| 引当ケース数 | `allocated_cases` | integer | NOT NULL, DEFAULT 0 |
| 引当バラ数 | `allocated_pieces` | integer | NOT NULL, DEFAULT 0 |
| ピッキング済フラグ | `is_picked` | boolean | NOT NULL, DEFAULT false（将来の「消し込み機能」用） |

- `UNIQUE (shipment_order_line_id, lot_id)`。ケース引当とバラ引当が同じロットに当たった場合は **1行にまとめて加算**する。
- CHECK: `allocated_cases >= 0`, `allocated_pieces >= 0`, `allocated_cases + allocated_pieces > 0`

### 3.8 在庫受払履歴 (`inventory_transactions`)

すべての **現在庫の変動**（入荷・出庫・荷崩し・移動・調整）の証跡ログ。追記のみ（UPDATE / DELETE しない）。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| ロットID | `lot_id` | ULID | NOT NULL, FK (`inventory_lots.id`) |
| 処理区分 | `transaction_type` | Ecto.Enum | NOT NULL。下表 |
| 変動ケース数 | `case_diff` | integer | NOT NULL。増減値（荷崩しなら `-1`） |
| 変動バラ数 | `piece_diff` | integer | NOT NULL。増減値（入数10の荷崩しなら `+10`） |
| 出庫オーダーID | `shipment_order_id` | ULID | NULL可, FK (`shipment_orders.id`)。出庫・荷崩し・出庫取消で設定 |
| 移動ID | `transfer_id` | ULID | NULL可。移動出庫と移動入庫のペアを結ぶ（アプリ側で `Ecto.ULID.generate()`） |
| 備考 | `note` | string | NULL可。調整・出庫取消では理由を必須とする |

| `transaction_type` | 意味 | 変動の向き |
| :-- | :-- | :-- |
| `receive` | 入荷 | ＋ |
| `ship` | 出庫確定 | － |
| `ship_reverse` | 出庫取消（出庫確定の巻き戻し） | ＋ |
| `auto_break` | 自動荷崩し | ケース－／バラ＋ |
| `transfer_out` | 移動出庫 | － |
| `transfer_in` | 移動入庫 | ＋ |
| `adjust` | 棚卸調整・廃棄 | ＋／－ |

> **引当・引当解除は在庫の増減ではないため受払履歴に記録しない**（記録は `shipment_allocations` と `shipment_orders.status` が担う）。

### 3.9 ステータス遷移

```
allocated ──出庫確定──▶ shipped ──出庫取消（管理者）──▶ reversed
    │
    └──取消──▶ cancelled
```

- `shipped` / `cancelled` / `reversed` からは他のステータスへ戻れない。
- 取消できるのは `allocated` のみ。`shipped` を戻す場合は出庫取消（[§4.5](#45-出庫取消管理者操作)）を使う。

## 4. コア業務ロジック仕様

すべて **単一トランザクション**（`Ecto.Multi` + `Repo.transact/1`）で処理し、途中で失敗したら全体をロールバックする。

### 4.0 共通ルール

- **ロック**: 対象ロットは `SELECT ... FOR UPDATE` で取得してから更新する（二重引当の防止）。複数ロットをロックするときは **常に `(expiration_date, received_date, id)` の昇順**で取得する（デッドロック防止）。
- **出庫可能期限**: 出庫引当の対象は `expiration_date >= GREATEST(shipment_date, COALESCE(min_expiration_date, shipment_date))` のロット。`min_expiration_date` が出庫予定日より前でも期限切れ在庫は引き当てない。
- **ソート順（先出し）**: `ORDER BY expiration_date ASC, received_date ASC, id ASC`

### 4.1 入荷

入力: 倉庫・商品・（期限日）・入荷日・ケース数・バラ数。

1. 期限区分が `none` 以外の商品は期限日を必須とする。`none` の場合は `9999-12-31` を設定。
2. 「同じ倉庫 × 商品 × 期限日 × 入荷日」のロットがあれば加算、なければ新規作成（`INSERT ... ON CONFLICT ... DO UPDATE` で原子的に加算）。
3. 受払履歴に `receive` を記録。

### 4.2 出庫時の自動引当と自動荷崩し

入力: 出庫倉庫・出庫予定日・明細（商品・`req_cases`・`req_pieces`・任意の `min_expiration_date`）・任意の `external_slip_id`。明細ごとに以下を行う。

1. **対象ロットの取得**: 指定倉庫・商品のロットのうち、[§4.0](#40-共通ルール) の出庫可能期限を満たすものを先出し順に取得（`FOR UPDATE`）。
2. **ステップ1 ケース要求分 (`req_cases`)**: ロットを上から走査し、有効ケース数 > 0 のロットから `req_cases` を満たすまで引き当てる（`allocated_case_qty` 加算、引当明細に加算）。有効ケース数の合計が足りなければ「ケース在庫不足」でロールバック。
3. **ステップ2 バラ要求分 (`req_pieces`)**: ロットを上から走査し、`req_pieces` が 0 になるまで次を繰り返す。
   1. **既存の有効バラから引当**: 有効バラ数 > 0 なら可能な限り引き当てる。
   2. **同一ロット内で自動荷崩し**: まだ要求が残り、そのロットの **有効ケース数 > 0** なら、**1ケースずつ**開封する（`case_qty - 1`, `piece_qty + units_per_case`、受払履歴に `auto_break`）。開封で増えたバラから引き当てる。要求が満たされるか有効ケースが尽きるまで繰り返す。
   3. それでも足りなければ **次のロット**へ進み、(a)(b) を行う。
4. 全ロットを走査しても `req_pieces` が残る場合は「バラ在庫不足」としてロールバック（荷崩しも含めて全て元に戻る）。
5. 引当結果を `shipment_allocations` に保存（同一ロットは1行に加算）。

補足:
- ステップ1で引き当てたケースは「引当済」のため、ステップ2の荷崩し対象にならない（有効ケース数で判定するため）。
- 荷崩しで余ったバラは、引当てずにそのロットのバラ在庫として残る。
- **荷崩しは出庫取消・引当解除でも元に戻さない**（開封済みのケースはバラ在庫のまま）。

### 4.3 出庫確定

`allocated` のオーダーを `shipped` にする。

1. 引当明細のロットを先出し順にロックする。
2. 引当明細ごとに、ロットの `case_qty` / `allocated_case_qty` を `allocated_cases` 分、`piece_qty` / `allocated_piece_qty` を `allocated_pieces` 分それぞれ減算。
3. 受払履歴に `ship`（ロット単位）を記録。
4. オーダーを `shipped`、`shipped_at` を現在時刻に更新。

### 4.4 引当解除（取消）

`allocated` のオーダーを `cancelled` にする。

1. 引当明細のロットをロックし、`allocated_case_qty` / `allocated_piece_qty` を引当分だけ減算（現在庫は変えない）。
2. オーダーを `cancelled` に更新。引当明細は **削除せず残す**（何を引き当てていたかの証跡）。
3. 数量変更は「取消 → 新規引当」の2操作で行う（呼び出し側が連続実行）。

### 4.5 出庫取消（管理者操作）

誤操作で `shipped` にしたオーダーを戻す。**管理者のみ**（認可は呼び出し側のアプリで制御。[§8](#8-未決事項)）。

1. 引当明細のロットをロックし、`case_qty` / `piece_qty` を引当分だけ **加算**（引当済数は変えない＝ロックは戻さない）。
2. 受払履歴に `ship_reverse` を記録（`note` に理由を必須入力）。
3. オーダーを `reversed` に更新。

### 4.6 倉庫間移動（即時反映・属性継承）

入力: 移動元倉庫・移動先倉庫・**対象ロット（ロットID指定）**・移動ケース数・移動バラ数。

1. **移動元ロットの減算**: 有効在庫（現在庫 − 引当済）の範囲で減算する。バラが不足し、そのロットの有効ケースがあれば、出庫時と同様に **同一ロット内で自動荷崩し** してから減算する。受払履歴に `transfer_out`（荷崩しは `auto_break`）を記録。
2. **移動先ロットへの加算**: 移動先倉庫の「同じ商品 × 同じ `expiration_date` × 同じ `received_date`」のロットへ `ON CONFLICT DO UPDATE` で加算（なければ新規作成）。受払履歴に `transfer_in` を記録。
3. 移動出庫と移動入庫には同じ `transfer_id` を付ける。

> 「自動引当による移動対象ロットの自動選択」は将来拡張とし、本バージョンでは対象外。

### 4.7 棚卸調整・廃棄

ロットを指定し、ケース数・バラ数の増減を登録する。有効在庫（現在庫 − 引当済）を下回る減算は不可。受払履歴に `adjust`（理由を `note` に必須入力）を記録。

### 4.8 画面入出力における「総バラ数」の表示仕様

- **入力時**: 入荷・出庫・移動のすべての画面で `[ケース数]` と `[バラ数]` の2入力欄を設ける。商品マスタの `units_per_case` を参照し、入力と同時に **総数：〇〇 個** をリアルタイム表示する。
- **一覧表示時**: 在庫一覧では、ロット単位・商品単位の集計行に常に `ケース数 ｜ バラ数 ｜ 総バラ数（ケース×入数＋バラ）` の3列をセットで表示する。
- 総バラ数の計算は Web 層・テンプレートに書かず、`FoodVault.Utils.Calc` に集約する（coding-rules §10.7, §16.2）。

## 5. 外部API仕様（発送システム向け）

- 提供側は本システム。LiveView 対象外の JSON API なので、Controller（`FoodVaultWeb.Api.V1.*`）と `:api` pipeline で実装する。
- **認証**: 共有シークレットによる Bearer トークン。値は `runtime.exs` で環境変数から読み、未設定なら起動時に落とす（coding-rules §13）。
- **ベースパス**: `/api/v1`。ID はすべて ULID 文字列。日付は ISO 8601（`YYYY-MM-DD`）。列挙値は小文字 snake_case 文字列。
- **冪等性**: 同じ `external_slip_id`（`cancelled` 以外）での再引当は、再処理せず既存オーダーを返す（200）。出庫確定・取消も、すでにその状態なら 200 で現状を返す。

| # | メソッド / パス | 用途 | 成功時 |
| :-- | :-- | :-- | :-- |
| ① | `POST /api/v1/shipment_orders` | 出庫引当（[§4.2](#42-出庫時の自動引当と自動荷崩し)） | 201（冪等再送は 200） |
| ② | `POST /api/v1/shipment_orders/:id/ship` | 出庫確定（[§4.3](#43-出庫確定)） | 200 |
| ③ | `POST /api/v1/shipment_orders/:id/cancel` | 引当解除（[§4.4](#44-引当解除取消)） | 200 |
| ④ | `POST /api/v1/shipment_orders/:id/reverse` | 出庫取消（[§4.5](#45-出庫取消管理者操作)）。body に `reason` 必須 | 200 |
| ⑤ | `GET /api/v1/shipment_orders/:id` | 状態・引当結果の照会（突合用） | 200 |

### ① 出庫引当

リクエスト:

```json
{
  "warehouse_id": "01JA...",
  "shipment_date": "2026-11-15",
  "external_slip_id": "01JB...",
  "lines": [
    {

      "req_cases": 0,
      "req_pieces": 3,
      "min_expiration_date": "2026-12-15"
    }
  ]
}
```

レスポンス（成功時）:

```json
{
  "order_id": "01JD...",
  "status": "allocated",
  "lines": [
    {
      "item_id": "01JC...",
      "allocations": [
        {
          "lot_id": "01JE...",
          "expiration_date": "2026-12-20",
          "allocated_cases": 0,
          "allocated_pieces": 3
        }

    }

```

### エラー応答

```json
{ "error": "insufficient_stock", "shortages": [{ "item_id": "01JC...", "shortage_cases": 0, "shortage_pieces": 2 }] }
```

| HTTP | `error` | 発生条件 | 発送システム側の扱い |
| :-- | :-- | :-- | :-- |
| 401 | `unauthorized` | トークン不正 | 設定エラーとして通知（リトライ不可） |
| 404 | `not_found` | オーダー・倉庫・商品が存在しない | 不整合として通知 |
| 409 | `invalid_state` | 状態遷移として不正（例：`cancelled` の出庫確定） | 画面を再読込して最新状態を表示 |
| 422 | `insufficient_stock` | 期限条件を満たす在庫が不足（ロールバック済み。オーダーは作られない） | 伝票を `shortage` で保存 |
| 422 | `validation_failed` | 入力不正（数量が負、明細が空など）。`errors` に項目別メッセージ | 入力エラーとして表示 |

## 7. 実装方針

### 7.1 Context とスキーマ（coding-rules §2.1：Context + スキーマの2層、子エンティティ専用 Context は作らない）

| Context | スキーマ（集約） |
| :-- | :-- |
| `FoodVault.Makers` | `Maker` |
| `FoodVault.Warehouses` | `Warehouse` |
| `FoodVault.Items` | `Item` |
| `FoodVault.Inventories` | `InventoryLot`, `InventoryTransaction`（入荷・移動・調整もここ） |
| `FoodVault.ShipmentOrders` | `ShipmentOrder`, `ShipmentOrderLine`, `ShipmentAllocation`（引当・確定・取消・出庫取消） |

### 7.2 更新処理

- 複数テーブルの更新は `Ecto.Multi` + `Repo.transact/1`。可変個の明細・ロットは `Enum.reduce` で Multi を積み、ステップ名は文字列で生成する（coding-rules §7）。
- 状態遷移は業務動詞で命名する（`allocate_shipment_order/1` / `ship_shipment_order/1` / `cancel_shipment_order/1` / `reverse_shipment_order/2`）。
- `cast_assoc` は使わない。数量の不変条件は changeset と DB の CHECK 制約の両方で守る。
- 関連ライブラリ: `Ecto.ULID` を提供する依存の追加が必要（`mix.exs` は現状未追加）。

## 付録. ドラフト v1 からの変更点

| # | 変更 | 理由 |
| :-- | :-- | :-- |
| 1 | PK を `BIGINT` の `xxx_id` から ULID の `id` に変更。FK は `{単数}_id` | 方針決定（ULID）／coding-rules §5.1 |
| 2 | DB の `ENUM` を `Ecto.Enum`（string, 小文字 snake_case）に変更 | coding-rules §5.3 |
| 3 | `is_active` を `archived_at` に変更 | coding-rules §14.4（論理削除は `archived_at`） |
| 4 | `created_at` を `inserted_at` に変更。全テーブルに `timestamps` | coding-rules §5.2 / §16.1 |
| 5 | テーブル数の誤記を修正（v1は「全6テーブル」と記載、実際の定義は7テーブル。v2 は明細追加で8テーブル） | v1 は親子テーブルを1項目にまとめており、数が合っていなかった |
| 6 | **`shipment_order_lines` を新設**。引当明細は `order_id` ではなく明細IDを参照 | v1 は出庫オーダーに商品・要求数が無く、取消・再引当・不足判定ができなかった |
| 7 | `shipment_orders.external_slip_id`（部分ユニーク）を追加 | 発送システムのAPIが送る `external_slip_id` の保存先が無く、冪等性が担保できなかった |
| 8 | 受払履歴の `reference_id`（無型の関連ID）を `shipment_order_id`（FK）＋ `transfer_id` に分割。`note` を追加 | 移動には出庫オーダーが無く、移動出庫/入庫のペアも結べなかった |
| 9 | 受払履歴に `ship_reverse`、オーダーに `reversed` を追加 | 発送設計書の「梱包後の取消調整」を実現する手段が在庫側に無かった |
| 10 | 出庫確定・引当解除・出庫取消のロジックを本書に追加（v1 は発送設計書にのみ記載） | 在庫側の責務であり、ケース引当分の減算が漏れていた |
| 11 | `min_expiration_date` を最初から引当仕様に組み込み（発送設計書の「改修」節を廃止）。出庫可能期限を `GREATEST` で定義 | 新規開発に「改修前/後」は不要。v1 は「期限切れでないもの」の定義が曖昧だった |
| 12 | 荷崩しを「1ケースずつ繰り返し」「取消でも元に戻さない」と明記。同一ロットの引当を1行に集約 | v1 は「通常1ケース」と曖昧で、取消時の扱いが未定義だった |
| 13 | 倉庫間移動を「ロットID指定＋同一ロット内で自動荷崩し」に確定 | v1 は「荷崩しするか、保有数チェックするか」「（または自動引当）」が未決だった |
| 14 | ロック順序、CHECK 制約、入数変更禁止、期限なし（`9999-12-31`）、荷まとめなしを明記 | v1 は「単一トランザクション」のみで二重引当・不整合の防止策が無かった |
| 15 | 外部API仕様（認証・エラー応答・冪等性）を本書へ移し、パスを REST 形式（`/api/v1/shipment_orders`）に変更 | 提供側が仕様を持つべき。v1 は在庫不足のレスポンスが未定義 |
| 16 | 技術基盤・画面構成・実装方針・未決事項を追加 | 実際のリポジトリ構成（`food_vault`/`food_ship`、Docker）に合わせた |
