## 1. システム概要と基本方針

食品特有の「消費期限・賞味期限管理」および「荷姿（ケース・バラ）管理」に対応した、複数倉庫向けの在庫管理システム。

### 1.1 コア要件

| 項目 | 決定仕様 | 備考 |
| :-- | :-- | :-- |
| 在庫管理単位 | **ケース数** と **バラ数** を分けて独立管理 | 画面・帳票では「総バラ数」も併記する（[§4.8](#48-画面入出力における総バラ数の表示仕様)） |
| ケース入数 | 商品マスタに **固定値** として保持 | 総バラ数 ＝ ケース数 × 入数 ＋ バラ数。**ロットが1件でも存在する商品は入数の変更を禁止**する |
| 先出し基準 | **第1優先：期限日（昇順）→ 第2優先：入荷日（昇順）→ 第3優先：ロットID（昇順）** | FEFO ＋ FIFO のハイブリッド。第3優先で順序を一意にする |
| 期限管理区分 | 商品マスタで「消費期限」「賞味期限」「管理なし」を区分 | 期限アラート通知は将来拡張。**本バージョンでは関連カラムも作らない**（機能の設計時にマイグレーションで追加する） |
| 出庫引当方式 | **自動引当（荷姿厳守＋期限順）** | 将来「自動引当＋ピッキング実績消し込み」へ拡張できる構造（引当と実績のロット逆転は起こらない前提） |
| 荷崩し | **完全自動** | バラ不足時、システムが古いロットのケースを1ケースずつ開封して引き当てる（[§4.2](#42-出庫時の自動引当と自動荷崩し)） |
| 最低許容期限 | 出庫引当の入力として **任意の `min_expiration_date`** を受け付ける | 発送システムの「出荷期限ルール」を実現する。**新規開発のため「改修」ではなく最初から仕様に含める** |
| 複数倉庫 | 出庫時は **オーダー時点で倉庫を指定** | 倉庫間移動は「移動中」状態を持たず **即時反映**。期限日・入荷日はそのまま継承 |
| 認証・認可 | **メール＋パスワードでログイン**。ユーザーは **管理者が登録**（自己登録なし）。ロールは **管理者(`admin`) / 担当者(`staff`) / 閲覧(`viewer`)** の3種 | 操作ごとの権限は [§7.3](#73-認証認可)。発送システムからのAPIは別系統（サービストークン） |

### 1.2 技術基盤

| 項目 | 内容 |
| :-- | :-- |
| スタック | Elixir / Phoenix 1.8 / LiveView / Ecto / PostgreSQL 15 / Tailwind CSS（Docker Compose で起動） |
| アプリ構成 | `food_vault`（本システム）と `food_ship`（発送）は **別プロジェクト・別DB・別コンテナ** |
| アプリ間通信 | `food_ship` → `food_vault` の一方向 HTTP（`Req` 使用）。Erlang クラスタ・DB共有はしない |
| コーディング規約 | [coding-rules.md](../coding-rules.md) に従う（Context + スキーマの2層、Multi による更新など） |

## 2. 共通規約

テーブル定義すべてに適用する。`coding-rules.md` に合わせている。`config/config.exs` の `generators: [timestamp_type: :utc_datetime, binary_id: true]` は、マイグレーションの ID 列を `:binary_id`（PostgreSQL の `uuid` 型）にするために残すが、`binary_id: true` が `phx.gen.*` に生成させるスキーマは **UUID** であって ULID ではない。ULID 化の手順は [§2.1](#21-ulid-基盤の前提) に定める。

| 項目 | 規約 |
| :-- | :-- |
| 主キー | 全テーブル **カラム名 `id`**、型は **ULID**（Ecto 型 `Ecto.ULID`、DB 列は `binary_id`＝`uuid` 型の 16 バイト）。`{App}.Schema` マクロ経由で定義する（coding-rules §5.1）。外部キーは `{参照先単数形}_id`。基盤の前提は [§2.1](#21-ulid-基盤の前提) |
| 列挙型 | DB の ENUM 型は使わず **`Ecto.Enum`（DB列は string）**。値は **小文字 snake_case の atom**（例 `:best_before`）。API の JSON では同じ文字列を使う |
| 日時 | `utc_datetime` で UTC 保存し、表示直前にだけ JST へ変換（coding-rules §16.1）。タイムスタンプは `timestamps(type: :utc_datetime)`。**`date` 型（期限日・入荷日・出庫予定日）は業務日付としてそのまま扱い、タイムゾーン変換しない** |
| 有効/無効 | `is_active` は使わず **`archived_at`（utc_datetime、NULL=有効）** による論理削除。FK は `on_delete: :nothing`（物理削除しない） |
| 期限なし | 期限区分 `none` の商品は `expiration_date = 9999-12-31` で保存する（NULL だとユニーク制約が効かないため）。`min_expiration_date` 付きの引当でも自然に対象になる |
| 数量 | `*_qty` / `*_cases` / `*_pieces` はすべて整数。DB に **CHECK 制約**で 0 以上などの不変条件を持たせる |

### 2.1 ULID 基盤の前提

実装の最初（スキーマを作る前）に次を済ませる。

| 項目 | 決定 |
| :-- | :-- |
| 依存パッケージ | `ecto_ulid`（Hex。`Ecto.ULID` 型を提供）を採用候補とする。**着手時に Elixir 1.20 / Ecto 3.13 でコンパイルとテストが通ることを最初に確認**し、通らない場合は同等の `Ecto.Type`（26 文字の Crockford Base32 ⇔ 16 バイト）を `FoodVault.ULID` として自前実装する（外部インターフェースは変えない） |
| 共通スキーママクロ | `FoodVault.Schema`（`@primary_key {:id, Ecto.ULID, autogenerate: true}` / `@foreign_key_type Ecto.ULID`）を **最初に作る**（coding-rules §5.1） |
| `config.exs` | `generators` の `binary_id: true` は残す（マイグレーション生成を `:binary_id` にするため）。`phx.gen.*` が出す `@primary_key {:id, :binary_id, ...}` は **生成後に `use FoodVault.Schema` へ手で置き換える** |
| `phx.gen.auth` の生成物 | `users` / `users_tokens` のスキーマ・マイグレーション・テストのフィクスチャも同様に ULID 化する。生成物の削減範囲（自己登録・マジックリンク・メール確認の除去）は [§7.3](#73-認証認可) |
| ID の形式検証 | Context の `get_*` は `<<_::208>>`（26 文字）ガードで受ける。API では、パスの ID が不正な形式なら 404 `not_found`、ボディの ID が不正なら 422 `validation_failed`（いずれも 500 にしない） |
| 並び順での使い方 | ULID の `id` 昇順は **同一ミリ秒内の生成順を保証しない**。先出しの第3優先（[§1.1](#11-コア要件)）は「順序を一意にするタイブレーク」としてのみ使い、作成順の意味は持たせない |

## 3. データベース設計

全 **11 テーブル**（マスタ 3、在庫 1、出庫 4、履歴 1、認証 2）で構成する。

| 区分 | テーブル |
| :-- | :-- |
| マスタ | `makers` / `warehouses` / `items` |
| 在庫 | `inventory_lots` |
| 出庫 | `shipment_orders` / `shipment_order_lines` / `shipment_allocations` / `shipment_order_events`（[§3.12](#312-出庫オーダー履歴-shipment_order_events)） |
| 履歴 | `inventory_transactions` |
| 認証 | `users` / `users_tokens`（[§3.10](#310-ユーザー-users)・[§3.11](#311-ユーザートークン-users_tokens)） |

以降の表では、全テーブル共通の `id`（ULID, PK）と `inserted_at` / `updated_at`（`inventory_transactions` と `shipment_order_events` は `inserted_at` のみ）を省略する。索引は [§3.13](#313-索引一覧) にまとめる。

### 3.1 メーカーマスタ (`makers`)

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| メーカーコード | `maker_code` | string | NOT NULL, UNIQUE（社内管理コード等） |
| メーカー名 | `maker_name` | string | NOT NULL |
| アーカイブ日時 | `archived_at` | utc_datetime | NULL可（NULL=有効） |

### 3.2 倉庫マスタ (`warehouses`)

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 倉庫コード | `warehouse_code` | string | NOT NULL, UNIQUE |
| 倉庫名 | `warehouse_name` | string | NOT NULL |
| アーカイブ日時 | `archived_at` | utc_datetime | NULL可（NULL=有効） |

### 3.3 商品マスタ (`items`)

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| メーカーID | `maker_id` | ULID | NOT NULL, FK (`makers.id`) |
| 商品コード | `item_code` | string | NOT NULL, UNIQUE（JANコードや自社品番） |
| 商品名 | `item_name` | string | NOT NULL |
| ケース入数 | `units_per_case` | integer | NOT NULL, CHECK (`>= 1`)。**ロット（在庫0を含む）が存在したら変更不可** |
| 期限区分 | `expiration_type` | Ecto.Enum | NOT NULL。`consumption`(消費期限) / `best_before`(賞味期限) / `none`(管理なし)。**ロット（在庫0を含む）が存在したら変更不可**（`none` のロットは期限日が `9999-12-31` で保存されるため、後から区分を変えると期限の意味が壊れる） |
| アーカイブ日時 | `archived_at` | utc_datetime | NULL可（NULL=有効） |

#### マスタの変更・アーカイブ規則

| 対象 | 規則 |
| :-- | :-- |
| 入数・期限区分の変更 | ロット（在庫0を含む）が1件でもあれば Context で拒否する。**競合対策**: 入荷（[§4.1](#41-入荷)）・出庫引当（[§4.2](#42-出庫時の自動引当と自動荷崩し)）・移動先ロット作成（[§4.6](#46-倉庫間移動即時反映属性継承)）は対象の `items` 行を `FOR SHARE` で読み、マスタ更新は `FOR UPDATE` で読んでから「ロットが無いこと」を検査する。同時に走っても、更新が先ならロット作成が待たされ、ロット作成が先なら更新が拒否される |
| 商品のアーカイブ | その商品の全ロットが `case_qty = 0` かつ `piece_qty = 0` で、`allocated` のオーダー明細に含まれていないときだけ可 |
| 倉庫のアーカイブ | その倉庫の全ロットが同様に在庫0・引当なしのときだけ可 |
| メーカーのアーカイブ | 有効な商品を持たないときだけ可 |
| アーカイブ済みの商品・倉庫・メーカーの扱い | 入荷・出庫引当・移動（元／先）の対象にできない。画面の選択肢と API ⑥⑦ の一覧に出さない。API ① で指定された場合は 422 `validation_failed`（`errors` に `item_id` / `warehouse_id` が `archived` であることを返す）。一覧・履歴の参照は可。出庫取消（[§4.5](#45-出庫取消管理者操作)）は、対象の商品・倉庫がアーカイブ済みなら 409 `invalid_state`（先に復帰させる） |
| 復帰 | `admin` が `archived_at` を NULL に戻す |

### 3.4 在庫ロット (`inventory_lots`)　★システムの心臓部

「倉庫 × 商品 × 期限日 × 入荷日」の粒度で現在庫と引当済数を保持する。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 倉庫ID | `warehouse_id` | ULID | NOT NULL, FK (`warehouses.id`) |
| 商品ID | `item_id` | ULID | NOT NULL, FK (`items.id`) |
| 期限日 | `expiration_date` | date | NOT NULL。消費/賞味期限。管理なしは `9999-12-31` |
| 入荷日 | `received_date` | date | NOT NULL。倉庫間移動時も元の入荷日を維持 |
| 現在ケース数 | `case_qty` | integer | NOT NULL, DEFAULT 0 |
| 現在バラ数 | `piece_qty` | integer | NOT NULL, DEFAULT 0 |
| 引当済ケース数 | `allocated_case_qty` | integer | NOT NULL, DEFAULT 0（出庫待ちロック分） |
| 引当済バラ数 | `allocated_piece_qty` | integer | NOT NULL, DEFAULT 0（出庫待ちロック分） |

- **複合ユニーク**: `UNIQUE (warehouse_id, item_id, expiration_date, received_date)`
- **CHECK 制約**（不変条件）:
  - `case_qty >= 0` かつ `piece_qty >= 0`
  - `0 <= allocated_case_qty <= case_qty`
  - `0 <= allocated_piece_qty <= piece_qty`
- 有効在庫（引当可能数）の計算式:
  - 有効ケース数 = `case_qty - allocated_case_qty`
  - 有効バラ数 = `piece_qty - allocated_piece_qty`
  - 有効総バラ数 = 有効ケース数 × `units_per_case` ＋ 有効バラ数
- **在庫が 0 になったロットも行は削除しない**（受払履歴・引当明細が FK で参照するため）。一覧画面では既定で 0 ロットを非表示にする。
- **バラの自動まとめ（荷まとめ）は行わない**。`piece_qty` が入数以上になっても自動でケースへ換算しない（入荷時の入力値どおり保持）。

### 3.5 出庫オーダー (`shipment_orders`)

出庫指示のヘッダ。1オーダー＝1倉庫・1出庫予定日。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 出庫元倉庫ID | `warehouse_id` | ULID | NOT NULL, FK (`warehouses.id`)。オーダー時点で指定 |
| 出庫予定日 | `shipment_date` | date | NOT NULL |
| ステータス | `status` | Ecto.Enum | NOT NULL, DEFAULT `allocated`。`allocated`(引当済) / `shipped`(出庫完了) / `cancelled`(取消) / `reversed`(出庫取消済)。遷移は [§3.9](#39-ステータス遷移) |
| 連携元伝票ID | `external_slip_id` | string | NULL可。発送システムの伝票ID（冪等性キー）。**部分ユニーク**: `UNIQUE (external_slip_id) WHERE external_slip_id IS NOT NULL AND status <> 'cancelled'` |
| 出庫確定日時 | `shipped_at` | utc_datetime | NULL可 |

> 部分ユニークにするのは、数量変更時に「取消 → 同じ伝票IDで再引当」を許すため。

- 画面で登録するオーダーは `external_slip_id = NULL`。**`external_slip_id` を持つオーダーは発送システム起源**として扱う（画面操作の制限は [§6](#6-画面構成案)・[§7.3](#73-認証認可)）。
- changeset は coding-rules §5.7 に従い、部分ユニークに対応する `unique_constraint`（`name:` に部分ユニーク索引名を指定）と `unsafe_validate_unique`（`query:` で `status != :cancelled` を条件に付ける）を対で書く。ただし API の冪等再送は検証エラーではなく「既存オーダーの返却」として扱う（[§5](#5-外部api仕様発送システム向け)）。
- 作成・確定・取消・出庫取消の **誰が・いつ・なぜ** は [`shipment_order_events`](#312-出庫オーダー履歴-shipment_order_events) に残す（本テーブルは現在の状態のみを持つ）。

### 3.6 出庫オーダー明細 (`shipment_order_lines`)

オーダーが「何を何個要求したか」の記録。取消・再引当・不足判定の根拠になる。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 出庫オーダーID | `shipment_order_id` | ULID | NOT NULL, FK (`shipment_orders.id`) |
| 商品ID | `item_id` | ULID | NOT NULL, FK (`items.id`) |
| 要求ケース数 | `req_cases` | integer | NOT NULL, DEFAULT 0 |
| 要求バラ数 | `req_pieces` | integer | NOT NULL, DEFAULT 0 |
| 最低許容期限日 | `min_expiration_date` | date | NULL可。指定時はこの日以降が期限のロットだけ引当対象 |

- `UNIQUE (shipment_order_id, item_id)`（同一オーダーに同じ商品の明細を重複させない）
- CHECK: `req_cases >= 0`, `req_pieces >= 0`, `req_cases + req_pieces > 0`

### 3.7 出庫引当明細 (`shipment_allocations`)

自動引当の結果（どのロットから何個出すか）。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 出庫オーダー明細ID | `shipment_order_line_id` | ULID | NOT NULL, FK (`shipment_order_lines.id`) |
| 対象ロットID | `lot_id` | ULID | NOT NULL, FK (`inventory_lots.id`) |
| 引当ケース数 | `allocated_cases` | integer | NOT NULL, DEFAULT 0 |
| 引当バラ数 | `allocated_pieces` | integer | NOT NULL, DEFAULT 0 |

- `UNIQUE (shipment_order_line_id, lot_id)`。ケース引当とバラ引当が同じロットに当たった場合は **1行にまとめて加算**する。
- 将来の「ピッキング実績の消し込み」は、その機能の設計時にカラム（ピッキング済フラグ等）を追加する（本バージョンでは未使用のカラムを作らない）。
- CHECK: `allocated_cases >= 0`, `allocated_pieces >= 0`, `allocated_cases + allocated_pieces > 0`

### 3.8 在庫受払履歴 (`inventory_transactions`)

すべての **現在庫の変動**（入荷・出庫・荷崩し・移動・調整）の証跡ログ。追記のみ（UPDATE / DELETE しない）。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| ロットID | `lot_id` | ULID | NOT NULL, FK (`inventory_lots.id`) |
| 処理区分 | `transaction_type` | Ecto.Enum | NOT NULL。下表 |
| 変動ケース数 | `case_diff` | integer | NOT NULL。増減値（荷崩しなら `-1`） |
| 変動バラ数 | `piece_diff` | integer | NOT NULL。増減値（入数10の荷崩しなら `+10`） |
| 出庫オーダーID | `shipment_order_id` | ULID | NULL可, FK (`shipment_orders.id`)。出庫・荷崩し・出庫取消で設定 |
| 移動ID | `transfer_id` | ULID | NULL可。移動出庫と移動入庫のペアを結ぶ（アプリ側で `Ecto.ULID.generate()`） |
| 備考 | `note` | string | NULL可。調整・出庫取消では理由を必須とする |
| 操作ユーザーID | `user_id` | ULID | NULL可, FK (`users.id`)。画面操作では必ず設定。**NULL＝発送システムからのAPI操作** |
| API操作者 | `operator` | string | NULL可（最大255文字）。API 操作で発送システムが渡す操作者の識別子（発送側ユーザーのメール等）。画面操作では NULL。CHECK: `user_id IS NOT NULL OR operator IS NOT NULL`（誰の操作かが必ず残る） |

| `transaction_type` | 意味 | 変動の向き |
| :-- | :-- | :-- |
| `receive` | 入荷 | ＋ |
| `ship` | 出庫確定 | － |
| `ship_reverse` | 出庫取消（出庫確定の巻き戻し） | ＋ |
| `auto_break` | 自動荷崩し（**1ロット・1オーダー（または1移動）につき1行**。複数ケースを開封しても合算する） | ケース－／バラ＋ |
| `transfer_out` | 移動出庫 | － |
| `transfer_in` | 移動入庫 | ＋ |
| `adjust` | 棚卸調整・廃棄 | ＋／－ |

> **引当・引当解除は在庫の増減ではないため受払履歴に記録しない**（記録は `shipment_allocations` と、状態遷移の履歴 [`shipment_order_events`](#312-出庫オーダー履歴-shipment_order_events) が担う）。

- `transfer_id` は参照先テーブルを持たない ULID のため、1回の移動で `transfer_out`（と必要なら `auto_break`）と `transfer_in` が **必ず同一トランザクションで対として記録される**ことをアプリ層とテストで担保する。

### 3.9 ステータス遷移

```
allocated ──出庫確定──▶ shipped ──出庫取消（管理者）──▶ reversed
    │
    └──取消──▶ cancelled
```

- `shipped` / `cancelled` / `reversed` からは他のステータスへ戻れない。
- 取消できるのは `allocated` のみ。`shipped` を戻す場合は出庫取消（[§4.5](#45-出庫取消管理者操作)）を使う。
- 各遷移（作成・出庫確定・取消・出庫取消）は `shipment_order_events` に同一トランザクションで記録する。

### 3.10 ユーザー (`users`)

画面にログインする担当者。管理者が登録し、本人による自己登録は行わない。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| メールアドレス | `email` | citext | NOT NULL, UNIQUE（大文字小文字を区別しない）。ログインID |
| 氏名 | `name` | string | NOT NULL |
| パスワード（ハッシュ） | `hashed_password` | string | NOT NULL, `redact: true`。平文は保存・ログ出力しない |
| ロール | `role` | Ecto.Enum | NOT NULL, DEFAULT `viewer`。`admin`(管理者) / `staff`(担当者) / `viewer`(閲覧) |
| 要パスワード変更 | `must_change_password` | boolean | NOT NULL, DEFAULT true。管理者が初期/再設定したパスワードでログインした直後は変更画面へ強制遷移 |
| アーカイブ日時 | `archived_at` | utc_datetime | NULL可（NULL=有効）。**アーカイブ済みユーザーはログイン不可** |

- 仮想フィールド `password` / `current_password` は `virtual: true, redact: true`。スキーマに `@derive {Inspect, only: [...]}` を付ける（coding-rules §5.4）。
- ロールの既定値を最小権限の `viewer` にするのは、ロール指定漏れで書き込み権限が付かないようにするため。

### 3.11 ユーザートークン (`users_tokens`)

ログインセッションの管理（`phx.gen.auth` 生成物）。本バージョンで使うのは `session` のみ。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| ユーザーID | `user_id` | ULID | NOT NULL, FK (`users.id`) |
| トークン | `token` | binary | NOT NULL |
| 用途 | `context` | string | NOT NULL。`session` |

- `UNIQUE (context, token)`。`inserted_at` のみ（`updated_at: false`）。セッション有効期間は `inserted_at` から判定する。
- **パスワード変更・ロール変更・アーカイブ時は、そのユーザーの全セッショントークンを削除**する（変更が即時に反映され、他端末のセッションも切れる）。

### 3.12 出庫オーダー履歴 (`shipment_order_events`)

出庫オーダーの状態遷移の証跡。追記のみ（UPDATE / DELETE しない）。`inserted_at` のみ持つ。オーダーの状態更新と **同じ `Ecto.Multi` で INSERT** する。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |

- 冪等な再送（すでにその状態で 200 を返す場合）では、イベントを **追加しない**。

## 4. コア業務ロジック仕様

すべて **単一トランザクション**（`Ecto.Multi` + `Repo.transact/1`）で処理し、途中で失敗したら全体をロールバックする。

### 4.0 共通ルール

- **ロック**: 対象ロットは `SELECT ... FOR UPDATE` で取得してから更新する（二重引当の防止）。デッドロックを防ぐため、**全操作共通のロックキー `(warehouse_id, item_id, expiration_date, received_date, id)` の昇順**で、次の順序・単位を守る。
  1. 先に `items` 行を `item_id` 昇順で `FOR SHARE`（[§3.3](#33-商品マスタ-items) のマスタ変更との競合対策）。
  2. 次に、その操作で触る **ロット全体を 1 回のクエリ（`ORDER BY` ＋ `FOR UPDATE`）でまとめて**ロックする。操作の途中で追加のロットをロックしない。
  3. 出庫引当は、明細（lines）を **`item_id` 昇順に並べ替えてから**処理する（複数明細で商品の順序が呼び出しごとに違っても、ロック順は同じになる）。
  4. 出庫確定・引当解除・出庫取消は、引当明細の `lot_id` をまとめて 1 クエリでロックする。倉庫間移動は [§4.6](#46-倉庫間移動即時反映属性継承) のとおり。
- **出庫可能期限**: 出庫引当の対象は `expiration_date >= GREATEST(shipment_date, COALESCE(min_expiration_date, shipment_date))` のロット。`min_expiration_date` が出庫予定日より前でも期限切れ在庫は引き当てない。
- **ソート順（先出し）**: `ORDER BY expiration_date ASC, received_date ASC, id ASC`

### 4.1 入荷

入力: 倉庫・商品・（期限日）・入荷日・ケース数・バラ数。

0. 倉庫・商品が有効（`archived_at` が NULL）であることを検証し、`items` 行を `FOR SHARE` で読む。
1. 期限区分が `none` 以外の商品は期限日を必須とする。`none` の場合は `9999-12-31` を設定。
2. 「同じ倉庫 × 商品 × 期限日 × 入荷日」のロットがあれば加算、なければ新規作成（`INSERT ... ON CONFLICT ... DO UPDATE` で原子的に加算）。
3. 受払履歴に `receive` を記録。

### 4.2 出庫時の自動引当と自動荷崩し

入力: 出庫倉庫・出庫予定日・明細（商品・`req_cases`・`req_pieces`・任意の `min_expiration_date`）・任意の `external_slip_id`・操作者（画面は `user`、API は `operator`）。

事前処理:

- **冪等チェック（API）**: `external_slip_id` があり、`cancelled` 以外の同一伝票IDのオーダーがあれば、新規作成せず [§5](#5-外部api仕様発送システム向け) の冪等ルール（内容が一致すれば既存を返す／不一致は 409）で応答する。
- 倉庫・商品が有効であることを検証し、`items` 行を `item_id` 昇順で `FOR SHARE`。明細を `item_id` 昇順に並べ替える（同一オーダー内に同じ商品の明細は不可）。

明細ごとに以下を行う。

1. **対象ロットの取得**: 指定倉庫・商品のロットのうち、[§4.0](#40-共通ルール) の出庫可能期限を満たすものを先出し順に取得（`FOR UPDATE`）。
2. **ステップ1 ケース要求分 (`req_cases`)**: ロットを上から走査し、有効ケース数 > 0 のロットから `req_cases` を満たすまで引き当てる（`allocated_case_qty` 加算、引当明細に加算）。有効ケース数の合計が足りなければ「ケース在庫不足」としてその明細の不足数を記録する。
3. **ステップ2 バラ要求分 (`req_pieces`)**: ロットを上から走査し、`req_pieces` が 0 になるまで次を繰り返す。
   1. **既存の有効バラから引当**: 有効バラ数 > 0 なら可能な限り引き当てる。
   2. **同一ロット内で自動荷崩し**: まだ要求が残り、そのロットの **有効ケース数 > 0** なら、荷崩しする。開封するケース数は **算術で一度に求める**: `k = min(有効ケース数, ceil(残り要求バラ数 ÷ units_per_case))`。ロットを 1 回の UPDATE で `case_qty - k`・`piece_qty + k × units_per_case` とし、受払履歴に `auto_break` を **1 行**（`case_diff = -k`, `piece_diff = +k × units_per_case`）記録する。結果は「1ケースずつ開封して繰り返す」場合と同じ。開封で増えたバラから引き当てる。
   3. それでも足りなければ **次のロット**へ進み、(a)(b) を行う。
4. 全ロットを走査しても `req_pieces` が残る場合は「バラ在庫不足」としてその明細の不足数を記録する。
5. 引当結果を `shipment_allocations` に保存（同一ロットは1行に加算）。

全明細の処理後:

6. **不足が 1 つでもあれば全体をロールバック**する（荷崩しも含めて全て元に戻る）。応答の `shortages` には、**不足した全明細分**（後続の明細の不足も含む）を返す。
7. 不足が無ければオーダー（`allocated`）・明細・引当明細・受払履歴（荷崩し）・オーダー履歴（`created`）を保存してコミット。

補足:
- ステップ1で引き当てたケースは「引当済」のため、ステップ2の荷崩し対象にならない（有効ケース数で判定するため）。
- 荷崩しで余ったバラは、引当てずにそのロットのバラ在庫として残る。
- **荷崩しは出庫取消・引当解除でも元に戻さない**（開封済みのケースはバラ在庫のまま）。バラが累積してケース出庫に支障が出る場合は、棚卸調整で荷まとめを行う（[§4.7](#47-棚卸調整廃棄入荷訂正荷まとめ)）。

### 4.3 出庫確定

`allocated` のオーダーを `shipped` にする。

1. 引当明細のロットを、[§4.0](#40-共通ルール) のロックキー順に **1 クエリでまとめて**ロックする。
2. 引当明細ごとに、ロットの `case_qty` / `allocated_case_qty` を `allocated_cases` 分、`piece_qty` / `allocated_piece_qty` を `allocated_pieces` 分それぞれ減算。
3. 受払履歴に `ship`（ロット単位）を記録。
4. オーダーを `shipped`、`shipped_at` を現在時刻に更新し、オーダー履歴に `shipped` を記録（画面の緊急操作では `reason` 必須、[§7.3](#73-認証認可)）。

### 4.4 引当解除（取消）

`allocated` のオーダーを `cancelled` にする。

1. 引当明細のロットを [§4.0](#40-共通ルール) のロックキー順に 1 クエリでロックし、`allocated_case_qty` / `allocated_piece_qty` を引当分だけ減算（現在庫は変えない）。
2. オーダーを `cancelled` に更新し、オーダー履歴に `cancelled` を記録（誰が・いつ・理由。画面の緊急操作では `reason` 必須）。引当明細は **削除せず残す**（何を引き当てていたかの証跡）。
3. 数量変更は「取消 → 新規引当」の2操作で行う（呼び出し側が連続実行）。

### 4.5 出庫取消（管理者操作）

誤操作で `shipped` にしたオーダーを戻す。**管理者のみ**。本システムの画面からは `admin` ロールのみ実行可（[§7.3](#73-認証認可)）。

**API 経由の場合**、在庫側は呼び出したユーザーのロールを判定できない。次のとおり責任を分ける。
- 管理者かどうかの判定は呼び出し側（発送システムの権限表）の責任。
- 在庫側は **`operator`（発送側の操作者）と `reason` を必須**とし、欠けていれば 422。両方をオーダー履歴と受払履歴に残す（誰が取り消したかを在庫側でも追跡できる）。
- 呼び出し元の認証はサービストークン（[§5](#5-外部api仕様発送システム向け)）で保護する。

1. 対象の商品・倉庫がアーカイブ済みなら 409 `invalid_state`。引当明細のロットを [§4.0](#40-共通ルール) のロックキー順に 1 クエリでロックし、`case_qty` / `piece_qty` を引当分だけ **加算**（引当済数は変えない＝ロックは戻さない）。
2. 受払履歴に `ship_reverse` を記録（`note` に理由を必須入力、API 操作は `operator` も記録）。
3. オーダーを `reversed` に更新し、オーダー履歴に `reversed`（理由必須）を記録。

### 4.6 倉庫間移動（即時反映・属性継承）

入力: 移動元倉庫・移動先倉庫・**対象ロット（ロットID指定）**・移動ケース数・移動バラ数。

事前処理:
- 移動元と移動先が同じ倉庫の場合は拒否。双方の倉庫と商品が有効であること。`items` 行を `FOR SHARE`。
- **移動先ロットを先に確保**する（`INSERT ... ON CONFLICT DO NOTHING`、数量 0。同じ商品 × `expiration_date` × `received_date`）。そのうえで **移動元・移動先の 2 ロットを [§4.0](#40-共通ルール) のロックキー順に 1 クエリでロック**してから減算・加算する（A→B と B→A の移動が同時に走ってもデッドロックしない）。

1. **移動元ロットの減算**: 有効在庫（現在庫 − 引当済）の範囲で減算する。バラが不足し、そのロットの有効ケースがあれば、出庫時と同様に **同一ロット内で自動荷崩し** してから減算する。受払履歴に `transfer_out`（荷崩しは `auto_break`）を記録。
2. **移動先ロットへの加算**: 事前に確保した移動先ロット（移動先倉庫の「同じ商品 × 同じ `expiration_date` × 同じ `received_date`」）へ加算する。受払履歴に `transfer_in` を記録。
3. 移動出庫と移動入庫には同じ `transfer_id` を付ける（対として必ず同一トランザクションで記録、[§3.8](#38-在庫受払履歴-inventory_transactions)）。

> 「自動引当による移動対象ロットの自動選択」は将来拡張とし、本バージョンでは対象外。

### 4.7 棚卸調整・廃棄・入荷訂正・荷まとめ

ロットを指定し、ケース数・バラ数の増減を登録する（`admin` のみ）。有効在庫（現在庫 − 引当済）を下回る減算は不可。受払履歴に `adjust`（理由を `note` に必須入力）を記録。次の運用はすべて本機能で行う。

| 運用 | 方法 |
| :-- | :-- |
| 入荷の誤入力の訂正 | 入荷登録は `staff` 以上だが、**訂正は `admin` の棚卸調整に集約**する（受払履歴を `receive` → `adjust` の2行で追えるようにし、取消機能を別に持たない）。ケース数・バラ数の誤りは増減で、期限日・入荷日の誤りは「誤ったロットの全数を減算 → 正しい期限日・入荷日で再入荷」で直す |
| 荷まとめ（バラ → ケース） | 荷崩しで累積したバラをケースに戻すときは、`case_diff = +k`・`piece_diff = -k × units_per_case` を **1回の調整**として登録する（有効バラ数が `k × units_per_case` 以上であること）。理由に「荷まとめ」を記入する |
| 実在庫が引当済数を下回る場合（紛失・破損） | 有効在庫を下回る減算は不可のため、`admin` が対象ロットを引き当てているオーダー（ロット詳細に表示。`shipment_allocations(lot_id)` で検索）の引当を **緊急操作として解除**してから調整する（[§7.3](#73-認証認可)）。発送システム起源のオーダーを解除した場合は、発送側で再引当が必要になる |

### 4.8 画面入出力における「総バラ数」の表示仕様

- **入力時**: 入荷・出庫・移動のすべての画面で `[ケース数]` と `[バラ数]` の2入力欄を設ける。商品マスタの `units_per_case` を参照し、入力と同時に **総数：〇〇 個** をリアルタイム表示する。
- **一覧表示時**: 在庫一覧では、ロット単位・商品単位の集計行に常に `ケース数 ｜ バラ数 ｜ 総バラ数（ケース×入数＋バラ）` の3列をセットで表示する。
- 総バラ数の計算は Web 層・テンプレートに書かず、`FoodVault.Utils.Calc` に集約する（coding-rules §10.7, §16.2）。

## 5. 外部API仕様（発送システム向け）

- 提供側は本システム。LiveView 対象外の JSON API なので、Controller（`FoodVaultWeb.Api.V1.*`）と `:api` pipeline で実装する。
- **認証**: `Authorization: Bearer <token>` による共有シークレット（**サービス間認証**。画面ユーザーのログインとは別系統）。
  - トークンは `runtime.exs` の環境変数 `INVENTORY_API_TOKENS`（カンマ区切り・**複数可**）から読み、未設定なら起動時に落とす（coding-rules §13）。比較は `Plug.Crypto.secure_compare/2`（定数時間）。トークンの値をログに出さない。
  - **ローテーション**: 新トークンを追加（旧と併存）→ 発送側の設定を切り替え → 旧トークンを削除、の順で、無停止で入れ替える。
  - **公開範囲**: API は画面と同じ Endpoint・ポートで動く。本番ではリバースプロキシで TLS を終端し、`/api` を発送システムの送信元（社内ネットワーク）に限定する。開発時の Compose 内通信（`http://food_vault_web:4000`）は内部ネットワークのみ。
- **操作者**: 状態を変える API（①②③④）は **`operator`（string、最大255文字）を必須**とし、受払履歴とオーダー履歴に残す（[§3.8](#38-在庫受払履歴-inventory_transactions)・[§3.12](#312-出庫オーダー履歴-shipment_order_events)）。発送システムは操作した画面ユーザーのメール等を渡す（CSV 取込は取り込んだユーザー）。
- **ベースパス**: `/api/v1`。ID はすべて ULID 文字列（形式不正は [§2.1](#21-ulid-基盤の前提)）。日付は ISO 8601（`YYYY-MM-DD`）。列挙値は小文字 snake_case 文字列。
- **冪等性**:
  - ① 同じ `external_slip_id`（`cancelled` 以外）での再送は、**要求内容が既存オーダーと一致する場合に限り**、再処理せず既存オーダーを返す（200）。一致の判定は `warehouse_id`・`shipment_date`・各明細の（`item_id`・`req_cases`・`req_pieces`・`min_expiration_date`）の比較（明細は `item_id` 順に正規化）。**不一致は 409 `idempotency_conflict`**（古い内容のオーダーを成功として返さない）。
  - 同じ `external_slip_id` の同時 POST でユニーク制約違反になった側は、500 にせず既存オーダーを再取得して上記の比較を行う。
  - ②③④ はすでにその状態なら 200 で現状を返す（②`shipped`、③`cancelled`、④`reversed`）。それ以外の状態からは 409 `invalid_state`。冪等応答ではオーダー履歴・受払履歴を追加しない。
- **エラー形式**: 全エンドポイント共通で `{ "error": "<code>", "message": "<説明>", ...付加情報 }`。`FoodVaultWeb.Api.FallbackController` で統一し、`ErrorJSON` の既定形式（`%{errors: %{detail: ...}}`）は API では使わない。不正な ID・存在しないルートも同じ形式で返す。

### エラー応答

```json
{ "error": "insufficient_stock", "shortages": [{ "item_id": "01JC...", "shortage_cases": 0, "shortage_pieces": 2 }] }
```

| HTTP | `error` | 発生条件 | 発送システム側の扱い |
| :-- | :-- | :-- | :-- |
| 401 | `unauthorized` | トークン不正 | 設定エラーとして通知（リトライ不可） |
| 404 | `not_found` | オーダー・倉庫・商品が存在しない（パスの ID の形式不正を含む） | 不整合として通知 |
| 409 | `invalid_state` | 状態遷移として不正（例：`cancelled` の出庫確定）。出庫取消で対象の商品・倉庫がアーカイブ済みの場合も | 画面を再読込して最新状態を表示 |
| 409 | `idempotency_conflict` | 同じ `external_slip_id` の既存オーダーと要求内容が異なる（[冪等性](#5-外部api仕様発送システム向け)）。応答に既存の `order_id` と `status` を含む | 既存オーダーを照会し、解除してから再引当（古い内容を成功として扱わない） |
| 422 | `insufficient_stock` | 期限条件を満たす在庫が不足（ロールバック済み。オーダーは作られない）。`shortages` は不足した **全明細分** | 伝票を `shortage` で保存 |
| 422 | `validation_failed` | 入力不正（数量が負、明細が空、`operator` 欠落、ボディの ID の形式不正、アーカイブ済みの商品・倉庫など）。`errors` に項目別メッセージ | 入力エラーとして表示 |

## 7. 実装方針

### 7.1 Context とスキーマ（coding-rules §2.1：Context + スキーマの2層、子エンティティ専用 Context は作らない）

| Context | スキーマ（集約） |
| :-- | :-- |
| `FoodVault.Accounts` | `User`, `UserToken`（認証・ユーザー管理。[§7.3](#73-認証認可)） |
| `FoodVault.Makers` | `Maker` |
| `FoodVault.Warehouses` | `Warehouse` |
| `FoodVault.Items` | `Item` |
| `FoodVault.Inventories` | `InventoryLot`, `InventoryTransaction`（入荷・移動・調整もここ） |
| `FoodVault.ShipmentOrders` | `ShipmentOrder`, `ShipmentOrderLine`, `ShipmentAllocation`, `ShipmentOrderEvent`（引当・確定・取消・出庫取消。ロットの更新は `Inventories` の公開関数を経由せず、ロックと一括更新のため同一 Multi 内で行う） |

### 7.2 更新処理

- 複数テーブルの更新は `Ecto.Multi` + `Repo.transact/1`。可変個の明細・ロットは `Enum.reduce` で Multi を積み、ステップ名は文字列で生成する（coding-rules §7）。
- 状態遷移は業務動詞で命名する（`allocate_shipment_order/1` / `ship_shipment_order/1` / `cancel_shipment_order/1` / `reverse_shipment_order/2`）。
- `cast_assoc` は使わない。数量の不変条件は changeset と DB の CHECK 制約の両方で守る。
- 関連ライブラリ: ULID の依存（`ecto_ulid` を候補。採否と自前実装への切替は [§2.1](#21-ulid-基盤の前提)）。`mix.exs` は現状未追加。
- 書き込み関数は **操作者を第1引数に取る**。画面は `user`（例 `receive_stock(user, attrs)`）で受払履歴・オーダー履歴の `user_id` に、API は `{:api, operator}` を渡して `operator` に記録する。

### 7.3 認証・認可

#### 方式

- Phoenix 1.8 の `mix phx.gen.auth`（`FoodVault.Accounts` / `FoodVaultWeb.UserAuth`）をベースにする。生成物から **自己登録・マジックリンク・メール確認を取り除き、パスワード認証のみ**にする。
- 現在ユーザーは Phoenix 1.8 の `current_scope`（`current_scope.user`）で扱い、`<Layouts.app current_scope={@current_scope} ...>` に渡す（`food_vault/AGENTS.md` の指示に従う）。coding-rules §11.3 の `current_user` は `current_scope.user` と読み替える。
- パスワードは bcrypt でハッシュ化。最小12文字（`phx.gen.auth` の既定）。ログイン失敗時のエラーは「メールアドレスまたはパスワードが正しくありません。」の1種類にし、存在有無を漏らさない。
- パスワード再設定は **管理者が再設定する運用**（メール送信基盤を本バージョンでは使わない）。再設定後は `must_change_password = true`。

#### ユーザー管理ルール

- ユーザーの作成・ロール変更・パスワード再設定・アーカイブは `admin` のみ。
- **有効な `admin` を常に1人以上残す**。最後の `admin` のロール降格・アーカイブは Context で拒否する。**自分自身のロール変更・アーカイブも不可**。
- アーカイブ済みユーザーのメールアドレスは再利用不可（`email` の UNIQUE のため）。復帰は `archived_at` を NULL に戻す。
- 初期管理者は seeds（開発）／リリースタスク（本番）で作成。初期パスワードは `runtime.exs` 経由の環境変数から読み、作成後に `must_change_password = true` とする。

#### 権限表

| 操作 | `admin` | `staff` | `viewer` |
| :-- | :--: | :--: | :--: |
| 在庫一覧・受払履歴・出庫オーダー・マスタの参照 | ○ | ○ | ○ |
| 自分のパスワード変更 | ○ | ○ | ○ |
| 入荷登録 | ○ | ○ | － |
| 画面登録オーダーの登録（自動引当）・出庫確定・引当解除 | ○ | ○ | － |
| 発送システム起源オーダーの確定・引当解除（**緊急操作**。理由必須・警告表示） | ○ | － | － |
| 倉庫間移動 | ○ | ○ | － |
| 棚卸調整・廃棄・入荷訂正・荷まとめ | ○ | － | － |
| 出庫取消（`shipped` → `reversed`） | ○ | － | － |
| マスタ（メーカー・倉庫・商品）の編集・アーカイブ | ○ | － | － |
| ユーザー管理 | ○ | － | － |

- 判定は **`FoodVault.Utils.Permission.can?(user, action)`** に一本化する（ステートレスな関数モジュール）。この権限表と1対1に対応させ、ボタンの表示とイベント処理の両方で同じ関数を呼ぶ。
- 上位ロールは下位ロールの操作を含む（`admin` ⊃ `staff` ⊃ `viewer`）。

#### 認可の実装（coding-rules §8.3 / §11 に従う）

| 層 | 実装 |
| :-- | :-- |
| ① HTTP plug | `require_authenticated_user`（全ロール）／`require_authenticated_admin_user`（`admin`） |
| ② LiveView `on_mount` | `:ensure_authenticated`（全ロール）／`:ensure_authenticated_staff`（`staff` 以上）／`:ensure_authenticated_admin`（`admin`）。**plug と同じ強さのフックを `live_session` に必ず指定**する（LiveView 間遷移は plug を通らないため） |
| ③ イベント単位 | 同一画面に複数ロールが入る画面（出庫オーダー詳細など）は、`handle_event` の先頭で `Permission.can?/2` を検査し、不許可なら `put_flash(:error, "権限がありません。")`。**テンプレートの `:if` だけで隠さない**（coding-rules §11.5） |

- ルーティング: 参照・業務画面は `/inventory_lots` 等の一般パス、`admin` 専用画面（棚卸調整・マスタ編集・ユーザー管理）は `/management/...`、認証系は `/users/log_in` 等（coding-rules §8.4）。
- 未ログインでの API 以外へのアクセスはログイン画面へ。ログイン後は元のページへ戻す。
- **API（`/api/v1`）は本節の対象外**。サービストークンで認証し、画面ユーザーのセッションとは分離する（[§5](#5-外部api仕様発送システム向け)）。
- 監査: ログイン成功・失敗は Logger カテゴリ `:log_in` で記録し、書き込み操作は操作ログに操作ユーザーを含める（coding-rules §12。未導入のため併せて実装する）。**業務上の証跡は DB（`inventory_transactions` と `shipment_order_events`）が担い**、Logger は補助とする（ログのローテーション後も誰がいつ何をしたかを追えるようにするため）。パスワード等は `redact: true` により自動マスクされる。
