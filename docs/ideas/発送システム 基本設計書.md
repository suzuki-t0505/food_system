# 発送システム 基本設計書（ドラフト v2.1）

- 対象アプリ: `food_ship`（Phoenix / LiveView、開発時ポート 4001、DB `food_ship_dev`）
- 連携先: 在庫管理システム `food_vault`（別アプリ・別DB）。**API の提供側仕様は在庫側設計書が正**（本書は呼び出し側の仕様のみを持つ）
- 関連文書: [食品在庫管理システム設計.md](食品在庫管理システム設計.md)、[coding-rules.md](../coding-rules.md)
- 状態: ドラフト（`docs/ideas/`）。正式版への昇格は別途承認を得て行う

---

## 1. システム概要と基本方針

発注元（EC・百貨店など）から順不同で届く出荷伝票（紙・FAX・PDF・CSV）を一元管理し、出荷予定日順の作業指示・梱包管理を行う。あわせて、在庫管理システムと API 連携して期限管理（FEFO）に沿った引当と在庫減算を自動化する。

### 1.1 コア要件

| 項目 | 決定仕様 | 備考 |
| :-- | :-- | :-- |
| システム構成 | 発送システム専用の DB を持ち、在庫管理システムとは **API 連携**で疎結合にする | 自動荷崩し・受払履歴などの在庫ロジックを二重実装しないため |
| 対象倉庫 | **特定の1倉庫に固定**。倉庫IDは設定値（`runtime.exs`）として保持 | 画面での倉庫選択は省略。倉庫IDは在庫側の `GET /api/v1/warehouses` で確認して設定する |
| 伝票の粒度 | **1伝票 ＝ 1発注元 × 1商品 × 1出荷予定日**。在庫側には **1伝票 ＝ 1出庫オーダー（1明細）** として引き当てる | 複数商品の紙伝票は商品ごとに複数行として入力する |
| 伝票入力方法 | 画面の手入力（紙・FAX・PDF を見ながら）と **CSV 一括取込** | CSV は1行＝1伝票（[§5.1](#51-伝票登録手入力csv)） |
| 順不同伝票の管理 | 受付日ではなく **出荷予定日** を軸にソート・グルーピング表示 | 梱包完了後に追加の伝票が届いても、未梱包分だけを識別できる |
| 数量・箱数の換算 | 商品ごとに「1件あたり標準箱数・商品数量（バラ数）」をマスタ化 | 基本は 1件＝1箱＝1個、一部 1件＝3箱＝3個。**箱数は手修正可、商品数量（バラ数）は手修正不可** |
| 在庫要求単位 | 在庫側へは常に **バラ数**（`req_pieces`、`req_cases = 0`） | バラ不足時のケース開封は在庫側の自動荷崩しに一任 |
| 出荷期限ルール | 「発注元 × 商品」ごとに出荷予定日からの最低残日数を定義 | 算出した最低許容期限日を `min_expiration_date` として在庫側へ渡し、先出し（FEFO）で引当 |
| 在庫減算のタイミング | ① 伝票登録時: 引当（仮押さえ）と在庫不足チェック　② 梱包完了時: 出庫確定で実在庫を減算 | 入力時点の欠品検知と、梱包完了時の確実な減算を両立 |
| トータルピック・帳票 | 引当後、**出荷予定日 × 発注元 × メーカー**ごとに伝票を束ねて「トータルピック」を作成し、**トータルピック表**と**伝票ごとの作業指示書**を PDF で出力 | メーカーは在庫側メーカーID で特定（[§3.2](#32-発送商品梱包換算マスタ-shipping_items)、[§5.2](#52-トータルピックの作成と作業指示書の出力)） |
| 認証・認可 | メール＋パスワードでログイン。ユーザーは管理者が登録。ロールは **管理者 / 担当者 / 閲覧** | 在庫側と同じ方式・別ユーザー管理（[§7](#7-認証認可)） |

### 1.2 技術基盤

| 項目 | 内容 |
| :-- | :-- |
| スタック | Elixir / Phoenix 1.8 / LiveView / Ecto / PostgreSQL 15 / Tailwind CSS（Docker Compose） |
| 連携方式 | `food_ship` → `food_vault` の一方向 HTTP（`Req`）。Compose 内のベース URL は `http://food_vault_web:4000` |
| コーディング規約 | [coding-rules.md](../coding-rules.md) に従う |

## 2. 共通規約

在庫側設計書 [§2](食品在庫管理システム設計.md) と同じ。要点のみ再掲する。

| 項目 | 規約 |
| :-- | :-- |
| 主キー | 全テーブル **`id`（ULID）**。外部キーは `{単数}_id`。在庫側のIDを保持する列は FK にせず ULID として保存（別DBのため） |
| 列挙型 | `Ecto.Enum`（string）、値は小文字 snake_case。在庫側 API の JSON とも同じ表記 |
| 日時 | `utc_datetime` で UTC 保存、表示時に JST 変換。`date` 型（出荷予定日など）は業務日付としてそのまま扱う |
| 有効/無効 | マスタは `archived_at`（NULL=有効）による論理削除 |
| 数量 | 整数。DB に CHECK 制約を置く |

## 3. データベース設計（発送システム専用DB）

全 **8 テーブル**（マスタ 3、伝票・ピック 3、認証 2）で構成する。以降の表では全テーブル共通の `id`（ULID, PK）と `inserted_at` / `updated_at`（`users_tokens` は `inserted_at` のみ）を省略する。

| 区分 | テーブル |
| :-- | :-- |
| マスタ | `clients` / `shipping_items` / `expiration_rules` |
| 伝票・ピック | `shipping_slips` / `slip_allocated_lots` / `total_picks` |
| 認証 | `users` / `users_tokens`（[§7](#7-認証認可)） |

### 3.1 発注元マスタ (`clients`)

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 発注元コード | `client_code` | string | NOT NULL, UNIQUE（CSV 取込時の識別コード） |
| 発注元名 | `client_name` | string | NOT NULL（例：ECサイト、百貨店A） |
| アーカイブ日時 | `archived_at` | utc_datetime | NULL可（NULL=有効）。アーカイブ済みは新規伝票の選択肢に出さない |

### 3.2 発送商品・梱包換算マスタ (`shipping_items`)

在庫側の商品（`items`）と **1対1** で紐づけ、発送独自の「件数 → 箱数・商品数量」の換算を保持する。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 在庫システム商品ID | `inventory_item_id` | ULID | NOT NULL, UNIQUE。在庫側 `items.id`（API 連携キー） |
| 商品コード | `item_code` | string | NOT NULL, UNIQUE。**在庫側の `item_code` と同じ値**（CSV 取込キー） |
| 在庫システムメーカーID | `inventory_maker_id` | ULID | NOT NULL。在庫側 `makers.id`（FK ではない）。**メーカーを特定するキー**。トータルピックのグルーピングに使う |
| メーカー名 | `maker_name` | string | NOT NULL。表示・検索用（登録時点の在庫側メーカー名のコピー） |
| 商品名 | `item_name` | string | NOT NULL。表示用 |
| 1件あたり標準箱数 | `boxes_per_order` | integer | NOT NULL, DEFAULT 1, CHECK (`>= 1`)。3箱になる商品は 3 |
| 1件あたり商品数量 | `pieces_per_order` | integer | NOT NULL, DEFAULT 1, CHECK (`>= 1`)。**在庫を減らす基準値（バラ数）** |
| アーカイブ日時 | `archived_at` | utc_datetime | NULL可（NULL=有効） |

- **メーカーは在庫側のメーカー（`makers`）と ID で紐づける**。発送側にメーカーマスタは持たず、`inventory_maker_id`（ID）と `maker_name`（表示用コピー）を商品に持つ。同じメーカーの商品は同じ `inventory_maker_id` になるため、これでグルーピングや絞り込みができる。
- 登録時は商品コードを入力すると、在庫側 `GET /api/v1/items?item_code=` から `inventory_item_id`・`item_name`・`inventory_maker_id`・`maker_name` を取得して初期入力する（手入力の ID 誤りを防ぐ）。**取得した値のコピーであり、在庫側の変更（商品のメーカー付け替え・メーカー名変更）は自動同期しない**（マスタ画面から再取得できる）。再取得で `inventory_maker_id` が変わった場合、すでに作成済みのトータルピックには影響しない。
- 梱包換算（`pieces_per_order` など）を変更しても、登録済み伝票の数量は変わらない（伝票側にスナップショットを持つ）。

### 3.3 出荷期限ルールマスタ (`expiration_rules`)

「発注元 × 商品」ごとの出荷可能期限ルール。**メーカー単位のルールは持たない**（メーカーは商品の属性であり、必要なら商品ごとに登録する）。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 発注元ID | `client_id` | ULID | NOT NULL, FK (`clients.id`) |
| 発送商品ID | `shipping_item_id` | ULID | NOT NULL, FK (`shipping_items.id`) |
| 最低残日数 | `min_remaining_days` | integer | NOT NULL, CHECK (`>= 0`)。出荷予定日から何日以上の期限が必要か（例：30） |

- `UNIQUE (client_id, shipping_item_id)`
- **最低許容期限日 ＝ 出荷予定日 ＋ `min_remaining_days`（日）**
- **ルールが未登録の「発注元 × 商品」は期限制限なし**（`min_expiration_date` を渡さない。在庫側は出庫予定日以降のロットを対象にする）。
- 伝票は引当時点の最低許容期限日を保持するため、ルールを後から変更・削除しても登録済み伝票には影響しない。このためルールは物理削除してよい。

### 3.4 出荷伝票 (`shipping_slips`)

順不同で届く伝票を管理する。**1行 ＝ 在庫側の1出庫オーダー**（`id` を在庫側の `external_slip_id` として渡す）。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 伝票番号 | `slip_no` | integer | NOT NULL, UNIQUE。**DB シーケンスで自動採番**（読み取り専用）。帳票・画面に `S-000123` 形式で表示する現場用の通し番号 |
| 発注元ID | `client_id` | ULID | NOT NULL, FK (`clients.id`) |
| 発送商品ID | `shipping_item_id` | ULID | NOT NULL, FK (`shipping_items.id`) |
| トータルピックID | `total_pick_id` | ULID | NULL可, FK (`total_picks.id`)。未ピックは NULL。`allocated` の伝票だけが紐づく（[§5.2](#52-トータルピックの作成と作業指示書の出力)） |
| 発注元伝票番号 | `client_slip_no` | string | NULL可。発注元の伝票・注文番号。CSV の重複取込防止に使う |
| 出荷予定日 | `scheduled_ship_date` | date | NOT NULL。ソート・集計の基準軸 |
| 件数 | `order_count` | integer | NOT NULL, CHECK (`> 0`)。伝票に記載された件数 |
| 箱数 | `box_count` | integer | NOT NULL, CHECK (`>= 1`)。初期値 `件数 × 標準箱数`。画面で手修正可 |
| 出庫総数量（バラ） | `total_piece_qty` | integer | NOT NULL, CHECK (`> 0`)。`件数 × 商品数量`。在庫への要求バラ数 |
| 最低許容期限日 | `required_exp_date` | date | NULL可。引当時に適用した値（ルール未登録なら NULL） |
| 在庫出庫オーダーID | `inventory_order_id` | ULID | NULL可。在庫側 `shipment_orders.id`。`allocated` / `packed` / `reversed` では必須 |
| ステータス | `status` | Ecto.Enum | NOT NULL, DEFAULT `pending`。下記 |
| 不足バラ数 | `shortage_pieces` | integer | NULL可。`shortage` のとき在庫側が返した不足数（画面表示用） |
| 登録経路 | `input_source` | Ecto.Enum | NOT NULL。`manual`(手入力) / `csv`(CSV取込) |
| 登録者ID | `user_id` | ULID | NOT NULL, FK (`users.id`) |
| 梱包完了者ID | `packed_by_user_id` | ULID | NULL可, FK (`users.id`) |
| 梱包完了日時 | `packed_at` | utc_datetime | NULL可 |

`status` の値:

| 値 | 意味 |
| :-- | :-- |
| `pending` | 引当待ち（保存済みだが在庫側の引当が未完了。通信失敗・数量変更の途中など） |
| `allocated` | 引当済・未梱包 |
| `shortage` | 在庫不足（期限条件を満たす在庫が足りない） |
| `packed` | 梱包完了・在庫減算済 |
| `cancelled` | 取消 |
| `reversed` | 梱包完了後の取消済（在庫側で出庫取消済） |

- **部分ユニーク**: `UNIQUE (client_id, client_slip_no, shipping_item_id) WHERE client_slip_no IS NOT NULL AND status <> 'cancelled'`（同じ伝票の二重登録を防ぐ。取消後の再登録は可）
- 同じ「発注元 × 商品 × 出荷予定日」の伝票が複数あってよい（追加伝票）。
- 索引: `(scheduled_ship_date, status)`（作業画面の主検索）、`(total_pick_id)`。

### 3.5 引当ロット明細控え (`slip_allocated_lots`)

在庫側が返した「どの期限日のロットが何個引き当てられたか」の控え。現場のピッキング画面に表示する。**在庫側の表示用キャッシュ**であり、在庫の正は在庫側にある。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| 伝票ID | `shipping_slip_id` | ULID | NOT NULL, FK (`shipping_slips.id`) |
| 在庫ロットID | `inventory_lot_id` | ULID | NOT NULL。在庫側 `inventory_lots.id`（FK ではない） |
| 期限日 | `expiration_date` | date | NOT NULL。ピッキング時に目視確認する期限日 |
| 引当バラ数 | `allocated_pieces` | integer | NOT NULL, CHECK (`> 0`)。そのロットからピッキングする個数 |

- `UNIQUE (shipping_slip_id, inventory_lot_id)`
- 再引当・数量変更のときは、同じトランザクションで旧行を削除して新行を保存する。
- 在庫側は `allocated_cases` も返すが、発送システムは常に `req_cases = 0` で要求するため **常に 0**。保存しない。
- 期限日なし商品は `9999-12-31` が返る。画面では「期限なし」と表示する。

### 3.6 トータルピック (`total_picks`)

「出荷予定日 × 発注元 × メーカー」の引当済み伝票をまとめてピッキングする作業単位（[§5.2](#52-トータルピックの作成と作業指示書の出力)）。**明細（商品×期限日の合算）は持たず**、紐づく伝票（`shipping_slips.total_pick_id`）の引当ロット明細から都度集計する。

| 論理名 | 物理名 | 型 | 制約 / 説明 |
| :-- | :-- | :-- | :-- |
| ピック番号 | `pick_no` | integer | NOT NULL, UNIQUE。DB シーケンスで自動採番（読み取り専用）。`TP-000045` 形式で表示 |
| 出荷予定日 | `scheduled_ship_date` | date | NOT NULL |
| 発注元ID | `client_id` | ULID | NOT NULL, FK (`clients.id`) |
| 在庫システムメーカーID | `inventory_maker_id` | ULID | NOT NULL。作成時点の `shipping_items.inventory_maker_id` |
| メーカー名 | `maker_name` | string | NOT NULL。作成時点のコピー（帳票表示用） |
| ステータス | `status` | Ecto.Enum | NOT NULL, DEFAULT `issued`。`issued`(発行済) / `outdated`(要再発行) / `cancelled`(取消) |
| 版 | `revision` | integer | NOT NULL, DEFAULT 1, CHECK (`>= 1`)。再発行のたびに加算し、帳票に「第N版」と表示 |
| 発行日時 | `issued_at` | utc_datetime | NOT NULL。作成または最後の再発行の日時 |
| 発行者ID | `user_id` | ULID | NOT NULL, FK (`users.id`) |

- 同じ「出荷予定日 × 発注元 × メーカー」に複数のピックがあってよい（追加伝票用の追加ピック）。ユニーク制約は設けない。
- 索引: `(scheduled_ship_date, status)`。

### 3.7 ステータス遷移（伝票）

```
            ┌──────────── 再引当（成功） ────────────┐
            ▼                                        │
 登録 ──▶ pending ──引当成功──▶ allocated ──梱包完了──▶ packed ──出庫取消（管理者）──▶ reversed
            │  ▲                  │
            │  └──在庫不足──▶ shortage ──再引当──┘
            │                     │
            └──────取消──────────┴───▶ cancelled（allocated / pending / shortage から）
```

- `packed` / `cancelled` / `reversed` からは他のステータスへ戻らない。
- 数量変更は `allocated` / `shortage` / `pending` で可能。一度 `pending` に戻してから再引当する（[§5.5](#55-数量変更出荷予定日の変更)）。
- `packed` を取り消せるのは管理者のみ（[§5.7](#57-梱包完了後の取消管理者操作)）。

## 4. 在庫管理システムとの連携

在庫側のAPI仕様は在庫側設計書 [§5](食品在庫管理システム設計.md) を正とし、**本書では重複して定義しない**。発送システムは次の API を呼ぶ。

| 用途 | 在庫側 API | 呼び出すタイミング |
| :-- | :-- | :-- |
| 出庫引当 | `POST /api/v1/shipment_orders` | 伝票登録・CSV 取込・再引当・数量変更の再引当 |
| 出庫確定 | `POST /api/v1/shipment_orders/:id/ship` | 梱包完了 |
| 引当解除 | `POST /api/v1/shipment_orders/:id/cancel` | 伝票取消・数量変更の前段 |
| 出庫取消 | `POST /api/v1/shipment_orders/:id/reverse` | 梱包完了後の取消（管理者） |
| 照会 | `GET /api/v1/shipment_orders/:id` | 状態の突合（[§5.4](#54-梱包完了)） |
| マスタ参照 | `GET /api/v1/warehouses` / `GET /api/v1/items?item_code=` | 倉庫ID設定・発送商品マスタ登録時（商品の応答にメーカーID・メーカー名を含む） |

### 4.1 伝票から引当リクエストへの対応

| 引当リクエスト項目 | 値 |
| :-- | :-- |
| `warehouse_id` | 設定値（対象倉庫） |
| `shipment_date` | `shipping_slips.scheduled_ship_date` |
| `external_slip_id` | `shipping_slips.id`（冪等性キー。再送しても二重引当されない） |
| `lines[0].item_id` | `shipping_items.inventory_item_id` |
| `lines[0].req_cases` / `req_pieces` | `0` / `shipping_slips.total_piece_qty` |
| `lines[0].min_expiration_date` | `shipping_slips.required_exp_date`（NULL なら項目ごと省略） |

### 4.2 応答の扱い

| 在庫側の応答 | 発送側の処理 |
| :-- | :-- |
| 201 / 200（成功） | `inventory_order_id` を保存、引当ロットを `slip_allocated_lots` に保存、`allocated` にする |
| 422 `insufficient_stock` | `shortage`、`shortage_pieces` を保存。画面にアラート |
| 422 `validation_failed` | `pending` のまま。エラー内容を画面に表示（設定・マスタ不整合の可能性） |
| 404 `not_found` | `pending` のまま。「倉庫または商品が在庫側に存在しません」と表示 |
| 409 `invalid_state` | 該当伝票を在庫側へ照会（GET）して状態を突合し、画面を最新化 |
| 401 `unauthorized` | 設定エラー。`pending` のまま、管理者向けにエラーを表示 |
| 接続エラー・タイムアウト・5xx | 自動リトライ（最大3回、`Req` の retry）。それでも失敗なら `pending` のまま「再引当」を促す |

- すべて **冪等な呼び出し**（引当は `external_slip_id`、確定・取消・出庫取消は現状態なら 200）のため、リトライしても二重処理にならない。
- 設定値（ベース URL・トークン・倉庫ID・タイムアウト）は `runtime.exs` で `FoodShip.Inventory.Client` のモジュール名キーに集約し、必須値は未設定なら起動時に落とす（coding-rules §13）。

## 5. 業務フローと例外処理

### 5.1 伝票登録（手入力・CSV）

1. オペレーターが「発注元」「出荷予定日」「商品」「件数」（＋任意で「発注元伝票番号」）を入力する、または CSV を取り込む。
2. システムがマスタを参照して「箱数」「出庫総数量（バラ）」「最低許容期限日」を自動計算する。
3. **先に伝票を `pending` で保存（コミット）してから**在庫側の引当 API を呼び、結果で `allocated` / `shortage` に更新する。
   - 在庫側の状態はロールバックできないため、API 呼び出しを DB トランザクション内に入れる coding-rules §7.2 の方式は採らない。先にローカル保存することで、通信失敗・アプリ停止があっても入力内容が消えず、`external_slip_id` による冪等な再引当で復旧できる。
4. 引当が完了（`allocated`）した伝票から、トータルピックの作成と作業指示書の出力に進む（[§5.2](#52-トータルピックの作成と作業指示書の出力)）。

CSV 取込:

- 形式: 1行＝1伝票。列は `client_code, client_slip_no, scheduled_ship_date, item_code, order_count`（文字コードは未決、[§9](#9-未決事項)）。
- **検証エラー（未登録の発注元・商品コード、日付・数値の不正、`client_slip_no` の重複など）が1行でもあればファイル全体を取り込まず**、行番号つきのエラー一覧を表示する（部分取込による重複登録を防ぐ）。
- 検証を通った場合は全行を保存し、**出荷予定日の早い順 → ファイル順**に引当する（在庫が逼迫したとき、出荷が近い伝票を優先するため）。
- **在庫不足は検証エラーではない**。その行は `shortage` で保存し、取込結果プレビューに引当成否を一覧表示する。
- 行数が多い場合は `Task` で処理し、`handle_info` で進捗を更新する（coding-rules §9.9）。

### 5.2 トータルピックの作成と作業指示書の出力

伝票の件数・箱数を入力し、**引当（`allocated`）まで完了した後**に行う。倉庫作業の準備として、複数伝票をまとめてピッキングできるようにし、現場向けの帳票を PDF で出力する。

**トータルピックとは**: 同じ「**出荷予定日 × 発注元 × メーカー**」の引当済み伝票を、**商品 × 期限日**ごとに合算し、まとめてピッキングしたうえで伝票ごとに仕分ける作業単位。

作成手順（作業画面の出荷予定日タブから、`staff` 以上が実行）:

1. 「トータルピック作成」を押すと、**未ピックの引当済み伝票**（`status = allocated` かつ `total_pick_id` が NULL）が「発注元 × メーカー」のグループに分かれて一覧表示される（伝票数・商品数・合計バラ数のプレビュー付き）。
2. 対象グループを選んで作成する。**グループごとに1つの `total_picks` が作成**され、対象伝票の `total_pick_id` が設定される。
3. 作成後は詳細画面へ遷移し、PDF をダウンロードできる。

対象外:
- `pending` / `shortage`（引当が確定していない）、`packed` / `cancelled` / `reversed` の伝票。
- すでにトータルピックに紐づいた伝票（二重にまとめない）。

**追加伝票・変更への対応**:
- ピック作成後に届いた追加伝票は、同じグループの **別のトータルピック（追加ピック）** として作成する。既存のピックは変更しない。
- 紐づき済みの伝票を **数量変更・出荷予定日変更・取消・梱包後取消（出庫取消）**したときは、その伝票をトータルピックから外し（`total_pick_id` を NULL）、ピックを「**要再発行**（`outdated`）」にする。数量変更・出荷予定日変更で外れた伝票は未ピックに戻るので、再引当後に再度ピック作成の対象になる。
- ピック表の集計対象は、紐づく伝票すべて（**梱包済みを含む**。ピッキングはすでに終わっていても、ピック全体の実績として表示する）。
- 要再発行のピックは PDF を再出力して差し替える（版 `revision` が加算され、帳票に「第N版」と表示される）。紐づく伝票が0件になったピックは自動で `cancelled` にする。
- ピックの取消は、紐づく伝票がすべて未梱包（`allocated`）のときだけ可能（伝票は未ピックに戻る）。
- 梱包完了（`packed`）はピックの状態に影響しない。

**出力する帳票（PDF）**:

| 帳票 | 単位 | 内容 |
| :-- | :-- | :-- |
| **トータルピック表** | トータルピック1件につき1通 | ヘッダ: ピック番号・版・出荷予定日・発注元・メーカー・発行日時・発行者。明細: 商品コード・商品名・**期限日**・合計バラ数・合計件数・合計箱数・チェック欄。最終行に合計。後半に **仕分け表**（明細行ごとの「伝票番号 × 数量」の内訳）を付ける |
| **作業指示書** | **伝票1件につき1枚** | 伝票番号・発注元・発注元伝票番号・出荷予定日・メーカー・商品コード・商品名・件数・箱数・出庫数量（バラ）・**引当ロットの期限日 × 個数**・最低許容期限日（ルールがある場合）・所属トータルピック番号。実績記入欄（実際の箱数・担当者・検品） |

- 明細の合算キーは「商品 × **期限日**」（在庫側のロットが入荷日違いで分かれていても、現場で見分けられないため期限日で集約する）。集計は都度、伝票の引当ロット明細から算出する（合計値を別テーブルに持たない）。
- 作業指示書は、トータルピックに紐づく伝票に限らず、`allocated` または `packed` の任意の伝票から単体で出力できる（梱包前の箱数修正後の再出力も可）。
- ピック作成時は、**トータルピック表と所属伝票の作業指示書を1つの PDF にまとめて**ダウンロードできる（並び順: ピック表 → 作業指示書を `slip_no` 昇順）。個別ダウンロードも可。
- 帳票は **都度生成**して保存しない（再出力しても常に最新の伝票内容が反映される。要再発行のピックは出力時に最新化される）。日時は JST で表示する。

### 5.3 出荷日別のピッキング・梱包

- 作業画面は **出荷予定日ごとにタブ分け・ソート**して表示する。タブの「残件数」は `pending` / `allocated` / `shortage` の合計。
- 各伝票行に、引き当てられたロットの **「期限日（例：2026-12-20）× 個数」** を表示する。現場担当者はその期限の商品を目視確認してピッキング・梱包する。
- 梱包時に実際の箱数が変わった場合は、画面上で箱数を修正できる（在庫数には影響しない）。
- 一部だけの梱包（分割梱包）は扱わない。1伝票は全数まとめて梱包完了する。

### 5.4 梱包完了

1. 「梱包完了」ボタン（複数行の一括完了も可）を押すと確認ダイアログを表示する。
2. 在庫側の **出庫確定 API** を呼び、成功したら `packed`、`packed_at`・`packed_by_user_id` を保存し、行をグレーアウトする。
3. 一括完了は **1伝票ずつ順に**呼び、伝票ごとの成否を一覧表示する。失敗した伝票は `allocated` のまま残る。
4. 409 `invalid_state` が返った場合は在庫側へ照会し、在庫側がすでに `shipped` なら発送側も `packed` に更新して整合させる。それ以外は最新状態を表示してエラーにする。

### 5.5 数量変更・出荷予定日の変更

件数または出荷予定日を変更するときの処理（`allocated` / `shortage` / `pending` のみ可。商品・発注元の変更は取消して再登録）。

1. 新しい件数・出荷予定日で `box_count` / `total_piece_qty` / `required_exp_date` を再計算し、`pending` として保存。
2. `inventory_order_id` があれば **引当解除 API**（旧オーダー取消）を呼び、`slip_allocated_lots` を削除。
3. **出庫引当 API** を新しい内容で呼び、結果で `allocated` / `shortage` にする。

トータルピックに紐づいている伝票は、手順1で **ピックから外れる**（[§5.2](#52-トータルピックの作成と作業指示書の出力)）。確認ダイアログにも「トータルピック TP-xxxxxx から外れ、再発行が必要になります」と表示する。

> **注意**: 解除と再引当はアトミックではない。再引当が在庫不足になると、旧引当は解除されたまま `shortage` になる。このため変更時の確認ダイアログに「在庫不足の場合、現在の引当は解除されます」と明記する。途中で失敗しても `pending` として残り、「再引当」ボタンで復旧できる。

### 5.6 追加伝票への対応（順不同・当日追加）

梱包完了後に追加の伝票が届いても、同じ出荷予定日タブ内に「未梱包」としてハイライト表示する。梱包済みの在庫は在庫側で減算済み、未梱包の引当済み在庫はロック済みのため、残りの有効在庫から先出しで引当される。

### 5.7 梱包完了後の取消（管理者操作）

誤操作で `packed` にした伝票を戻す場合。**管理者（`admin`）のみ**。

1. 理由の入力を必須とし、在庫側の **出庫取消 API** を呼ぶ。
2. 成功したら `reversed` にする。在庫は元のロットに戻る（**引当ロックは再設定されない**ため、出荷が必要なら「複製して再登録」で新しい伝票を作る）。
3. 在庫側の受払履歴には `ship_reverse` と理由が残る。

### 5.8 例外ケースへの対策

| 例外シナリオ | 挙動・対策 |
| :-- | :-- |
| ① 伝票入力時に在庫不足 | 入力内容は消さず `shortage` で保存し、不足数を表示。在庫側で入荷された後、「再引当」ボタン（`shortage` / `pending` の行）で引当 API を再実行する |
| ② 引当 API の通信失敗 | `pending` で保存済み。「再引当」で復旧（冪等） |
| ③ 梱包前の件数変更 | [§5.5](#55-数量変更出荷予定日の変更) |
| ④ 梱包前の伝票取消 | `allocated` は引当解除 API を呼んで `cancelled`。`shortage` / `pending` は（オーダーがあれば解除してから）`cancelled`。トータルピックに紐づく伝票はピックから外れ、ピックは要再発行になる |
| ⑤ 同じ伝票の二重登録 | `client_slip_no` の部分ユニーク制約で防止（画面では「すでに登録されています」） |
| ⑥ 梱包完了（`packed`）後の取消 | [§5.7](#57-梱包完了後の取消管理者操作) |
| ⑦ 在庫側マスタとの不整合 | 在庫側の商品が見つからない（404）場合は画面に原因を表示。マスタ画面の「再取得」で在庫側の値を取り込む |

## 8. 実装方針

### 8.1 Context とスキーマ（coding-rules §2.1）

| Context | スキーマ（集約） |
| :-- | :-- |
| `FoodShip.Accounts` | `User`, `UserToken` |
| `FoodShip.Clients` | `Client` |
| `FoodShip.ShippingItems` | `ShippingItem` |
| `FoodShip.ExpirationRules` | `ExpirationRule` |
| `FoodShip.ShippingSlips` | `ShippingSlip`, `SlipAllocatedLot`（登録・引当・梱包・取消・CSV 取込） |
| `FoodShip.TotalPicks` | `TotalPick`（作成・再発行・取消・ピック明細と仕分け内訳の集計） |
| `FoodShip.Inventory.Client` | 在庫側 API クライアント（`Req`）。DB を持たない外部境界モジュール |

- 状態遷移は業務動詞で命名する（`register_shipping_slip/2` / `allocate_shipping_slip/1` / `pack_shipping_slip/2` / `cancel_shipping_slip/1` / `reverse_shipping_slip/3`、`create_total_picks/2` / `reissue_total_pick/2` / `cancel_total_pick/2`）。
- `ShippingSlips` の数量変更・取消・梱包後取消は、紐づくトータルピックの更新（外す・`outdated` 化・0件なら `cancelled`）を同じ `Ecto.Multi` に含める。ピック作成も「ピック挿入＋伝票の `total_pick_id` 更新」を1つの Multi で行う（`FOR UPDATE` で対象伝票をロックし、二重にピックされない）。
- ピック明細の集計は `TotalPicks` のクエリ関数（`defp *_query/2` に分割）で行い、`Utils.Calc` 等でテンプレートに計算式を書かない（coding-rules §6, §10.7）。

### 8.2 PDF 帳票

- 帳票は LiveView ではなく **Controller**（`FoodShipWeb.ReportController`：`total_pick/2`・`work_order/2`・`total_pick_bundle/2`）でダウンロード配信する。認可は HTTP plug で `staff` 以上に限定する（LiveView ではないため `on_mount` は不要）。
- 帳票の HTML テンプレートは `FoodShipWeb.ReportHTML`（HEEx）で作り、A4 縦・日本語フォント（Noto Sans JP）で PDF 化する。生成は `FoodShip.Utils.Pdf` に閉じ込める（外部 I/O の境界。テストではこのモジュールだけをモックしてよい）。
- **推奨**: ブラウザ描画方式の `ChromicPDF`（HTML/CSS をそのままレイアウトでき、日本語・罫線表に強い）。`Dockerfile.dev` に Chromium と日本語フォント（`fonts-noto-cjk`）の追加、`mix.exs` への依存追加、アプリ起動時の supervisor 登録が必要。ライブラリの最終決定は [§9](#9-未決事項) の未決事項。
- 件数が多い場合（例：数十伝票分の束ね PDF）は生成に時間がかかるため、タイムアウトを設定し、必要に応じて Task + `handle_info` で非同期化する（coding-rules §9.9）。
- 画面からの書き込み関数は操作ユーザーを引数に取る。
- テストでモックしてよいのは `FoodShip.Inventory.Client`（外部 I/O の境界）のみ。成功系・在庫不足・通信失敗・409 の各ケースを書く（coding-rules §15.5）。
- 在庫側の更新（引当・確定など）はローカル DB のトランザクションの外で実行し、成功後にローカル状態を更新する。失敗時は冪等リトライで復旧する前提（[§5.1](#51-伝票登録手入力csv)）。
- 採番列（`slip_no` / `pick_no`）は DB シーケンスで採番し、スキーマでは `read_after_writes: true` の読み取り専用フィールドにする（`cast` しない）。

| 4 | 発注元・商品の在庫側マスタとの自動同期 | 現状は登録時コピー＋手動再取得 |
| 5 | ログイン試行制限・セッション期間・メール再設定 | 在庫側と同じ扱い（在庫側設計書の未決事項を参照） |
| 6 | 「複製して再登録」の仕様 | 出庫取消後の再出荷用。複製元の引き継ぎ項目（発注元伝票番号は引き継がない等） |
| 7 | 帳票のレイアウト詳細 | トータルピック表・作業指示書の項目配置、用紙（A4縦で想定）、現場で使っている既存様式（FAX 伝票・納品書との関係）。サンプル帳票のヒアリングが必要 |
| 8 | 帳票へのバーコード／QR の印字 | `slip_no` / `pick_no` をバーコード化してスキャン消込（将来）に使うか。本バージョンは数字表示のみ |
| 9 | PDF 生成ライブラリの最終決定 | `ChromicPDF`（推奨）か、Chromium を使わない方式か。Docker イメージ・本番環境の制約を確認 |
| 10 | トータルピックの作成タイミング | 現状は担当者の手動作成（ボタン）。伝票登録時の自動作成は、印刷後の追加伝票の扱いが複雑になるため見送り |
| 11 | ピッキング実績の記録 | 帳票の記入欄（手書き）のみ。画面での「ピック完了」登録や検品スキャンは対象外 |

## 付録B. ドラフト v1 → v2 の変更点

| # | 変更 | 理由 |
| :-- | :-- | :-- |
| 1 | 在庫側 v2.1 に合わせ、ID を ULID の `id`、列挙を小文字 snake_case の `Ecto.Enum`、`is_active` を `archived_at`、`created_at` を `inserted_at` に変更 | 在庫側・coding-rules との整合 |
| 2 | **API 定義を本書から削除し、在庫側設計書を正とした**。「在庫管理システム側の改修（1箇所のみ）」節を廃止 | 新規開発に「改修前/後」は不要。提供側が仕様を持つべき。v1 の API は在庫側 v2 とパス・項目名が食い違っていた |
| 3 | 伝票の粒度を「1伝票＝1発注元×1商品×1出荷予定日＝在庫側1オーダー（1明細）」と明記。CSV は1行＝1伝票 | v1 は「入力・取込単位ごとに引当」が曖昧だった |
| 4 | ステータスに **`pending`（引当待ち）** と **`reversed`（出庫取消済）** を追加。`shortage_pieces` を追加 | v1 は通信失敗時の状態が無く、梱包後取消の結果状態も未定義だった |

| 6 | 伝票保存を先に行い、その後に API を呼ぶ方式に確定（冪等キー `external_slip_id = 伝票ID`） | 通信失敗で入力が消える／在庫側だけ引当が残る不整合を防ぐ |

| 8 | 出荷期限ルール未登録は「制限なし」と定義し、`required_exp_date` を NULL 可に。ルールは「発注元×商品」単位に限定（メーカー単位は持たない） | v1 は NOT NULL と「商品（メーカー含む）」が曖昧で、ルール無しの場合が定義できなかった |
