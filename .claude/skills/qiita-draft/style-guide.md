# 文章構成・文体ガイド

過去の投稿記事（https://qiita.com/suzuki-t0505 の 5 記事、2021〜2024 年）の傾向をまとめたもの。ドラフトはこのガイドに合わせて書く。

## 全体の構成

1. **導入**（`# はじめに`）: 「今回は〜します。」と記事で扱うことを 1〜2 文で述べる。続けて「この記事では Phoenix のバージョン `1.x.x` を使用しています。」と書き、バージョン確認コマンドの出力をコードブロックで載せる
2. **本編**: 作業した順番どおりに見出しを並べる。時系列で読めば再現できる流れにする（結論を先に置く構成にはしない）
3. **締め**（`## 最後` または `## 終わり`）: 分かったこと・所感を 2〜3 文で書き、「ここまで読んでいただきありがとうございました。」で終える

連載にする場合は、`# はじめに` にシリーズの記事一覧（リンク付き。その記事自身はリンクなし）を載せ、直後に `## 目次` を置き、締めで「次回は〜について見ていきます。」と次回を予告する。

## 見出し

- 見出しは作業内容をそのまま短く書く（「プロジェクトの作成」「ルーティングの設定」「コントローラーの実装」「Google認証を実装」）
- 大きな作業は `##`、その中の手順は `###` に分ける
- 「起きたこと」「背景」のような抽象的な見出しより、具体的な作業名・エラー名を使う

## 1 つの節の書き方

「**一言の前置き → コード → コードの後に説明**」の順で書く。

- 前置きは 1 文（「Google認証用のルートを追加します。」「以下のコマンドで認証機能を追加します。」「まず、プロジェクトの作成をします。」）
- コードの後の説明は、処理の順に「まず、〜。続いて、〜。次に、〜。最後に〜。」と追っていく。関数名は `` `renew_session/1` `` のようにアリティ付きでバッククォートに入れる
- 実行結果は「〜できました。」「問題なく機能しています。」と確認した事実を書き、スクリーンショットを添える（ドラフトでは `（スクリーンショット: 〜）` と置き場所だけ書く）

## コードブロック

| 用途 | 書き方 |
| :-- | :-- |
| 既存ファイルへの変更 | ` ```diff_elixir:lib/sample_web/router.ex `（`+` / `-` を付け、関係ない部分は `...` で省略） |
| 新規ファイル・コードの抜粋 | ` ```elixir:lib/sample/accounts.ex `（ファイルパスを付ける） |
| コマンド | ` ```bash ` |
| エラーメッセージ・実行結果 | 言語指定なしの ` ``` `（原文のまま載せる） |

- ライブラリを紹介するときは、hex.pm などの URL を 1 行で単独に置く（リンクカードになる）
- 注意点は `:::note warn`、補足は `:::note info` で囲む

## 文体

- です・ます調。1 文を短くし、文ごとに改行する
- 一人称は「自分」。つまずいた点や納得した点を、締めや説明の中に素直な感想として書く
- 堅い言い回しや箇条書きの多用を避け、手順を文章でつないでいく
- タイトルは「PhoenixにGoogle認証を実装する」「dialyzerを使った静的解析」のように、技術名と内容を素直に並べる。`【】` は連載の編名にだけ使う
- タグは `Elixir` / `Phoenix` / `LiveView` に、題材のライブラリ名を足す

## 失敗・エラー解決の記事への当てはめ

過去記事は手順解説が中心なので、エラー解決の記事も同じ流れに乗せる。

1. `# はじめに` — 何を実装していて何のエラーが出たか、バージョン
2. `## 〇〇を実装` — エラーが出るまでにやったこと（コード）
3. `## 発生したエラー` — 実行したコマンドと、エラーメッセージの原文
4. `## 原因` — 問題のコードと、処理を順に追った説明。試してだめだったことは `:::note warn` か本文で触れる
5. `## 解決方法` — `diff_elixir` で修正を示し、再実行して直ったことを確認する
6. `## 最後` — 学んだこと・感想、お礼
